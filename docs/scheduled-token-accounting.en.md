# Scheduled Session Token Accounting (EngineCumulative)

> English mirror of [`scheduled-token-accounting.md`](./scheduled-token-accounting.md); the Chinese original is authoritative on any divergence.

This page documents the scheduled-session engine-cumulative token-accounting kernel: the `ScheduledTokenAccounting::EngineCumulative { base_total_tokens, engine_total_tokens }` variant plus the paired match in `persist_scheduled_engine_state`. The kernel landed through the Community PR [pinvou-agent#865](https://github.com/Pinvou/pinvou-agent/pull/865) backflow (itself a port of the closed-source official build's sessions-side change); the backflow landed while this repo's round-1 Rust dead-code sweep had just removed the single-variant predecessor (`PreservePersisted` only) and its plumbing, so this PR re-lands the full kernel on the swept tree and extends it with the cumulative variant. The lifetime total goes through `scheduled_lifetime_total` (saturating base + engine); `persist_scheduled_engine_state` and `persist_scheduled_token_total` share that single encoding, and the combined result replaces rather than accumulates into the persisted total. `scheduled_lifetime_total` is a consolidation that landed together with the kernel — two bare `saturating_add` sites carry no marker requiring them to stay identical; consolidating them means neither site can drift alone.

The producer is deliberately unwired: this tree constructs the variant nowhere outside tests. Wiring needs only an app-side follow-up PR — the spawn-time base is already read from the persisted total in `assistant/engine.rs` on every spawn (`scheduled_base_total_tokens`), cross-turn usage is already accumulated in the forwarder's `TurnComplete` arm, and the producer only needs to construct `EngineCumulative` in the `SessionUpdated` arm. Note, however, that `SessionUpdated` carries no usage, so wiring it alone persists exactly the value the previous `TurnComplete` already persisted (an accounting no-op); the incremental landing stays on the `TurnComplete` arm's direct `persist_scheduled_token_total` write. That write must not be removed or replaced with the enum path — `TurnComplete` has no message payload and cannot build a full `ScheduledEngineState` — and both paths must keep sharing the single `scheduled_lifetime_total` encoding (each contract leg is pinned by its own leg of the regression test).

The workspace-field half-hunk from the same upstream alignment batch was judged broken and is deliberately not ported: `session.metadata.workspace` keeps its existing profile-derived semantics.

Accounting contract: `engine_total_tokens` is usage accumulated since that engine spawned, never a per-update delta; the combined result replaces the persisted total, and a stale base may lower it, so every re-spawn must reload the base from the persisted total. The saturating clamp and the replace-not-max() semantics are both pinned by a regression test (base + engine saturates at `u64::MAX`; stale base `{100, 5}` → 105). The enum and the shared encoding are registered as APP fingerprints in `scripts/fork-guard.sh`, so a future dead-code sweep or alignment sync cannot silently remove the kernel:

```sh
cargo test --manifest-path pinvou3-app/src-tauri/Cargo.toml --lib scheduled_engine
```
