# 应用内升级（deb）设计

> 2026-06-04 实装（commit f1ac20a），全链路 e2e 已验证。

## 一句话

App 启动静默检查线上 `latest.json`，有新版则设置图标亮红点，用户在设置页一键「下载并安装」（sha256 校验 + pkexec 提权 apt），重启生效。

```
启动/手动 → check_for_update (GET latest.json, 三段版本比较)
          → download_update (流式下载 ~/.pinvou3/updates/, 边下边算 sha256, update:progress 事件)
          → install_update  (pkexec apt-get install -y, Depends 自动拉齐)
          → restart_app     (app.restart(), exec 新 inode)
```

## 关键决策与 why

| 决策 | why |
|---|---|
| 自建轻量机制，不用 Tauri updater plugin | 官方 updater 不支持 deb |
| 静态 HTTPS + latest.json，零服务端逻辑 | nginx 托管清单与安装包即可，无业务服务要维护 |
| 路径方式 `pinvou.com/pinvou3/`，不建二级域名 | 使用 Pinvou 独立品牌域名和 HTTPS 证书，复用现有源站及 `/pinvou3/` 发布目录 |
| 更新源 URL 硬编码常量，不进 settings.json | 是基础设施不是用户偏好，可改会成攻击面；release 始终使用固定 HTTPS 地址，`PINVOU3_UPDATE_URL` 仅供 debug/test 指向 loopback 测试服务 |
| 下载目录 `~/.pinvou3/updates/`，不用 /tmp | tmpfs 受内存限制 + 重启清空（下载完提示重启后文件就没了） |
| 安装走 pkexec 弹系统密码框 | 与 super_permission.rs 同套路；但用 `.output()` 捕 stderr 透传 apt 真实报错（lock 占用/磁盘不足） |
| 仅 `latest > current` 才提示 | 天然降级保护，服务器版本 ≤ 本地不打扰 |
| 装完不自动重启 | apt 替换 `/usr/bin/pinvou3` 后老进程持旧 inode 继续跑无害，用户点「立即重启」才 exec 新版 |
| 启动检查失败全静默 | 内网/断网环境不打扰用户；设置页手动检查才显示错误 |
| 发布脚本先传 deb 后传 latest.json | 避免清单已指向新版而 deb 还没传完，客户端 404 |

## 更新源安全迁移与信任模型

正式 release 构建现在固定使用 `https://pinvou.com/pinvou3/latest.json`，不再读取
`PINVOU3_UPDATE_URL`；这是有意的破坏性安全迁移。清单与安装包请求的整个重定向链
逐跳只允许 HTTPS，不能通过 `302` 降级到 HTTP。只有 debug/test 构建可将变量指向
loopback 测试服务，且重定向的每一跳都必须仍是 loopback HTTP/HTTPS。

自托管发行方不能再依赖生产进程环境变量切换更新源；需要在源码中替换
`UPDATE_MANIFEST_URL` 常量、使用有效 HTTPS 源并重新构建客户端。

当前信任根是 HTTPS 更新源及其发布权限。若 HTTPS 源站或发布权限失陷，攻击者能够同时
替换安装包与清单并生成自洽 SHA-256；此风险在当前信任模型中明确接受。客户端和发布台
不增加 Authenticode、证书指纹或时间戳二次阻断，Windows 签名仍以独立签名服务器上的
沃通工具退出码为权威。

## latest.json 格式

```json
{
  "version": "0.3.0",
  "notes": "更新说明（纯文本）",
  "pub_date": "2026-06-10T08:00:00Z",
  "url": "https://pinvou.com/pinvou3/pinvou3_0.3.0_amd64.deb",
  "sha256": "<64位hex>",
  "size": 48291840
}
```

版本号须为合法 SemVer（`sync-version.mjs --check` 保证），且发布不得带预发布/构建后缀——客户端按三段数字比较，预发布号会被判为不更新；sha256 下载后强校验，不匹配删文件拒装。

## 发版流程

1. 改根目录 `VERSION`，运行 `node scripts/sync-version.mjs` 同步各登记版本文件（脚本以 `sync-version.mjs --check` 校验一致，不再是三处手工 bump）
2. 提供发布目标：`export PINVOU3_RELEASE_SERVER='<发布账号>@<发布源站地址>'`（占位符写法；真实值见私有运维资料，脚本缺省报错不再内置）
3. `./scripts/release-deb.sh "本次更新说明"`
4. 双端收尾：脚本只发发布源站，按「服务端现状」把产物镜像到 nginx-edge 并做双端验证

## 服务端现状（双服务器，2026-09-28 起以此为准）

`pinvou.com` 的 DNS A 记录指向 **nginx-edge（公网入口）**；原发布机（发布源站）仍在线。两机的地址、账号与密钥见私有运维资料，不写入本仓。两机均为 nginx 静态托管 `/var/www/pinvou3/`，**两机之间没有自动同步**：发版只落一台，另一台就是旧版/404（0.10.5 发版实测踩坑：只发发布源站一台时，公网 latest.json 仍是 0.10.4、新 dmg 404）。

| | 发布源站 | nginx-edge（pinvou.com 公网入口） |
|---|---|---|
| SSH | 发布账号（见私有运维资料） | 发布账号（见私有运维资料） |
| 目录属主 | `admin:admin`，rsync 直传免 sudo | `pinvou-update:pinvou-update`，上传后需 `chown` |
| nginx 配置 | `/etc/nginx/sites-available/pinvou`（源文件 `deploy/nginx-pinvou-domain.conf`），OTA location include 自 `/etc/pinvou3/nginx-pinvou3-updates.conf`（仓库副本当前的部署目标，线上迁移完成前仍为旧路径 `~/pinvou3-deploy/`，迁移见下） | `/etc/nginx/sites-available/pinvou`，OTA location 在 `/etc/nginx/snippets/nginx-pinvou3-updates.conf`（其副本另含遗留 `/pinvou3-global/stable/` 海外旧通道，ma-xiao 时代产物，勿动） |
| HTTPS | Certbot / Let's Encrypt，`certbot.timer` 自动续期 | acme.sh（ZeroSSL），证书在 `/etc/nginx/ssl/` |

### OTA include 配置放置与迁移

仓库副本 `deploy/nginx-pinvou-domain.conf` 现 include `/etc/pinvou3/nginx-pinvou3-updates.conf`（不再指向家目录旧路径）。源站按下面步骤放置并迁移；迁移完成前，线上生效的仍是 `~/pinvou3-deploy/` 旧路径——此时直接部署仓库副本，`nginx -t` 会因 include 目标缺文件直接失败、reload 被拒绝（线上继续用旧配置，OTA 不丢），但未放置文件就重启 nginx 会让整个站点起不来：

```bash
# 先把仓库副本 deploy/nginx-pinvou3-updates.conf 上传到源站，再在源站执行（占位路径均为固定系统路径，无敏感值）
sudo mkdir -p /etc/pinvou3
sudo install -m 644 deploy/nginx-pinvou3-updates.conf /etc/pinvou3/
# 把 sites-available/pinvou 的 include 由 ~/pinvou3-deploy/nginx-pinvou3-updates.conf
# 改为 /etc/pinvou3/nginx-pinvou3-updates.conf，然后：
sudo nginx -t && sudo systemctl reload nginx
```

发版步骤（release-*.sh 目前只发布到源站；下文 `$PINVOU3_ORIGIN_HOST` 为发布源站地址，从私有运维资料取值，或直接 `export PINVOU3_ORIGIN_HOST="${PINVOU3_RELEASE_SERVER#*@}"` 与发布目标同源）：

1. 按上文发版流程把包 + `latest.json` 发到发布源站（先文件后清单，原子改名）；
2. 手工镜像到 nginx-edge：同法上传同名文件（远端 sha256 校验）→ 备份 `latest.json.bak.<UTC时间戳>.pre-<版本>` → 上传与源站一致的 `latest.json`（`.new` → 回读校验 → `mv` → `chmod 644` → `chown pinvou-update`）；
3. 双端验证：`curl https://pinvou.com/pinvou3/latest.json`（公网，走 edge）与 `curl --resolve "pinvou.com:443:$PINVOU3_ORIGIN_HOST" https://pinvou.com/pinvou3/latest.json`（直连源站）对应字段都应是新版——deb 发版比对顶层 `version`/`url`/`sha256`，macOS 发版比对 `platforms["macos-universal"]` / `platforms["macos-arm64"]` 的 `version`/`sha256`（顶层字段只随 deb 发版更新，macOS 单独发版时顶层不变是预期）；
4. 产物可达：公网 `curl -fsSI https://pinvou.com/pinvou3/<本次新包文件名>`（=edge）与 `curl -fsSI --resolve "pinvou.com:443:$PINVOU3_ORIGIN_HOST" https://pinvou.com/pinvou3/<本次新包文件名>`（源站）均应 200——0.10.5 踩坑正是新 dmg 公网 404。

两机的 `latest.json` location 均带 `Cache-Control: no-cache`，客户端每次检查都拿最新；包文件名带版本号、内容不可变，可放心缓存。

## e2e 验证方法

```bash
# 1. 假更新源：latest.json(version=9.9.9) + 真 deb（sha256 重算填入）。
#    http.server 以 CWD 为站点根，更新 URL 带 /pinvou3/ 前缀：文件放在 pinvou3/ 子目录、
#    服务从其父目录启动（在 pinvou3/ 里面启动会 404——站点根多了一层）。
#    本命令在前台驻留；客户端步骤须另开一个终端执行。
mkdir -p /tmp/fake-updates/pinvou3 && cd /tmp/fake-updates && python3 -m http.server 8899
# 2. （另开终端）env 指向假源启动
PINVOU3_UPDATE_URL=http://127.0.0.1:8899/pinvou3/latest.json ./pinvou3-app/run-dev.sh
# 3. 红点 → 设置页发现 9.9.9 → 下载进度 → pkexec → 安装 → 重启
# 4. 降级保护：清单改 0.0.1 → 应显示「已是最新版本」
```

## 边界情况

| 情况 | 处理 |
|---|---|
| apt lock 占用 / 磁盘不足 | stderr 末尾透传，设置页红字显示 |
| sha256 不匹配 | 删文件 + 报错，不进安装 |
| pkexec 取消（exit 126） | 报「用户取消授权」，状态回滚 |
| 重复下载 | 后端批准记录对应的确定性文件已按精确大小和 SHA-256 复验时跳过 |
| 前端篡改路径或更新元数据 | download/install 必须匹配后端随机 receipt 与批准的版本、URL、大小、SHA-256；不信任前端副本 |
| 下载路径被符号链接或特殊文件占用 | 仅接受普通非符号链接文件；下载写入同目录自有随机 `.part` 后无覆盖原子提交 |
| 用户目录安装包在提权前后被替换 | 提权 helper 复制到 root-owned 临时文件，在 root 上下文复验精确大小/SHA-256 后才交给 apt |
