# 控制端 claim 限流桶回收

来源、连接与全局限流仍按固定窗口依次消费；默认每60秒分别为30、10、10000次，
来源和连接表各最多4096桶。配对码查询前拒绝的请求仍返回同一公开无效码错误，
内部 audit 用 claim_rate_limited 与 claim_invalid 区分准入和查询结果。

新 key 遇满表时，每轮最多检查64个不同的桶；表不足64桶时，该轮每桶只检查一次。
后续满表请求仍可再次扫描活跃桶，不承诺跨轮永不重复。
已过期桶删除；仍活跃桶按原值移至表尾，started_at 和 count 均不改变。
后续满表扫描从未检查的前部继续，避免持续续期的前缀遮挡过期尾部。
不新增游标、过期索引或后台任务，也不清空活跃表、增加容量或放宽限额。

公平进展依赖后续满表请求；它不承诺任意位置的空位在首次请求中就被找到。
在一张不超过容量上限的表内，原有未检查桶会在有限轮次中被访问；续期后仍活跃
的桶按实际窗口保留。全部桶仍活跃时继续拒绝新 key，已有 key 的限额也不会重置。

回归：在 remote-control-relay 运行 npm test。新增真实 manager、假时钟和合法但
不存在的配对码，分别验证两个表的65/4096容量、多窗口续期与尾部替换、全活跃
拒绝及有效计数、窗口中段扫描不延后原到期点、三层窗口边界/时钟倒退和原短路计费顺序。audit 与实际 lookup
计数共同断言，不能因公开错误相同就把被限流误认作已进入查询。

这些测试不启动真实 Relay，不证明实际公网吞吐量或部署安全门槛。
