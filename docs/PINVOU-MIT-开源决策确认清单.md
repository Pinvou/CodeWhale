> 本文是工程与风险评估，不替代正式法律意见。

## 1. 当前结论

审计当时的结论是：PINVOU 可以开源，MIT 也适合“优先扩大采用、允许商业生态”的目标，但当时的私有仓库**不具备直接公开条件**。截至 2026-07-26，干净公开仓库已经建立；本节以下内容保留为历史审计记录，不代表公开仓库仍处于相同状态。

以下 P0 项全部关闭后，才能批准公开：

- 软件著作权和公司授权明确；
- H3C 内部代码、二进制、协议、品牌和生产运维内容完成拆分；
- 当前文件和 Git 历史中的密钥全部轮换并清理；
- 第三方代码、技能、二进制和素材的许可证完成核实；
- 使用全新、干净的公开仓库，不携带未经审计的旧分支、tag、PR 和 Actions 历史；
- 开源治理、安全响应和持续维护机制准备完成。

状态约定：

- ✅ 已由现场审计确认
- ⬜ 需要团队确认
- ⛔ 未完成前禁止公开
- ⚠️ 可以保留，但必须明确接受风险

建议：如果主要目标是生态、传播和采用，MIT 合适；如果核心桌面代码本身就是主要商业壁垒，需要重新评估许可证和公开范围。

### 3.2 是否接受 MIT 的商业后果

⬜ 核心团队明确接受以下结果：

- [ ] 任何人都可以复制、修改和重新发布 PINVOU；
- [ ] 任何人都可以换品牌后销售；
- [ ] 任何人都可以把修改后的版本闭源；
- [ ] 第三方没有义务把修改贡献回来；
- [ ] 第三方可以基于 PINVOU 开发直接竞品；
- [ ] 已经按 MIT 发布的版本不能再从合法获得者手中收回授权；
- [ ] 团队愿意把商业护城河放在品牌、服务、企业能力和交付上，而不是代码独占上。

MIT 的主要条件是保留版权和许可证声明。官方参考：

- [OSI：MIT License](https://opensource.org/license/mit)
- [Choose a License：MIT](https://choosealicense.com/licenses/mit/)

### 3.3 最终开源边界

⬜ 确认是否采用以下默认边界。

建议公开并采用 MIT：

- 通用 Tauri/React 桌面应用；
- Agent 编排、会话和产物 UI；
- 通用 MCP、Skills、Commands 和工作流框架；
- 通用本地知识库、模型配置、记忆和产物管理能力；
- 通用远程控制协议中经安全审计、与生产部署解耦的部分；

建议继续私有：

- 未经授权的企业工作流、测试数据、素材和基线。

## 6. 推荐仓库结构

```text
Pinvou/pinvou3                    公开，MIT
├── 通用桌面 UI
├── 通用 Agent 能力
├── 通用 MCP / Skills / Workflow
├── 通用本地模型和知识库能力
└── 第三方许可证声明

Pinvou/pinvou3-internal           私有
├── H3C EIP
├── H3C 知道
├── H3C 品牌资产
├── 内部 OTA
├── 生产部署脚本
├── 内部测试与设备配置
└── 企业专属工作流

Pinvou/pinvou3-release            可选，私有
├── 签名密钥
├── 共享 API Key
├── Release CI
├── 发布服务器配置
└── 官方安装包生成
```

基本原则：公开仓库不能依赖私有仓库才能完成基本构建和主要功能；私有层可以依赖公开核心。

## 7. 推荐执行顺序

### 阶段一：决策与授权

1. 确认开源目的和 MIT 商业后果；
2. 确认公开/私有边界；
3. 确认版权主体；
4. 完成公司、法务、安全和开源委员会审批；
5. 处理历史贡献者授权。

### 阶段二：拆分与密钥处理

1. 拆除 H3C EIP 和知道；
2. 移走 H3C 品牌素材；
3. 移走生产部署和 OTA；
4. 轮换全部候选 Key；
5. 删除内部地址、账号和网络拓扑；
6. 清理第三方素材并补齐许可证。

### 阶段三：建立公开仓库

1. 保留现有私有仓库；
2. 从干净快照建立公开仓库；
3. 添加 MIT、NOTICE、SECURITY 等文件；
4. 添加贡献者归属；
5. 启用安全扫描、依赖扫描和主分支保护。

### 阶段四：发布验证

1. 匿名 clean clone；
2. Linux 和 Windows 构建；
3. 全历史密钥扫描；
4. 依赖许可证扫描；
5. SBOM 检查；
6. README、Issue、PR 和安全流程检查；
7. 最终开源签字确认。

### 阶段五：公开后的持续维护

1. 建立漏洞响应负责人和时限；
2. 定期执行密钥和依赖扫描；
3. 对外发布签名构建和校验值；
4. 明确官方版本与社区 fork 的关系；
5. 定期复查公开/私有边界；
6. 确保内部 overlay 的提交不会被误推到公开仓库。
