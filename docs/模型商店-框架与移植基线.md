# 模型商店：框架与移植基线

> 从 LMM（`D:\LMM-Rust`，Rust + Tauri，约 11.7k 行 core）里提炼出来的业务框架，
> 作为**在 pinvou3 内原生实现模型商店模块**的依据。不再用 sidecar 形式。
> 最后更新 **2026-09-18**。

---

## 0. 这份文档解决什么

LMM 是给 H3C MegaCube / NVIDIA GB10（ARM64 Linux）做的本地模型管理应用。它已经在真机上
跑通了完整链路，也踩了两个多月的坑。现在要把这套能力**原生做进品悟**，只编进 Linux 版。

所以这份文档只回答三件事：

1. 模型商店到底在做什么（业务骨架）
2. 哪些约束是**血换来的**，新实现必须守住（否则会把同样的坑再踩一遍）
3. 移植时哪些搬、哪些扔、怎么分期

## 1. 一句话业务

> 从**模型商店**下载模型卡片 → 按卡片里的**六个 shell 脚本**装引擎、下权重、部署、启用
> → 本机跑起一个 OpenAI 兼容服务 → 品悟直接用它对话。

全程用户不碰 API Key，不碰命令行。

### 数据流

```
   商店服务器                      本机
 ┌──────────────┐          ┌─────────────────────────────┐
 │ card.json    │  HTTPS   │ 卡片库(sqlite)              │
 │ 六个脚本     │ ───────► │  ├ 记录：状态/端点/脚本副本 │
 │ 附属文件     │ 内容寻址 │  └ API Key                  │
 └──────────────┘          │                             │
                           │ 脚本执行器(pty)             │
                           │  ├ 注入 LMM_* 环境变量      │
                           │  ├ 解析进度/提示/标记行     │
                           │  └ 静默超时 / 取消          │
                           │         │                   │
                           │         ▼                   │
                           │ docker 容器 ← 引擎镜像      │
                           │   + 权重目录(几十~上百 GB)  │
                           │         │                   │
                           │         ▼                   │
                           │ http://127.0.0.1:<port>/v1  │
                           └─────────────────────────────┘
```

**关键认知：模型商店本身不懂任何模型。** 它是一个**脚本编排器 + 状态机**。怎么装 vLLM、
怎么起 SGLang、权重放哪，全写在卡片作者交付的脚本里。商店只负责：按顺序跑、把过程如实
显示给用户、把结果记进库、出错时说人话。

这个边界是整个设计的地基——它让"上架一张新卡"不需要改客户端。

| `errors.rs` | 347 | 把技术错误翻译成用户看得懂的话 | 直接搬 |

|---|---|---|
| `admin.rs` | **1880** | 本地 HTTP 管理接口，**纯粹为 sidecar 形态存在**。原生实现后前端直接调 Tauri command，这一层整个消失 |

少一个"token 不能出栈到前端"的安全约束。

## 3. 卡片契约

### 卡片 = card.json + 六个入口脚本（+ 可选附属文件）

```
install_engine.sh    装推理引擎（docker 镜像 / ollama / …）
download_model.sh    下权重
deploy.sh            部署（写配置、探 GPU 直通方式）
enable.sh            启用（起容器，直到服务真的可用）
stop.sh              停用
uninstall.sh         卸载
```

固定文件名、固定语义。**执行器只认这六个名字**，不解析脚本内容。

### 宿主 → 脚本：环境变量

```
LMM_CARD_ID            卡片 id
LMM_MODEL_NAME         模型名（库里的主键之一）
LMM_MODELS_DIR         权重根目录（宿主规定，脚本必须往这儿放）
LMM_STAGING_DIR        下载暂存目录
LMM_SOURCE_REPO_ID     HF 仓库名
LMM_SOURCE_FILENAME    单文件模型的文件名
LMM_MODEL_SIZE_BYTES   标称体积（算进度用）
LMM_ENGINE_NAME/_VERSION/_IMAGE    引擎标识
LMM_DEPLOY_PROFILE     用户选的部署方案 id
LMM_HF_ENDPOINT/_TOKEN 下载源与凭据（**选源是宿主的职责，卡片不该写死**）
LMM_OLLAMA_HOST        ollama 地址
LMM_PURGE_WEIGHTS      1=删权重 0=保留（卸载时）
LMM_PROBE_ONLY         1=只探测不安装（引擎探针）
LMM_CANCEL_FILE        取消标记文件路径，脚本应当轮询它
LMM_WORKER             双机卡用：宿主可执行文件路径，供脚本调用从机控制
```

### 脚本 → 宿主：标记行（写到 stdout）

```
LMM_PROGRESS_BYTES=已下载/总量      进度条、网速、剩余时间
LMM_PROMPT=<问题>                   向用户要一个输入（暂停等待）
LMM_PROMPT_FORM=<JSON>              向用户要一组字段（比如从机地址+密码）
LMM_CONTAINER_NAME=<名字>           报告容器名 —— **判断"这容器是不是我起的"的唯一依据**
LMM_ENDPOINT_URL=<地址>             报告服务地址
LMM_ENDPOINT_MODEL=<id>             报告服务真正认的模型 id
LMM_NEED_ROOT=1                     这一步需要提权
```

> **`LMM_CONTAINER_NAME` 为什么重要**：镜像不是身份。别人用同一个镜像起的容器跟我们的
> 长得一模一样，只有容器名能区分。

## 4. 状态机

```
  可下载 ──下载──► 已下载 ──部署──► 已部署 ──启用──► 运行中
              ▲         │              │              │
              │         │              └──── 停用 ◄───┘
              │         │
              └─卸载────┴──────────────────────┘
              （权重留在盘上，卡片留在库里）

  已下载 ──删除──► 可下载
         （权重真删，记录移除）
```

库记录里两个字段表达它：`status ∈ {downloaded, deployed}` + `running: bool`。

**卸载和删除是两个动作，区别不只是权重删不删，更是卡片留不留在库里**：

| 动作 | 权重 | 库记录 | 结果 |
|---|---|---|---|
| **卸载** | 留在盘上 | **留着**，退回「已下载」 | 下次点「部署」直接用，不必重下 |
| **删除** | 真删 | 移除 | 腾出磁盘，要用得重新下载 |

两件事必须同进同退：权重留着而记录没了 → 几十 GB 没有任何界面管得到；记录留着而权重
没了 → 库里多一条指向空气的死数据。

## 5. 必须守住的不变量（都是血换来的）

### 5.1 执行器层

| # | 不变量 | 不守会怎样 |
|---|---|---|
| 1 | **取消等于失败**。取消必须返回错误，绝不标记成功 | v1.0.6 的大 bug：用户取消了下载，界面显示"已完成" |
| 2 | **pty 必须关 ECHO**（`TCSANOW`） | 用户输入的答案会原样回显进日志，密码也一样 |
| 3 | **静默超时要分档**，不能一刀切 | 卸载是几百 GB 的 `rm -rf` 且全程不出声，5 分钟那档会把它误杀，杀完磁盘半删、记录完好，之后每次重试都失败 |
| 4 | 工作线程必须有 **panic 兜底**（Drop 守卫 + `catch_unwind`） | job 一 panic：卡片在并发表里永久锁死、日志长轮询永不返回、清理任务也清不掉它 |
| 5 | **剥离终端控制序列**再进日志 | 进度条转义字符糊满整个日志面板 |

超时分档（实测值）：

```
默认（download_model / stop）      300 秒无输出
install_engine / deploy / enable / uninstall   1800 秒无输出
引擎探针                            20 秒
```

### 5.2 生命周期层

| # | 不变量 | 不守会怎样 |
|---|---|---|
| 6 | **脚本退出 0 ≠ 事情做完了**。结论必须来自磁盘的实际样子 | 2026-09-18 真机：`ornith15-bf16` 的卡片脚本根本不删权重（spec 1.0 老卡），退出 0，记录被删 → **67GB 孤儿**，界面再也管不到 |
| 7 | **释放量必须是实测差值**，不能用 card.json 的标称体积 | 界面报"已释放 67GB"而磁盘一个字节没少 |
| 8 | **并发约束必须全局唯一**。同一张卡不能被两处同时操作 | 真机：两个 `hf download` 抢同一批文件的锁，速度从 2.2MB/s 掉到 569KB/s |
| 9 | **容器以 root 写进挂载目录的文件，普通用户删不掉** | 2026-09-18：735 个 root 属主的 JIT 缓存让 `rm -rf` 失败 → 整个卸载非零退出，而此前容器和 22GB 权重已经删了。可重建的缓存**不该**让卸载失败 |
| 10 | **卸载默认真删权重是宿主的行为**，跟规范里写给卡片作者的"默认保留"不是一回事 | 两边搞混会删掉不该删的 |

### 5.3 接入与网关层

| # | 不变量 | 不守会怎样 |
|---|---|---|
| 11 | **模型名必须一字不差**。转发时要把请求里的 `model` 换成库里的 `endpoint_model` | 差一个字符上游就 404 |
| 12 | 判断"这个模型能不能接进对话"看 **`endpoint_url`，不是引擎名** | 引擎名是开放集合；文生图/视频卡（`/generate`、ComfyUI 根）不是对话模型，往 `/v1/chat/completions` 发会拿到 422，而界面只会说一句笼统的"服务不可用" |
| 13 | 模型卸载后，品悟模型列表里指向它的行**必须一起清掉** | 网关此后对那个 model_name 一律 404，而 404 在多数客户端眼里是"地址写错了"不是"模型没了"。那行死数据很可能正是当前默认模型 |
| 14 | 回环地址也要带鉴权（`credential_action: replace`） | 品悟认为"本地模型不需要 Key"，漏了会以 `credential_state: missing` 存下 → 网关 401 → 被误判成 generic 错误 |

### 5.4 工程层

| # | 不变量 | 不守会怎样 |
|---|---|---|
| 15 | 错误分类用**词边界**匹配，不要在整段原文里做子串匹配 | `ConnectTimeout=10` 里的 `timeout` 命中，把真正的原因（ssh 返回 255 = 连不到从机）换成"操作超时，请稍后重试"。**把人引向错误方向，比不给提示更糟** |
| 16 | 进度事件必须真的有人监听 | 旧版发的 `update-progress` 事件前端根本没订阅，所以下载时从来没有进度条 |
| 17 | 符号链接不能打在容器挂载目录**内部**（要打在挂载点本身） | 容器里那个链接是悬空的 |
| 18 | 内置卡片的脚本随应用升级，**刷新逻辑要放在所有启动路径上** | sidecar 模式下 `refresh_builtin_cards()` 从不执行，改了脚本推上去一点效果没有，白查一轮 |

## 6. 原生化后的形态

### 6.1 模块布局（建议）

```
pinvou3-app/src-tauri/src/features/model_store/
  mod.rs              对外门面 + #[cfg(target_os = "linux")] 门控
  db.rs               sqlite 卡片库
  store_client.rs     商店 API 客户端
  script_runner.rs    pty 执行器（协议、超时、取消）
  lifecycle.rs        六个脚本的编排（原 model_manager 主体）
  run_state.rs        任务与日志
  errors.rs           错误翻译
  orphans.rs          残留清理
  (可选) gateway.rs / worker.rs / probe.rs
  data/test-store/    内置测试卡
```

命令层 `src-tauri/src/app/commands/model_store.rs`，前端复用现有
`src/features/model-store/`（3,648 行已经写好且有测试）。

### 6.2 Linux-only 门控

pinvou3 已有成例（`features/lmm/platform/{linux,unsupported}.rs`）：真实实现只在 Linux
编译，其他平台给一个返回 `installed: false` 的空壳。前端侧栏入口已被 `lmmInstalled`
门控，Windows/macOS 上整个不渲染。**这套门控照搬即可**，改个名字。

依赖也要跟着门控（`Cargo.toml` 的 `[target.'cfg(target_os = "linux")'.dependencies]`），
否则 Windows 构建会去编 rusqlite / nix 之类的东西。

### 6.3 前端要改的地方

现有前端通过 `lmm-client.js` 发 HTTP 到 sidecar。原生化后：

| 现在 | 改成 |
|---|---|
| `lmmRequest('POST', '/admin/v1/...')` | `invoke('model_store_...')` |
| `GET /runs/{id}/log?from=N&wait=25` 游标长轮询 | Tauri 事件推送（或保留游标语义，改成 command 轮询） |
| sidecar 拉起/握手/收尸 | 整个删掉 |
| Bearer token | 整个删掉（同进程，没有跨进程边界） |

**前端 3,648 行里，真正跟 sidecar 绑定的只有 `lmm-client.js`（约 300 行）和
`useLmmTasks.js` 的长轮询部分。** 其余（列表合并、状态机、卡片详情、任务面板、品悟模型
接入、厂商图标）与传输方式无关，可原样保留。

### 6.4 分期建议

| 期 | 内容 | 产出 |
|---|---|---|
| **一期** | db + store_client + script_runner + lifecycle + run_state + errors，内置测试商店 | 能下载、部署、启用、停用、卸载、删除一张卡 |
| **二期** | orphans（残留回收）、已安装引擎管理、system_probe | 磁盘能收得回来，装不上时说得清为什么 |
| **三期** | gateway（局域网暴露）、worker（双机卡） | 按需 |

## 6.5 从本地目录 / U 盘导入

**框架已落地（2026-09-20），卡片侧消费待接**——见本节末「当前状态」。

**这条原定是一期之后的重点**（2026-09-18 定的）。

下载是整条链路上最贵的一步：权重动辄几十到上百 GB，引擎镜像几十 GB（SGLang 那个
49GB），而目标环境的出口带宽实测只有 233 KB/s。所以要给用户第二条路：**东西已经在
本机别的目录、或者在 U 盘上时，直接拿来用，不要再下一遍。**

已有的先例可以照抄：MiniMax-H3 那张卡的 `install_engine.sh` 就是这么做的——自动扫
暂存目录 / `~/Downloads` / U 盘挂载点，找不到才 `LMM_PROMPT` 问一次路径，取到后按
`SOURCE_LOCKS.json` 校验 sha256。

要做成通用能力的话，几个必须想清楚的点：

1. **扫哪儿**：常见下载目录 + 已挂载的可移动设备（`/media/<user>/*`、`/mnt/*`、
   `/run/media/<user>/*`）。不要全盘扫——几 TB 的盘上 `find` 一遍的代价用户不会接受。
2. **怎么认**：靠**内容**而不是文件名。权重按 `weights.sha256` 清单逐个核对，镜像按
   `RepoDigests` + 平台核对（不能用 image `.Id`，containerd image store 下它返回的是
   清单摘要不是配置摘要——这个坑 Qwen3.8-Flash-Next 那张卡踩过）。
3. **认错了比没认出来更糟**：校验不过就当没找到，老老实实去下载，绝不"差不多就用"。
4. **U 盘随时会被拔**：导入过程中设备消失要能说清楚发生了什么，而不是报一句 I/O error。

### 当前状态（2026-09-20）

分工定了，而且跟上面第 2 条「怎么认」的结论一致：**宿主回答「去哪找」，卡片脚本
回答「这份对不对」。**

定这个分工是因为一个硬事实——**权重目录名是卡片内部的知识**，宿主推不出来：

| 卡片 | 权重目录 | `source_repo_id` 末段 | 对得上 |
|---|---|---|---|
| qwen38fn-nvfp4-single | `$LMM_MODELS_DIR/Qwen3.8-Flash-Next-NVFP4` | 同名 | ✅ |
| ornith15-bf16 | `$LMM_MODELS_DIR/Ornith-1.5-35B-A3B` | 同名 | ✅ |
| qwen38-27b-sglang0519 | `$LMM_MODELS_DIR/Qwen3.8-27B-NVFP4-unsloth` | `Qwen3.8-27B-NVFP4` | ❌ |
| minimax-h3-int8-single | `$LMM_MODELS_DIR/$LMM_MODEL_NAME` | 两个仓库拼的一句话 | ❌ |
| deepseek-v4-flash-vision-dual | `$CARD_STORE/model` | 不在权重目录下 | ❌ |

7 张卡里只有 4 张能用仓库名末段推出目录名。而能同时回答「是哪个模型」和「全不全」
的只有卡片脚本自己——它手里有目录名，也有哈希清单。

**已落地（`platform/linux/import_scan.rs`）**

- 搜索根目录收敛成一处，且**可配**：`Settings::import_scan_dirs` +
  `model_store_storage_settings` / `model_store_set_storage_settings` 两个命令，
  界面在模型商店页头的「存储」按钮。
- 内置根目录：当前权重目录、暂存目录、`~/models`、下载/桌面，以及**运行时枚举**
  的可移动介质（`/media/<user>/*`、`/run/media/<user>/*`、`/mnt/*`）。
- 通过 `LMM_IMPORT_DIRS` 下发给**所有**脚本（含 `install_engine`，MiniMax 找交付包
  用的是同一批位置），换行分隔——U 盘卷标带空格和中文是常事。
- 下载前扫一遍（15 秒预算、每根 2 层、不跟软链、跳过点目录），结果
  **写进运行日志**并通过 `LMM_IMPORT_CANDIDATES` 交给下载脚本。

**为什么把根目录列表收敛这件事本身就值**：改之前有四张卡各写各的列表
（ornith15 找 `~/LMM/model`，MiniMax 找 `$HOME`，彼此都不一样），而**没有一张
包含 `~/models` 或用户配置的权重目录**。2026-09-20 踩的就是这条：用户把 124GB 的
Qwen3.8-Flash-Next 放在 `~/models`，卡片一个都不看那儿，照样从网上重下。

真机（192.168.11.29）上按新规则预演，U 盘 `/media/sky/gannp` 上另有 7 个模型、
约 400GB 是当前完全看不见的，其中 `Ornith-1.5-35B-A3B`（67GB）的目录名跟
ornith15 卡片期望的完全一致。

**卡片侧消费：二期**（2026-09-20 定的）

眼下**没有一张卡片脚本读 `LMM_IMPORT_DIRS` / `LMM_IMPORT_CANDIDATES`**，所以推理
引擎和权重的**自动复用**还没有真正发生——下载前用户能在日志里看见本机已有什么，
但脚本不会去用它。一期到此为止，接上的两件事排进二期：

1. 往卡片的 `common.sh` 里加一个共用的 `lmm_find_imported()`，消费这两个变量，
   命中后交给卡片自己的完整性判据核对。要重新上架生产商店。
2. **复用方式要定**：固定盘上的副本可以软链/硬链进权重目录，但可移动介质上的
   不行——U 盘一拔模型就悬空，而那时用户早忘了它是链过来的，只能整份拷。这一项
   要往用户自己的目录里写东西，动手前先确认。

一期先落地「可配 + 看得见」是有道理的：用户当下真正被卡住的是**权重目录跟实际
存放位置对不上**（2026-09-20 那 124GB），那一条改设置就能解，不需要等复用。

### 数据目录

一期用 `~/.pinvou3/model-store/`：

```
~/.pinvou3/model-store/
  models.db          卡片库
  models/            权重（几十~上百 GB）
  staging/           下载暂存
  cards/<card-id>/   卡片的脚本与运行期状态
  vendor/<card-id>/  厂商部署包
```

跟品悟自己的数据放一起，卸载品悟时一目了然。**权重目录要允许用户改**（LMM 本来就支持，
搬过来成本不高）：几十上百 GB 的东西，用户很可能想放到别的盘。

> 注意：这跟设备上 LMM 遗留的 `~/.local/share/local-model-manager/`（含约 106GB 已下载
> 权重）是两套，互不干扰——按 2026-09-18 的决定「另起炉灶」。旧数据等新实现验通之后
> 一次性清理。

## 7. 移植时的已知债

这些是 LMM 现在就有的问题，**移植是修掉它们最好的时机**，不要照搬：

1. **脚本退出 0 但权重还在 → 记录照样被删**（第 5.2 节第 6 条）。正确做法：purge 请求
   跑完发现权重仍在磁盘上，就**不要删记录**，退回「已下载」并如实告知。
2. **内置卡脚本刷新只挂在 GUI 启动路径上**（第 18 条）。新实现要挂在模块初始化处。
3. **`qwen38-27b-nvfp4-mtp` 的权重下载没有任何 sha256 校验**——厂商包里就没给清单。
4. **正式商店的 `ornith15-bf16` 是 spec 1.0 老卡**，不认 `LMM_PURGE_WEIGHTS`，脚本自己的
   注释都写明"LMM 显示的已回收空间对这张卡片不准确"。这类老卡要么重新交付，要么宿主
   兜底删除。
