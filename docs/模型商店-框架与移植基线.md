# 模型商店：框架与移植基线

> 从 LMM（`D:\LMM-Rust`，Rust + Tauri，约 11.7k 行 core）里提炼出来的业务框架，
> 作为**在 pinvou3 内原生实现模型商店模块**的依据。不再用 sidecar 形式。
> 最后更新 **2026-09-22**（对齐代码现状，修掉 6 处漂移；逐处都带了 `文件:行` 依据）。
>
> **读这份文档的规矩**：它自称「动这个模块的代码之前应该先读它」，所以**每条断言都必须
> 能指到具体文件和行**。发现指不到的（文件/函数不存在、数字跟代码对不上、结论已被推翻），
> **当场修掉并留一条勘误**，不要绕过去——前几轮的漂移全是「当时对、后来没改」攒出来的。

## 0. 这份文档解决什么

LMM 是给 H3C MegaCube / NVIDIA GB10（ARM64 Linux）做的本地模型管理应用。它已经在真机上
跑通了完整链路，也踩了两个多月的坑。现在要把这套能力**原生做进品悟**，只编进 Linux 版。

所以这份文档只回答三件事：

1. 模型商店到底在做什么（业务骨架）
2. 哪些约束是**血换来的**，新实现必须守住（否则会把同样的坑再踩一遍）
3. 移植时哪些搬、哪些扔、怎么分期

## 1. 一句话业务

> 从**模型商店**下载模型卡片 → 按卡片里的**六个 shell 脚本**装引擎、下权重、部署、启用
> → 本机跑起一个 OpenAI 兼容服务 → 品悟直接用它对话。

全程用户不碰 API Key，不碰命令行。

### 数据流

```
   商店服务器                      本机
 ┌──────────────┐          ┌─────────────────────────────┐
 │ card.json    │  HTTPS   │ 卡片库(sqlite)              │
 │ 六个脚本     │ ───────► │  ├ 记录：状态/端点/脚本副本 │
 │ 附属文件     │ 内容寻址 │  └ API Key                  │
 └──────────────┘          │                             │
                           │ 脚本执行器(pty)             │
                           │  ├ 注入 LMM_* 环境变量      │
                           │  ├ 解析进度/提示/标记行     │
                           │  └ 静默超时 / 取消          │
                           │         │                   │
                           │         ▼                   │
                           │ docker 容器 ← 引擎镜像      │
                           │   + 权重目录(几十~上百 GB)  │
                           │         │                   │
                           │         ▼                   │
                           │ http://127.0.0.1:<port>/v1  │
                           └─────────────────────────────┘
```

**关键认知：模型商店本身不懂任何模型。** 它是一个**脚本编排器 + 状态机**。怎么装 vLLM、
怎么起 SGLang、权重放哪，全写在卡片作者交付的脚本里。商店只负责：按顺序跑、把过程如实
显示给用户、把结果记进库、出错时说人话。

这个边界是整个设计的地基——它让"上架一张新卡"不需要改客户端。

## 3. 卡片契约

### 卡片 = card.json + 六个入口脚本（+ 可选附属文件）

```
install_engine.sh    装推理引擎（docker 镜像 / ollama / …）
download_model.sh    下权重
deploy.sh            部署（写配置、探 GPU 直通方式）
enable.sh            启用（起容器，直到服务真的可用）
stop.sh              停用
uninstall.sh         卸载
```

固定文件名、固定语义。**执行器只认这六个名字**，不解析脚本内容。

### 宿主 → 脚本：环境变量

```
LMM_CARD_ID            卡片 id
LMM_MODEL_NAME         模型名（库里的主键之一）
LMM_MODELS_DIR         权重根目录（宿主规定，脚本必须往这儿放）
LMM_STAGING_DIR        下载暂存目录
LMM_SOURCE_REPO_ID     HF 仓库名
LMM_SOURCE_FILENAME    单文件模型的文件名
LMM_MODEL_SIZE_BYTES   标称体积（算进度用）
LMM_ENGINE_NAME        引擎名（lifecycle.rs:760 / :786）
LMM_ENGINE_VERSION     引擎版本（lifecycle.rs:762 / :788）
LMM_DEPLOY_PROFILE     用户选的部署方案 id（lifecycle.rs:1703，只在 deploy 时注入）
LMM_HF_ENDPOINT/_TOKEN 下载源与凭据（**选源是宿主的职责，卡片不该写死**）
LMM_OLLAMA_HOST        ollama 地址
LMM_IMPORT_DIRS        去哪找本机已有的权重/交付包，换行分隔（给**所有**脚本）
LMM_IMPORT_CANDIDATES  扫描结果，换行分隔（只给 download_model）
LMM_PURGE_WEIGHTS      1=删权重 0=保留（卸载时；两个值都显式设，不留空档）
LMM_PROBE_ONLY         1=只探测不安装（引擎探针，lifecycle.rs:1204）
LMM_CANCEL_FILE        取消标记文件路径，脚本应当轮询它（script_runner.rs:1089）
HF_HUB_DISABLE_XET=1   **刻意不带 LMM_ 前缀**：直接喂给 huggingface_hub，这样对
                       厂商自带、我们改不动的下载脚本也生效（lifecycle.rs:840）
```

> **`LMM_ENGINE_IMAGE` 不在这张表里**——它不是宿主注入的，方向是反的，见下一小节。

> **`LMM_WORKER` 这一期不注入**。LMM 会给双机卡注入一个宿主可执行文件路径供脚本
> 控制从机，但从机控制（`core/worker.rs`，941 行）排在三期还没搬。刻意不注入：
> 指向一个不存在的程序，脚本只会拿到一句 "No such file or directory"，那句话不
> 告诉任何人发生了什么。改成给双机卡注入 `LMM_DUAL_UNSUPPORTED`（lifecycle.rs:799
> 起的注释 + :807），脚本会在真正要动从机那一步以它自己的话失败。

### 脚本 → 宿主：标记行（写到 stdout）

```
LMM_PROGRESS_BYTES=已下载/总量      进度条、网速、剩余时间
LMM_PROMPT=<问题>                   向用户要一个输入（暂停等待）
LMM_PROMPT_FORM=<JSON>              向用户要一组字段（比如从机地址+密码）
LMM_CONTAINER_NAME=<名字>           报告容器名 —— **判断"这容器是不是我起的"的唯一依据**
LMM_ENDPOINT_URL=<地址>             报告服务地址
LMM_ENDPOINT_MODEL=<id>             报告服务真正认的模型 id
LMM_ENGINE_IMAGE=<镜像>             install_engine 报告这个引擎实际用的 docker 镜像
LMM_NEED_ROOT=1                     这一步需要提权
```

> **`LMM_CONTAINER_NAME` 为什么重要**：镜像不是身份。别人用同一个镜像起的容器跟我们的
> 长得一模一样，只有容器名能区分。

> **`LMM_ENGINE_IMAGE` 的方向勘误（2026-09-22）**：这份文档原先把它跟
> `LMM_ENGINE_NAME/_VERSION` 并成一行「`LMM_ENGINE_NAME/_VERSION/_IMAGE` 引擎标识」
> 放在**宿主 → 脚本**那张表里，而且标记行清单里没有它。两处都错了：
> **宿主从不注入 `LMM_ENGINE_IMAGE`**（全仓没有一处 `env.insert("LMM_ENGINE_IMAGE"`），
> 它是 `install_engine.sh` 打到 stdout、由宿主 `extract_marker(&install_lines,
> "LMM_ENGINE_IMAGE=")` 读回来的（`lifecycle.rs:1027`，`extract_marker` 定义在
> `lifecycle.rs:2301`）。
>
> **为什么必须由脚本报**：宿主拿得到卡片声明的引擎名和版本，但拿不到镜像 tag——
> 那是脚本自己决定的（有的引擎压根不是 docker 镜像，比如 ollama，见
> `lifecycle.rs:28`）。这一行的唯一消费方是「已安装引擎」的删除功能：有它才能精确
> `docker rmi`，没有就只能不删。取值时**取最后一次出现**（`extract_marker` 循环里
> 一路覆盖），脚本多打几遍不会出问题。

## 4. 状态机

```
  可下载 ──下载──► 已下载 ──部署──► 已部署 ──启用──► 运行中
              ▲         │              │              │
              │         │              └──── 停用 ◄───┘
              │         │
              └─卸载────┴──────────────────────┘
              （权重留在盘上，卡片留在库里）

  已下载 ──删除──► 可下载
         （权重真删，记录移除）
```

库记录里两个字段表达它：`status ∈ {downloaded, deployed}` + `running: bool`。

**卸载和删除是两个动作，区别不只是权重删不删，更是卡片留不留在库里**：

| 动作 | 权重 | 库记录 | 结果 |
|---|---|---|---|
| **卸载** | 留在盘上 | **留着**，退回「已下载」 | 下次点「部署」直接用，不必重下 |
| **删除** | 真删 | 移除 | 腾出磁盘，要用得重新下载 |

两件事必须同进同退：权重留着而记录没了 → 几十 GB 没有任何界面管得到；记录留着而权重
没了 → 库里多一条指向空气的死数据。

## 5. 必须守住的不变量（都是血换来的）

### 5.1 执行器层

| # | 不变量 | 不守会怎样 |
|---|---|---|
| 1 | **取消等于失败**。取消必须返回错误，绝不标记成功 | v1.0.6 的大 bug：用户取消了下载，界面显示"已完成" |
| 2 | **pty 必须关 ECHO**（`TCSANOW`） | 用户输入的答案会原样回显进日志，密码也一样 |
| 3 | **静默超时要分档**，不能一刀切 | 卸载是几百 GB 的 `rm -rf` 且全程不出声，5 分钟那档会把它误杀，杀完磁盘半删、记录完好，之后每次重试都失败 |
| 4 | 工作线程必须有 **panic 兜底**（Drop 守卫 + `catch_unwind`） | job 一 panic：卡片在并发表里永久锁死、日志长轮询永不返回、清理任务也清不掉它 |
| 5 | **剥离终端控制序列**再进日志 | 进度条转义字符糊满整个日志面板 |

超时分档（实测值）：

```
默认（download_model / stop）      300 秒无输出
install_engine / deploy / enable / uninstall   1800 秒无输出
引擎探针                            20 秒
```

### 5.2 生命周期层

| # | 不变量 | 不守会怎样 |
|---|---|---|
| 6 | **脚本退出 0 ≠ 事情做完了**。结论必须来自磁盘的实际样子 | 2026-09-18 真机：`ornith15-bf16` 的卡片脚本根本不删权重（spec 1.0 老卡），退出 0，记录被删 → **67GB 孤儿**，界面再也管不到 |
| 7 | **释放量必须是实测差值**，不能用 card.json 的标称体积 | 界面报"已释放 67GB"而磁盘一个字节没少 |
| 8 | **并发约束必须全局唯一**。同一张卡不能被两处同时操作 | 真机：两个 `hf download` 抢同一批文件的锁，速度从 2.2MB/s 掉到 569KB/s |
| 9 | **容器以 root 写进挂载目录的文件，普通用户删不掉** | 2026-09-18：735 个 root 属主的 JIT 缓存让 `rm -rf` 失败 → 整个卸载非零退出，而此前容器和 22GB 权重已经删了。可重建的缓存**不该**让卸载失败 |
| 10 | **卸载默认真删权重是宿主的行为**，跟规范里写给卡片作者的"默认保留"不是一回事 | 两边搞混会删掉不该删的 |

### 5.3 接入与网关层

| # | 不变量 | 不守会怎样 |
|---|---|---|
| 11 | **模型名必须一字不差**。转发时要把请求里的 `model` 换成库里的 `endpoint_model` | 差一个字符上游就 404 |
| 12 | 判断"这个模型能不能接进对话"看 **`endpoint_url`，不是引擎名** | 引擎名是开放集合；文生图/视频卡（`/generate`、ComfyUI 根）不是对话模型，往 `/v1/chat/completions` 发会拿到 422，而界面只会说一句笼统的"服务不可用" |
| 13 | 模型卸载后，品悟模型列表里指向它的行**必须一起清掉** | 网关此后对那个 model_name 一律 404，而 404 在多数客户端眼里是"地址写错了"不是"模型没了"。那行死数据很可能正是当前默认模型 |
| 14 | 回环地址也要带鉴权（`credential_action: replace`） | 品悟认为"本地模型不需要 Key"，漏了会以 `credential_state: missing` 存下 → 网关 401 → 被误判成 generic 错误 |

### 5.4 工程层

| # | 不变量 | 不守会怎样 |
|---|---|---|
| 15 | 错误分类用**词边界**匹配，不要在整段原文里做子串匹配 | `ConnectTimeout=10` 里的 `timeout` 命中，把真正的原因（ssh 返回 255 = 连不到从机）换成"操作超时，请稍后重试"。**把人引向错误方向，比不给提示更糟** |
| 16 | 进度事件必须真的有人监听 | 旧版发的 `update-progress` 事件前端根本没订阅，所以下载时从来没有进度条 |
| 17 | 符号链接不能打在容器挂载目录**内部**（要打在挂载点本身） | 容器里那个链接是悬空的 |
| 18 | 内置卡片的脚本随应用升级，**刷新逻辑要放在所有启动路径上** | sidecar 模式下 `refresh_builtin_cards()` 从不执行，改了脚本推上去一点效果没有，白查一轮 |

## 6. 原生化后的形态

### 6.1 模块布局（已落地）

原先这里画的是一份「建议」：所有文件平铺在 `features/model_store/` 下。**实际落地时
多了一层 `platform/`**，因为架构守卫只放行 `/platform/` 下的 `#[cfg(target_os)]`（见
§6.2 第 1 条）。以现状为准：

```
pinvou3-app/src-tauri/src/features/model_store/
  mod.rs              对外门面（re-export platform::backend 的同名函数）
  platform/
    mod.rs            linux / unsupported 二选一，cfg 全收在这里
    unsupported.rs    非 Linux 的桩，一律回「本平台不支持」
    linux/
      mod.rs
      config.rs         设置、数据目录、HF token（密钥环 + 文件回退）
      db.rs             sqlite 卡片库
      disk.rs           空间检查、字节格式化
      store_client.rs   商店 API 客户端（含测试商店脚本落地）
      script_runner.rs  pty 执行器（协议、超时、取消）
      proc_timeout.rs   外部命令的超时封装
      lifecycle.rs      六个脚本的编排（原 model_manager 主体）
      import_scan.rs    「去哪找本机已有的权重」，见 §6.5
      run_state.rs      任务注册表与日志环形缓冲
```

### 6.2 Linux-only 门控

pinvou3 已有成例：**`features/shared_knowledge_host/platform/`**（`mod.rs` + `linux.rs`
+ `unsupported.rs`）。真实实现只在 Linux 编译，其他平台给一个返回 `available: false`
的同名同签名空壳。**这套门控照搬即可**，改个名字——模型商店就是照它搬的，
`features/model_store/platform/mod.rs` 的注释里写明了这一点。

> **勘误（2026-09-22）**：这里原先写的是「成例是 `features/lmm/platform/{linux,
> unsupported}.rs`，前端由 `lmmInstalled` 门控」。**这两个东西在本仓库和 `origin/main`
> 里都不存在**（`git ls-tree -r origin/main | grep features/lmm` 零命中，`lmmInstalled`
> 全仓唯一一次出现就是这份文档自己）。照着它去找会白找一轮。

三件必须一起做的事：

1. **cfg 只能写在 `/platform/` 下**。这是仓库的硬约定，`scripts/architecture-guard.py`
   的 `target_cfg_allowed()`（第 253 行）只放行这个目录下的平台条件编译。
2. **两个平台分支都要 `pub mod`**，不能一边 pub 一边私有。因为下面紧跟着的是模块级
   re-export（`pub(crate) use unsupported as backend`），rustc 对非 pub 模块的模块级
   re-export 无条件报 E0365——写成私有 `mod unsupported;` 时 Linux 上编不到这一支，
   一直不露头，Windows/macOS 一编就是 E0365 加 20 处级联 E0603（见
   `features/model_store/platform/mod.rs` 的注释）。
3. **不要做成「编译期就没有这些命令」**。那样前端 `invoke` 拿到的是底层的
   "command not found"，界面只能显示一句莫名其妙的话；桩函数回一句「这个功能只在
   Linux 设备上有」才是用户能看懂的解释。

前端侧栏入口的门是 `modelStoreAvailable`（`src/app/main.jsx:1271`），值来自
`invoke('model_store_availability')` 的 `available` 字段；`main.jsx:3943` / `:4708`
（侧栏与导航列表）和 `:3445`（移动端「更多」）三处共用它。

> 那次 `.catch(() => {})` 的教训写在 `main.jsx:1265` 上方：2026-09-18 从 sidecar 改
> 原生时命令名由 `lmm_status` 换成 `model_store_availability`，这一处漏改，调用抛
> 「命令不存在」被静默吞掉，入口永远不渲染，界面上毫无异常。**可用性探测的 catch
> 里必须留痕。**

依赖也要跟着门控（`Cargo.toml` 的 `[target.'cfg(target_os = "linux")'.dependencies]`），
否则 Windows 构建会去编 rusqlite / nix 之类的东西。

## 6.5 从本地目录 / U 盘导入

**框架已落地（2026-09-20），正式商店在架卡片自 2026-09-21 起全部消费**——见本节末
「当前状态」。

**这条原定是一期之后的重点**（2026-09-18 定的）。

下载是整条链路上最贵的一步：权重动辄几十到上百 GB，引擎镜像几十 GB（SGLang 那个
49GB），而目标环境的出口带宽实测只有 233 KB/s。所以要给用户第二条路：**东西已经在
本机别的目录、或者在 U 盘上时，直接拿来用，不要再下一遍。**

已有的先例可以照抄：MiniMax-H3 那张卡的 `install_engine.sh::find_delivery()` 就是这么
做的——自动扫 `$LMM_STAGING_DIR` / `~/Downloads` / `~/桌面` / `$HOME` / U 盘挂载点
（每个目录套 `timeout 5`，总时长封顶 20 秒），取到后按厂商自己的 `SOURCE_LOCKS.json`
校验 sha256。

> **勘误（2026-09-22）**：原文这里写的是「找不到才 `LMM_PROMPT` 问一次路径」。
> **那条路已经被删掉了，不要再照抄。** 脚本里原来确实是 `LMM_PROMPT=text|…` + `read`，
> 2026-09-17 真机上把整个任务挂死了 3 小时 13 分：输入框没渲染出来，脚本一直阻塞在
> `read` 上，而 `max_concurrent_downloads=1`，这一个卡住把后面排队的下载全堵死。现在
> 找不到就**直接失败并说清楚「缺什么、放哪、然后重点一次下载」**（理由写在
> `data/test-store/minimax-h3-int8-single/install_engine.sh:199-213`）。
> **通用能力也别再引入「让用户手打文件系统路径」这种交互**。

要做成通用能力的话，几个必须想清楚的点：

1. **扫哪儿**：常见下载目录 + 已挂载的可移动设备（`/media/<user>/*`、`/mnt/*`、
   `/run/media/<user>/*`）。不要全盘扫——几 TB 的盘上 `find` 一遍的代价用户不会接受。
2. **怎么认**：靠**内容**而不是文件名。权重按 `weights.sha256` 清单逐个核对，镜像按
   `RepoDigests` + 平台核对（不能用 image `.Id`，containerd image store 下它返回的是
   清单摘要不是配置摘要——这个坑 Qwen3.8-Flash-Next 那张卡踩过）。
3. **认错了比没认出来更糟**：校验不过就当没找到，老老实实去下载，绝不"差不多就用"。
4. **U 盘随时会被拔**：导入过程中设备消失要能说清楚发生了什么，而不是报一句 I/O error。

### 当前状态（框架 2026-09-20 落地，卡片侧 2026-09-21 接上）

分工定了，而且跟上面第 2 条「怎么认」的结论一致：**宿主回答「去哪找」，卡片脚本
回答「这份对不对」。**
