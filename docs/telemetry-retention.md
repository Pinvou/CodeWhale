# 实时 D1 / D7 / D30 留存

留存按安装实例去重，以首次成功完成用户任务的北京时间日期为第 0 天；只包含用户发起的 assistant、code、team 任务。页面打开、仅提交、失败、系统任务和计划任务均不能激活或形成留存。首次具备采集资格的 `analytics_cohort_started` 继续用于激活漏斗，不再作为留存起点。

第 N 个自然日当天即进入 D<N> 分母；当天成功完成任务也可立即进入分子。看板标注“实时更新”和“今日观察”数量，观察日结束前数值仍可变化。已经在第 N 天达成的留存不要求今天继续活跃。观察日未到的安装不进入分母，成功发生在相邻日期也不能替代精确第 N 天。今日 / 7 日 / 30 日切换不改变此口径。样本少于 30 时隐藏百分比，继续显示分子、分母。

此口径使用 `behavior-v1.5`。API 的 `metric_version_started_at` 来自本数据目录首次成功启用并保存本版口径的时间，页面按北京时间显示“本实例切换时间”，最后事件和报表更新时间也明确标注并使用北京时间；重启不刷新。旧留存文件缺少该字段时，在本版首次成功持久化时补记，不挪用用于历史完整性判断的 `initialized_at`。无持久依据的计算返回 `null`，页面显示“未记录”，不能用生成报表的时间或固定日期代替。它不是全网发布日期；本次修订尚未部署，实际部署记录另由发布流程填写。

## 持久依据和删除

服务在数据目录的 `retention-facts.json` 保存文件格式版本、初始化时间、本版口径启用时间，以及每个安装的首次成功日、从首次成功日到第 30 天之间的成功日期集合和历史完整性标志；`retention-facts.initialized` 标记它已成为持久依据；首次写入先原子替换事实文件，再原子替换标记，避免标记直写留下半个文件，但不承诺断电级 fsync 持久性。已有损坏标记仍拒绝启动，不能自动覆盖；备份与恢复须保全这两个文件。每个安装最多保留 31 个日期，不保存对话、任务正文、模型、工具或原始事件内容。日期集合支持幂等重复和乱序上报；更早的成功到达时重算起点与各观察日。已初始化后依据文件缺失会拒绝启动，避免按截断的原始事件静默重建。

持久日期必须是安全整数，且在 JavaScript 可表示的北京日期范围内（`1..100000000`）；加载时不再以当前时钟裁定已保存日期是否有效，避免时钟回拨或离线恢复误拒。新观察事件仍须满足发生时间不晚于当前统计时刻。

这些最小留存依据与原始事件的 35 天/容量清理独立，保留至对应安装的统计数据被删除。清理原始事件之前必须先成功保存留存依据；存储失败会阻止清理，查询返回不可用，不伪装成 0。已落盘的事件在留存依据写入失败时返回可重试，重试可幂等确认。初次启动也先从清理前的事件建立依据。文件损坏或未知版本拒绝启动，必须修复或恢复有效备份，不能删除文件后声称历史完整。

显式删除先持久化既有删除 tombstone，再清除留存依据和原始数据。启动和回算均排除已删除的安装；恢复旧留存文件不能复活已删除主体。未注册主体和非安装实例不进入回算。

## 历史迁移与核对

首次部署时，旧安装的原始事件可能已经截断。因此自动迁移和备份回算都将它们标为“历史可能不完整”，而不会把残存的第一条成功宣称为真正首次成功。新部署后新注册、且未出现注册前成功事件的安装从完整采集开始。历史不完整时，已知样本仍展示，但不声称可还原全部历史。

注册前成功事件也可能来自客户端时钟偏差；现有最小依据不能证明它是偏差还是实际历史缺口，因此仍保守标记历史可能不完整。后续正常事件或再次回算不会自动将该标记恢复为完整，不能通过删除依据文件或修改标志消除提示。

存量安装未被依法删除前，“历史可能不完整”可能持续存在，这是保守迁移的预期稳态，不是等待 35 天就会自动修复的事故。`history_unresolved_installations` 也包括尚无已知成功、无法证明历史完整的存量安装，不等同于本次分母内的 `history_incomplete_installations`。排障应比较这两个数量及回算输入，不能以消除徽章为目标删除安装或依据。

使用新代码目录中的脚本流式扫描现存文件及备份，默认只复算、不改写文件内容，也不把备份事件恢复进在线原始事件日志：

远控留存复用在线主体归属投影：发起端提交与执行端成功可跨扫描批次、跨备份文件关联，文件顺序不影响结果；只有可归属的发起端形成成功留存，单独执行端、已删除主体及非安装身份不能补出留存。扫描前先应用身份、墓碑和时间过滤，再关联远控事实。工具仅在内存中为每个远控任务保留至多四条关联证据（首次提交、首个权威终态、选定回执及首次有效模式），内存随不同任务数增长；不把整份备份或投影事件写回在线原始日志。

远控成功留存按发起端 A 的提交日期归属，仍必须具有明确成功终态，只有提交不能形成成功留存。回执的到达或发生日期不改变这个归属；跨日完成/接收的同一任务不会再形成次日成功活动。内部投影单独保存这个稳定时间供线上及离线留存消费，不把执行端 B 的墙钟作为 A 的 cohort 日期，原执行和回执诊断时间保持不变。这是远控成功任务的发起日归属，不是对端完成时刻的估计。缺少发起端时间证据的投影不形成留存。修复前若已持久化迟到回执造成的额外日期，最小依据没有任务级来源，不能自动删除可能属于其他真实成功的日期；应保全并核对配套备份，禁止清空事实库重建或伪造完整历史。此修复也不将既有 `history_complete=false` 自动提升为完整。

```sh
node remote-control-relay/scripts/backfill-retention.mjs \
  --data-dir /path/to/telemetry \
  --source /path/to/backup/behavior-events.jsonl
```

只读复算是指不替换文件内容；加载已有留存事实/标记时仍执行私有权限收紧（chmod 0600），可能修改元数据，在不允许 chmod 的只读挂载上会因 EROFS 等错误拒绝运行。CLI 失败只给出闭集类别/错误码，不回显原始数据或具体路径；排障须离线逐项核对输入，不能把错误当作空数据。

已有删除 tombstone 时，运行环境必须具有与服务一致的 `PINVOU_TELEMETRY_DEVICE_PEPPER`，用于匹配已删除主体；不要将其作为命令行参数或打印。脚本只输出汇总数量，不输出安装身份。相同快照或事件重复输入不会重复增加留存分子、分母；`scanned_events` 表示实际读取的可解析 JSON 行数，重复快照仍会增加该扫描量。复算同时报告新口径结果和 `legacy_cohort_start` 对照，二者不能作为旧线上报表的逐值重演：起点、事件范围与校验规则均可能不同。对照项仅使用本次扫描源内的 cohort 起始和核心用户成功任务，仍执行当前的安装资格、身份一致性、非未来时间戳及北京日期 `day >= 1` 校验；`after` 还合并已有持久依据，旧线上口径则受当时日志窗口和规则影响。对照用于解释差异，不保证还原过去发布的数字，不能把预先找到的样本数作为验收目标。

`before` 是按当前设备清单清理之前的持久依据指标，`after` 是本次回算结果；二者的历史完整性计数基准不同：`before.d1/d7/d30` 内的 `history_unresolved_installations` 仅统计原文件已存的历史不完整行，`after` 还纳入当前清单中无成功行、无法证明历史完整的旧安装。因此即使日志为空，`complete/0 → partial/1` 也可能仅来自清单协调，不代表回算损坏了历史。`rows_dropped` 显示因设备不在有效清单中、非安装身份或删除墓碑而移除的原有行数。灾难恢复时应先核对设备清单与留存依据是否配套，不能只比较留存率。`malformed_lines` 计非法 JSON，`invalid_events` 计可解析但不是事件对象的行，`invalid_timestamp_events` 计无效时间或小于第 1 个北京时间日期的行；这些行不形成留存依据。默认原始事件文件缺失按空日志处理，显式指定的备份源缺失仍报错，避免把路径错误当成成功回算。

`excluded_events` 分别报告 `ineligible_identity`（非当前合格安装，包含已删除主体）、`future_timestamp`（时间尚未到达）、`identity_mismatch`（两个身份字段不一致）；三个原因按该顺序互斥计数，发生在时间有效性校验之后，不能把排除量重复相加到 `scanned_events`。`--help` 可与其他参数一起使用；以 `--` 开头的相对路径使用 `--data-dir=DIR` 或 `--source=JSONL` 的等号形式传递，带空格的完整参数仍需 shell 引号。

先备份当前代码和数据，核对只读结果，再停止服务，在停止期间重新复算并应用：

```sh
node remote-control-relay/scripts/backfill-retention.mjs \
  --data-dir /path/to/telemetry \
  --source /path/to/backup/behavior-events.jsonl --apply --offline
```

`--offline` 是操作方对服务已停止、无其他写者的确认，脚本不代替进程管理。在线服务也没有跨进程单写者锁，须由进程管理保证一个数据目录只有一个写者。应用后重新启动，核对认证 API 与页面的分子、分母、实时及历史标识；重启和原始事件清理不得让已保存的留存消失。回滚须同时恢复匹配的代码与数据备份，并保全期间新增事件和删除 tombstone，不能用旧备份撤销用户删除。

缺少 `devices.json` 且目录内已有留存、事件或删除记录等依赖材料时，新版拒绝启动；在线启动和离线回算都要求有效库存，不能把读取失败或结构错误当作空清单。旧版可能从未登记设备却已创建空留存/原始日志、尚未保存设备清单，这种目录升级后同样可能拒启，因此不保证所有旧空目录都能无干预升级。

恢复时优先找回与现有事实配套的有效设备清单，保留当前删除墓碑。只有全部写者已停止、目录已完整备份，且操作方根据可靠的原登记记录及备份核实从未登记过设备、留存行与各事件文件确为空、删除墓碑也不存在或为空时，才可按服务正式保存的空清单格式 `{"version":2,"devices":[]}` 恢复缺失文件，并保持普通私有文件权限。该格式中的 `version:2` 与服务保存格式一致；不能仅凭文件缺失、当前在线数为零、窗口到期或某个空日志推断库存为空。有删除墓碑或不能证明为空时继续保全数据并查找配套库存，不得猜测生成空清单或删除留存依据/标记来绕过拒启；合法的空清单会使不在库存中的留存行被清理。合法但不配套的空/子集库存仍沿用这一清理契约；在线协调和离线回算会在移除无对应删除墓碑的孤立行之前向 stderr 输出 `retention_inventory_omission` 结构化告警，仅包含行数，不含安装身份、摘要或凭据。出现告警时核对配套备份，不能把它当作历史真实完整的证明；有已知删除墓碑的正常删除不告警。

写入或原子替换失败时会尝试清理本次临时文件；进程被强制终止时仍可能留下 `.tmp` 文件。它们不作为有效依据加载；只有在服务及回算工具均停止、核对权威文件有效后，才可清理确认无写者使用的孤儿临时文件。

留存依据/标记的读取、在线库存的私有文件检查以及遥测原子写目标拒绝符号链接或非普通文件；共用原子写原语的既有遥测文件也不再静默替换链接。遇到这一检查失败时，停止全部写者，核对链接真实目标和当前删除墓碑，备份并将确认有效的内容恢复为配置数据目录内的普通私有文件，再按上述配套恢复流程启动。不得通过删除依据、跳过安全检查或直接覆盖链接目标“修复”。离线回算对 `devices.json`、墓碑及原始日志/备份源的只读入口没有同等的链接拒绝策略，操作方须核实来源和真实目标；这不放宽留存依据或写入目标的检查。CLI 经代码目录 symlink/junction 启动也受支持。
