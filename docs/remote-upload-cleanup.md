# 远控上传批次的清理确认

附件上传在导航中断后保留进程内未知批次围栏。放弃本地
`prepared_not_sent` 任务只证明该任务没有提交，不能证明 B 的上传暂存已删除。
旧 `attachment_abort` 的 `aborted` 和 A 归一化的 `already_absent` 仅表示逻辑撤销，
也不能作为未知批次解除围栏的依据。

## 足够的证据

只有原上传函数已经退出、每个实际发出的 begin/chunk 均收到确定成功回执，才可
尝试恢复。chunk 中包含最终发布；函数尚在运行、未知 begin 句柄、丢失 ACK、无效
回执或仍可能迟到成功的调用，一律不解除围栏。

用户显式放弃原待发送任务时，A 对原批次的每个已知句柄发送
`attachment_abort_confirmed`，仍属于现有 `attachment_v1` 加密 RPC：

- 请求 body 恰为 `task_id`、`transfer_id`；身份来自当前已认证连接和 B 的会话映射。
- 成功 body 恰为 `transfer_id`、`cleanup_confirmed: true`。
- B 在上传状态锁内核对完整连接/租约/代次、会话、任务和句柄；拒绝已消费或已被任务
  接纳的上传，然后撤销传输并删除暂存。仍有外部读取所有者、删除失败或未知句柄
  均返回错误，不产生成功证据。失败清理保留原有有界 pending-cleanup 所有权。
- A 只接受与当前待收回执绑定一致的已认证成功响应；错误 `transfer_unknown` 不被
  归一化为清理成功，旧响应不能重新证明附件可提交。
- 同一批次内保存已确认句柄的结果，可在本地 abandon 失败或其他句柄清理失败后继续
  人工处理；不重新上传，不提交任务，不把超时变成成功。

全部句柄清理确认后，还必须收到 Rust 对该原任务的 never-attempted abandon 成功。
最后仅删除同一 owner、连接/租约、会话、任务和内存批次对象的记录。导航或租约变更
中的旧回调不能删除后来创建的批次。只存在本地准备工作、从未发出 RPC 的已退出
批次不需要 B 的空操作证明，但仍需要本地 abandon 成功。

## 兼容与失败

不改变现有能力列表、握手和旧操作的请求/回包。旧 A 不发出新增操作；新 B 仍按旧
合同处理旧请求。Relay 继续只转发现有 `remote_action_request/result` 的密文。
旧 B 在解密后会拒绝新增操作，丢弃该帧并继续处理后续合法帧；A 按现有 15 秒超时
保留围栏，随后仍可放弃本地未发送任务。离线、旧端、删除失败或证据不足不阻止
本地 abandon，但不会解围栏；仍须核对 B 后断开并建立新连接。

已经上传完成、尚未提交的已知批次使用独立三语提示，允许继续原任务或先放弃它。
本确认是用户放弃前的安全清理改进，不是未知上传的自动重试或已提交任务的取消。
