# Team Relay 多设备人工验收

> 当前状态：自动化层已完成；执行本清单前，需要先有一个可被所有测试设备访问的 HTTPS Hub。本文不包含生产部署授权。

## 1. 验收前提

- 一套隔离的 Team Relay Hub、PostgreSQL 和附件目录；
- 一个所有设备可访问的 HTTPS 基础地址，例如 `https://demo.example.com/pinvou3/team-relay`；
- 三台 Pinvou 桌面设备，分别作为 A、B、C；
- 一组无敏感信息的小测试文件：`.md`、`.xlsx`、`.png` 各一个；
- 可以查看 Hub 服务健康、应用日志和数据库只读结果，但日志中不得打印邀请码、团队加入码、device token 或文件内容。

完整接力需要 A、B、C 三个成员。只有两台设备时，可以先验证“加入、邀请、A 派给 B、B 最终交付、A 接收”的短链路；Handoff 与回传仍需第三个成员身份。

## 2. 建立团队

1. 确认隔离 Hub 已设置 `TEAM_RELAY_ALLOW_SELF_SERVICE_ENROLLMENT=true`。
2. A 打开“团队接力”，确认登录页只填写邮箱和名字；界面不显示团队名、加入码、服务 URL 或设备名。
3. A 登录后应看到“加入团队 / 新建团队”，创建 `Team Relay Demo` 后页面显示真实团队名和空工作箱；重启 A 后无需再次登录。
4. A 点击“团队加入码”，确认重复打开时仍显示同一个 8 位加入码，并把加入码通过合适渠道发给 B、C。
5. B、C 先用不同邮箱和允许相同的名字登录，再在团队页面使用同一个团队加入码加入；分别验证小写输入以及省略横线也能成功，并确认重名选择项使用脱敏邮箱提示区分。
6. 任一成员打开“账户与名字”修改名字，确认所有已加入团队同步显示新名字，完整邮箱不出现在成员列表和工作记录中。
7. A、B、C 刷新后都应看到三个成员；B、C 默认也可查看当前加入码。A 切换“对成员隐藏”后只有 A 能看到，再切回后恢复。
8. A 刷新加入码后，旧码必须失败、新码可供多个新成员重复使用，B、C 的已有连接不受影响；A 暂停加入后当前码立即失效，再启用会生成新码。
9. A 移除一个无未结束工作的成员后，确认移除前的加入码自动失效，当前成员仍可查看新码。
10. 使用同一客户端连续提交 5 次错误加入码，第 6 次应返回 `429 rate_limited` 和 `Retry-After`；等待限流窗口或重启演示 Hub 后再继续验收。

## 3. 固定接力旅程

依次执行且每一步都在三端观察当前行动人、负责人和接力路径：

1. A 派活给 B，并明确选择一个 `.md` 文件；A 端应显示“等待 B 接受”，接力棒和责任仍在 A。
2. B 在“需要我处理”中看到“待确认”任务和应用角标，但此时只能看到任务摘要，材料栏不得泄露 `.md` 的元数据或内容；仅打开详情会清除未读数字，不会清除“待确认”行动提醒。
3. B 点击“拒绝任务”并填写原因；B 的任务列表不再保留该邀请，A 收到提醒并看到“待重新派发”。A 改派给 C 后，B 不再收到该线程后续更新，C 看到新的待确认邀请。
4. C 拒绝后，A 再改派给 B；B 点击“接受任务”，此时 `owner/current_actor` 才变为 B，材料栏才出现 `.md`。B 点击“准备全部材料”，所有共享文件应进入本机私有任务目录，界面显示已准备状态并可本机打开；HTML/HTM 使用 Pinvou 的 HTML 产出物窗口，其他文件使用系统应用，“打开所在位置”定位到准确文件。
5. B 点击“更新进展”，填写当前进展、可选下一步并选择一个新的本地文件；取消时文件不得上传，确认后应显示上传进度并新增一条“进展更新”历史。确认该动作持久化为 `note + delivery.subtype=progress`；升级前没有 subtype 的旧 `note`、A 在 B 处理期间追加的通用备注，以及待验收阶段的通用备注仍显示“补充说明”，不得重标为进展。三端看到 revision 和历史同步更新，但当前行动人、负责人、回传目标和线程状态都保持不变，B 仍可继续处理；A、C 此时不显示“更新进展”入口。
6. B 点击“使用我的 Agent”，选择普通对话或 Pinvou 代码模式；代码模式默认直接使用 Pinvou 原生代码会话，并可主动切换其他已接入 ACP。首次应默认勾选全部材料，将所选文件作为实际附件挂入新建的私人 Session，并预填关键任务信息；再次点击应默认复用同一 Session，显示当前代码 Agent、代码目录、已带入材料和 Git 信息，只默认勾选新增材料。勾选“使用新会话”后应解锁工作方式、代码 Agent 和工作区选择，默认重新带入全部材料；确认后原会话保留，该工作改为关联新会话。预填内容只进入输入框，不自动发送；不得自动 clone、checkout、pull、commit 或 push。
7. B 点击“邀请协作”选择 C，并附带一个新的 `.xlsx` 文件；提交后 B 端显示“等待 C 接受”，B 仍可“更新进展”“更换接收人”或“撤回邀请”，但不能最终交付或再次邀请其他协作者。
8. B 先撤回一次邀请，确认 C 的邀请消失、B 恢复正常处理；随后再次邀请 C。C 在“需要我处理”中看到“待确认”，接受前不能读取 `.xlsx`；C 点击“接受接力”后才成为 `current_actor`，线程负责人仍是 B，并获得完整材料权限。
9. C 点击“交回上一处理人”，任务应直接回到 B，而不是回到最初派发人 A；C 不得继续转派，也不得直接最终交付。
10. B 最终交付给 A，并附带一个新的 `.png` 文件；A 在“需要我处理”中看到置顶排列的“待验收”工作，先点击“要求补充”。
11. B 补充后再次最终交付，A 点击“接收并结束”。
12. 三端重启，线程仍在“已结束”，动作顺序、接力路径和附件名称一致。

另用一个未更新的 `0.1` 客户端连接同一升级后 Hub，确认它省略 `X-Pinvou-Team-Relay-Protocol` 时仍保持旧版“派活/转交立即生效”；升级后的 `0.2` 客户端在旧 Hub 上应显示明确的“直接生效”文案，不得误导为等待确认。

在升级后的 Hub 上，再让一个仅使用 `0.1` 客户端的成员保持在线。`0.2` 发送方选择该成员时，表单应在发送前提示“对方当前版本不支持确认，将直接生效”；响应中的 `transfer_mode` 应为 `direct_legacy`，对方无需确认即可处理。该成员用 `0.2` 客户端完成一次 bootstrap 后，成员能力应自动刷新，后续派发、协作邀请和改派应返回 `confirmed`。把该设备最后能力登记时间改为 30 天以前后，应再次安全降级为 `direct_legacy`。

## 4. 工作列表管理

1. B 在任意线程的“更多”菜单中置顶；B 当前视图内该工作应置顶显示，A、C 的顺序不受影响。B 重启后置顶仍保留。
2. 已结束线程可由 B 归档并进入“已归档”，随后可恢复；未结束线程不显示归档入口，直接调用也应被 Hub 拒绝。
3. A 新建一项工作后，从“更多”选择“取消工作”，填写原因并二次确认；B 应看到 `cancel` 记录和已取消状态，双方都不能再追加动作。
4. B 不能取消 A 发起的工作；已接收结束的工作也不能取消。界面不得提供物理删除入口。

## 5. 可靠性与权限

- B 退出应用时由 A 派一项新工作；B 再启动后应通过 bootstrap 看见它；
- 提交动作后立即断网，恢复网络并刷新，不得生成重复动作；
- 两端基于同一 revision 操作时，失败端应显示冲突并刷新权威线程；
- 断开 SSE 后恢复，页面应重新 bootstrap；
- 把 B 窗口置于后台并由 A 派活；若系统通知总开关已开启，B 应立即收到不含工作正文或文件内容的通用提醒。接受、拒绝、撤回和改派后，只有受影响成员收到行动提醒，其他团队成员只刷新共享状态；
- 未明确选择的本地文件、Pinvou Session、Agent 对话和工作区不得出现在 Hub；
- 本机任务目录路径、任务与 Agent Session 的关联记录不得出现在 Hub；Agent 完成后也不得自动回传或交付；
- 超过 20 MiB、被禁止的扩展名和越权附件下载必须失败；
- Web 宿主只显示 unsupported，不发起 Team Relay 请求。

## 6. 通过证据

验收记录至少包含：

- Hub 健康检查与协议版本；
- A、B、C 每一步的页面截图或录屏；
- 线程 ID、最终 revision 和动作种类序列，不记录消息原文或 token；
- 三端重启后的同一线程状态；
- 重复提交、revision 冲突、SSE 重连和附件限制结果；
- Remote Relay、OTA 健康入口及 Pinvou 其他核心页面的回归结果。

任一设备状态不一致、出现假成功、重复动作、敏感信息进入日志或未选择文件被上传，都视为未通过，先停止演示部署并回到对应层修复。
