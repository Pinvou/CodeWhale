# 用户行为埋点实施任务与状态

> 需求基线：`docs/用户行为埋点需求文档.md` v1.2
>
> 状态基线：`feat/behavior-analytics-platform` 同步 `origin/main@76c1f8d97` 后的代码
>
> 更新规则：每个任务独立提交；实现、契约测试和状态更新必须位于同一提交。

## 1. 状态定义

| 状态 | 判定标准 |
|---|---|
| 完全实现 | 需求中的触发时机、字段、关联关系、异常终态、隐私约束和自动化测试均已覆盖 |
| 部分实现 | 已有可复用代码或部分事件，但缺少关键路径、字段、终态或测试 |
| 未实现 | 没有对应生产代码，或现有占位/模拟代码不能形成可用闭环 |
| 暂缓 | 本轮明确不进入实现范围，不得以模拟数据或占位事件冒充完成 |

## 3. 实施顺序与依赖

1. 先完成 BA-01～BA-03，建立所有事件共享的契约、授权和可靠投递底座。
2. 完成 BA-09，使服务端先兼容新协议，再上线 BA-04～BA-08 的 P0 生产事件。
3. 完成 BA-10 并用固定数据验收 P0 指标，达到阶段 A 完成标准。
4. 按 BA-11～BA-16 的独立功能边界接入 P1 事件，再完成 BA-17。
5. BA-18 随各阶段持续补齐，最终集中执行安全、隐私、恢复和性能验收。
6. BA-19、BA-20 保持暂缓；本轮不得产生商业或实验事件，也不得展示模拟指标。

## 4. 独立提交约束

- 每个 BA 任务使用一个独立提交；确有跨任务公共修改时归入最先依赖的底座任务，后续任务只消费稳定接口。
- 每个提交必须同步更新本表中的“当前状态”和代码审计依据，并包含该任务直接相关的自动化测试。
- 任务只有在生产路径、异常路径、隐私约束和测试全部满足时才能标记“完全实现”；测试通过不能替代触发点审计。
- P2 暂缓项不因移除模拟数据而标记“完全实现”。
