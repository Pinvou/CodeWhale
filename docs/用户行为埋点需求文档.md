# Pinvou Agent 用户行为埋点需求文档

> 文档状态：待产品、研发、数据与法务评审
>
> 文档版本：1.0
>
> 更新日期：2026-08-27
>
> 适用范围：Pinvou Agent 桌面端、Web 宿主、遥测服务、运营看板及账号/订单服务
>
> 相关资料：[设备运营统计初版](./设备运营统计-初版.md)、[GitHub PR #642](https://github.com/Pinvou/pinvou3/pull/642)

## 1. 背景

当前行为埋点已经覆盖任务开始/结束、语音开始、工具安装完成、场景触发和模型使用等基础事件，但还不足以回答以下产品问题：

- 新用户是否完成了首次有效任务，在哪一步流失？
- 用户提交的任务是否真正成功，耗时和失败原因是什么？
- 语音、场景、工具、知识库、代码模式等能力是否被发现并形成稳定使用？
- 工具从曝光、安装、配置到实际调用的完整转化如何？
- 模型使用量来自用户主动选择、系统默认还是故障回退？
- 技术上的“任务完成”是否给用户带来了可感知价值？
- 版本发布后，核心成功率、留存和错误率是否发生异常变化？
- 商业转化是否真实发生，而非由前端模拟数据推导？

本需求在不采集会话正文和私人数据的前提下，建立统一、可追溯、可验收的行为分析体系。本文是产品与数据口径文档，不代表其中所有事件已经实现。

## 2. 目标与非目标

### 2.1 目标

1. 建立从首次打开、完成配置到首次成功任务的激活漏斗。
2. 建立任务、语音、场景、工具、模型及重点功能的使用与质量指标。
3. 能以安装实例为匿名主体计算活跃、留存、漏斗和版本质量。
4. 登录体系可用后，支持在获得明确授权的前提下计算跨设备账号指标。
5. 统一事件命名、属性、去重、版本、留存、删除和数据质量标准。
6. 为运营看板、版本复盘、功能决策和受控实验提供可信数据。

### 2.2 非目标

- 不记录用户输入、模型回复、会话标题、文件内容、文件名或文件路径。
- 不记录工具参数、工具输出、命令正文、原始错误堆栈、API Key、Token 或 Cookie。
- 不以埋点替代日志、崩溃分析、性能监控、安全审计或财务账本。
- 不使用行为数据自动评价单个员工、客户或用户的绩效。
- 不从客户端伪造订阅、支付、续费、退款等商业事件。
- 不把“任务技术完成”直接等同于“用户问题已解决”。

## 3. 产品指标体系

### 3.1 北极星指标

**周成功任务活跃安装数（WSTA）**：北京时区自然周内，至少产生一次 `task_finished(status=success)` 的唯一安装实例数。

选择该指标的原因：它同时约束活跃和核心价值交付，比打开应用、发送消息或任务总量更接近用户获得价值。

同时观察以下护栏指标，避免通过降低任务门槛或重复触发虚增北极星指标：

- 任务成功率；
- 成功任务 P50/P90 总耗时；
- 任务取消率和失败率；
- 7 日成功任务留存率；
- 埋点拒绝率、丢弃率和重复率；
- 用户负向反馈率。

### 3.2 核心指标口径

| 指标 | 计算口径 | 说明 |
|---|---|---|
| 新安装数 | 首次出现 `app_first_open` 的唯一 `installation_id` | 重装且本地身份被删除时视为新安装 |
| 激活安装数 | 首次打开后 24 小时内至少一次成功任务的唯一安装数 | 激活窗口固定为 24 小时 |
| 激活率 | 激活安装数 / 同期新安装数 | 按首次打开日期归因 cohort |
| 首次价值耗时 | `first task_finished(success).occurred_at - app_first_open.occurred_at` | 输出 P50/P75/P90，未激活者不进入耗时分布 |
| 日活跃安装数 | 当日至少一次 `task_submitted` 的唯一安装数 | 页面打开不算核心活跃 |
| 日成功活跃安装数 | 当日至少一次成功任务的唯一安装数 | 作为日级北极星代理指标 |
| 任务接纳率 | `task_admitted` 数 / `task_submitted` 数 | 衡量提交后能否进入引擎 |
| 任务成功率 | 成功 `task_finished` 数 / 已结束 `task_finished` 数 | `cancelled` 单列，不从分母剔除 |
| 首输出耗时 | `task_first_output - task_admitted` | 无首输出的失败任务单列 |
| 任务总耗时 | `task_finished - task_admitted` | 按模式、模型、版本和平台分组 |
| 人均任务数 | 期间任务数 / 期间唯一活跃安装数 | 只适合周期汇总 |
| 每活跃安装日任务数 | 任务总数 / 各自然日活跃安装数之和 | 禁止对含零活跃日的“每日比率”再次平均 |
| D1/D7/D30 留存 | 首次激活后第 1/7/30 日再次成功完成任务的 cohort 比率 | 以激活日为 cohort 起点 |
| 功能采用率 | 使用某功能的唯一成功活跃安装数 / 同期成功活跃安装数 | 功能事件必须达到定义的“有效使用”节点 |
| 工具调用成功率 | 成功 `tool_call_completed` / 全部 `tool_call_completed` | 按工具类型、工具键、版本分组 |
| 正向反馈率 | `positive` 反馈数 / 全部明确反馈数 | 未反馈不视作正向或负向 |

### 3.3 主体口径

- 默认主体是匿名 `installation_id`，看板必须标注“安装实例/设备”，不得展示为“用户”。
- 服务端签发的 `device_id` 是安装主体的服务端代理标识，可用于上传鉴权和去重。
- 登录后可增加不可逆的 `account_id_hash`，但账号指标和安装指标必须分栏展示。
- 未经明确授权，不得用硬件指纹、IP、文件或会话内容推导跨安装身份。
- 同一账号跨设备去重仅用于账号指标；安装维度原始事实仍需保留。

## 4. 采集原则与隐私边界

### 4.1 数据最小化

只采集回答既定产品问题所需的结构化枚举、布尔值、受控标识和耗时。任何新增属性必须说明用途、取值范围、负责人和保留周期。

禁止字段包括但不限于：

- prompt、response、会话标题和摘要；
- 文件内容、文件名、绝对路径和知识库正文；
- 工具参数、命令、stdout、stderr 和原始错误消息；
- API Key、密钥、Token、Cookie、授权码、邮箱、手机号和真实姓名；
- 完整公网 IP、硬件序列号和可逆设备指纹；
- 用户自定义工具名、服务器地址、模型服务地址等可能包含私人信息的自由文本。

### 4.2 用户控制

- 首次启用前展示简明说明：收集目的、数据类型、保留周期和关闭入口。
- 默认策略由最终隐私评审决定；无论默认开关如何，设置页必须提供随时关闭入口。
- 关闭后不再产生新行为事件，待发送队列应清除或按用户选择处理。
- 提供“删除本机行为数据”和“申请删除服务端数据”的路径。
- 企业托管环境允许管理员通过策略关闭，但界面应向用户显示当前状态。

### 4.3 安全与合规

- 全链路 HTTPS；上传接口需鉴权、限流、限制批大小并校验 schema。
- 看板和明细接口必须鉴权并遵循最小权限，不公开设备级明细。
- 日志不得打印完整事件包、凭证或被拒绝的原始自由文本。
- 行为数据与账号、支付数据的关联必须经过专门权限控制和审计。
- 正式上线前由产品、法务/隐私、安全和数据负责人共同批准数据清单。

## 5. 统一事件模型

### 5.1 命名与版本

- 事件名使用小写 `snake_case`，采用“对象_动作”结构，如 `task_submitted`。
- 已发布事件不改变原义；语义变化时增加 `schema_version` 或创建新事件。
- 属性名使用小写 `snake_case`，枚举值使用小写 `snake_case`。
- 时间均以 UTC Unix 毫秒上传；看板默认按北京时间自然日展示，并允许切换时区。
- 单个事件建议不超过 8 KiB，单批最多 50 条；超限事件应拒绝并记录原因。

### 5.2 公共字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `schema_version` | integer | 是 | 初始值 `1` |
| `event_id` | string | 是 | 客户端生成的全局唯一 ID，作为幂等键 |
| `event_name` | string | 是 | 受服务端白名单约束 |
| `occurred_at` | integer | 是 | 客户端 UTC 毫秒时间 |
| `received_at` | integer | 服务端 | 服务端接收时间，不由客户端信任 |
| `device_id` | string | 服务端注入 | 服务端签发的匿名设备标识 |
| `account_id_hash` | string | 否 | 登录且合规授权后由可信身份层生成 |
| `app_version` | string | 是 | 根目录 `VERSION` 对应版本 |
| `platform` | enum | 是 | `windows`、`macos`、`linux`、`web` |
| `arch` | enum | 是 | `x86_64`、`aarch64`、`unknown` |
| `channel` | enum | 是 | `stable`、`beta`、`dev`、`unknown` |
| `locale` | enum | 是 | 仅受支持语言代码，不上传自由文本 |
| `session_id` | string | 条件必填 | 会话内事件必填，使用内部随机 ID |
| `turn_id` | string | 条件必填 | 任务链路事件必填 |
| `operation_id` | string | 条件必填 | 安装、导入、工具调用等开始/结果事件共用 |
| `entry_point` | enum | 否 | 用户从何处进入功能 |
| `mode` | enum | 否 | `assistant`、`code`、`scheduled`、`team` 等 |
| `input_type` | enum | 否 | `text`、`voice`、`attachment`、`mixed`、`system` |
| `status` | enum | 否 | 事件规定的受控状态 |
| `duration_ms` | integer | 否 | 非负，服务端限制最大值 |
| `error_category` | enum | 否 | 失败事件必填，禁止上传原始错误 |
| `experiment_ids` | string[] | 否 | 已登记的实验与分组，不含自由文本 |

### 5.3 统一错误分类

`error_category` 只允许以下一级分类；需要细分时增加经过评审的二级枚举 `error_code`：

- `permission_denied`
- `authentication_failed`
- `configuration_missing`
- `network_unavailable`
- `timeout`
- `rate_limited`
- `provider_error`
- `model_error`
- `tool_error`
- `unsupported`
- `user_cancelled`
- `validation_failed`
- `internal_error`
- `unknown`

原始错误只进入本地诊断日志，并按现有日志脱敏规范处理。

### 5.4 事件关联与幂等

- 一次用户任务以 `turn_id` 串联提交、接纳、首输出、工具调用和结束事件。
- 一次异步操作以 `operation_id` 串联开始和结果，重试不得生成新的逻辑操作 ID。
- 同一 `event_id` 重传时，服务端只接受一次并返回重复计数。
- 服务端按 `event_id` 去重，不以时间、设备或属性组合猜测重复事件。
- 事件乱序到达时按 `occurred_at` 还原漏斗；超过保留窗口的数据拒绝进入业务指标。

## 6. 事件字典

优先级定义：P0 为首期指标闭环必需，P1 为重点功能分析，P2 为优化和实验分析。表中“结果属性”为除公共字段外的必填或核心属性。

### 6.1 应用与激活

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `app_first_open` | 本安装首次完成应用初始化后，仅一次 | `install_source`、`previous_version_present` | P0 |
| `app_opened` | 用户可交互主窗口就绪，每次冷启动一次 | `launch_type`、`startup_duration_ms` | P1 |
| `onboarding_started` | 首次引导首屏可见 | `entry_point` | P0 |
| `onboarding_completed` | 引导最后一步成功完成 | `duration_ms`、`provider_configured` | P0 |
| `onboarding_skipped` | 用户主动跳过 | `step`、`duration_ms` | P0 |
| `provider_setup_started` | 用户开始新增或修改模型供应商配置 | `provider_key`、`entry_point`、`operation_id` | P0 |
| `provider_setup_completed` | 凭据保存且最小可用性校验通过 | `provider_key`、`operation_id`、`duration_ms` | P0 |
| `provider_setup_failed` | 保存或校验失败 | `provider_key`、`operation_id`、`error_category` | P0 |

约束：`provider_key` 必须来自内置目录；自定义供应商统一记为 `custom`，不得上传名称、URL 或凭据。

### 6.2 核心任务链路

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `task_submitted` | 用户提交有效输入，进入客户端发送流程 | `session_id`、`turn_id`、`mode`、`input_type`、`entry_point`、`has_attachment` | P0 |
| `task_admitted` | 引擎确认本轮被接纳 | `session_id`、`turn_id`、`queue_duration_ms` | P0 |
| `task_rejected` | 提交后未被接纳且不会继续执行 | `session_id`、`turn_id`、`error_category`、`stage` | P0 |
| `task_first_output` | 本轮首次出现对用户可见的文本或成果 | `session_id`、`turn_id`、`output_type`、`duration_ms` | P0 |
| `task_cancel_requested` | 用户主动请求取消正在运行的任务 | `session_id`、`turn_id`、`stage` | P1 |
| `task_finished` | 本轮进入唯一终态 | `session_id`、`turn_id`、`status`、`duration_ms`、`error_category`（失败时） | P0 |
| `task_retry_requested` | 用户从失败或既有回复发起重试/重新生成 | `session_id`、`source_turn_id`、`retry_reason` | P1 |

`task_finished.status` 仅允许：

- `success`：引擎正常结束且产生用户可见结果；
- `failed`：因系统、模型、工具或配置错误终止；
- `cancelled`：用户取消生效；
- `rejected`：进入执行前被拒绝；
- `interrupted`：应用退出、引擎断连等造成未知终态。

每个 `task_admitted` 最终必须对应且只对应一个 `task_finished`。后台内部维护任务如果不代表用户意图，不得计入核心任务；必须采集时使用 `mode=system` 并从产品指标排除。

### 6.3 语音输入

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `voice_entry_clicked` | 用户点击语音入口 | `session_id`、`entry_point` | P1 |
| `voice_permission_result` | 系统麦克风权限请求返回 | `status=granted/denied/restricted/error`、`error_category` | P1 |
| `voice_started` | 已获得音频流并开始录音 | `session_id`、`operation_id` | P0 |
| `voice_recognition_completed` | 识别成功且生成非空文本 | `operation_id`、`duration_ms`、`recognizer_type` | P1 |
| `voice_recognition_failed` | 识别失败或结果为空 | `operation_id`、`duration_ms`、`error_category` | P1 |
| `voice_message_submitted` | 识别结果被实际提交为任务 | `operation_id`、`session_id`、`turn_id` | P1 |
| `voice_cancelled` | 用户在提交前取消 | `operation_id`、`stage`、`duration_ms` | P1 |

不得上传录音、识别文本、文本长度的高精度值或可还原内容的特征。需要长度分析时使用 `length_bucket`：`1_20`、`21_100`、`101_500`、`500_plus`。

### 6.4 工具市场、安装与调用

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `tool_impression` | 工具卡片进入可视区域；同页同工具仅一次 | `tool_key`、`tool_type`、`entry_point`、`position_bucket` | P1 |
| `tool_detail_opened` | 用户打开工具详情 | `tool_key`、`tool_type`、`entry_point` | P1 |
| `tool_install_started` | 用户确认安装并开始执行 | `tool_key`、`tool_type`、`operation_id` | P0 |
| `tool_install_completed` | 安装进入成功或失败终态 | `tool_key`、`tool_type`、`operation_id`、`success`、`duration_ms`、`error_category` | P0 |
| `tool_configuration_completed` | 工具所需授权/配置校验通过 | `tool_key`、`tool_type`、`operation_id` | P1 |
| `tool_uninstall_completed` | 用户完成卸载 | `tool_key`、`tool_type`、`success`、`error_category` | P2 |
| `tool_call_started` | 引擎准备执行一次工具调用 | `session_id`、`turn_id`、`operation_id`、`tool_key`、`tool_type` | P0 |
| `tool_call_completed` | 工具调用成功、失败或取消 | 上述字段加 `success`、`duration_ms`、`error_category` | P0 |

约束：

- `tool_key` 只能使用已登记的稳定目录键；用户自建或未知工具统一映射为 `custom`/`unknown`。
- MCP、CLI、Skill 和内置工具分别使用 `mcp`、`cli`、`skill`、`builtin`。
- 调用统计只记录工具类别、稳定键和结果，不记录参数、返回值、服务器地址和用户自定义名称。
- 安装成功不代表采用；“工具采用”必须至少发生一次成功 `tool_call_completed`。

### 6.5 场景入口

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `scene_impression` | 场景入口实际可见；同页同场景仅一次 | `scene_l1`、`scene_l2`、`entry_point` | P1 |
| `scene_selected` | 用户选择场景 | `scene_l1`、`scene_l2`、`entry_point` | P1 |
| `scene_submitted` | 携带场景标识的输入被实际提交 | `scene_l1`、`scene_l2`、`session_id`、`turn_id` | P0 |

场景效果以 `turn_id` 关联后续任务成功率、首输出耗时和反馈率；只比较“触发次数”不能判断场景价值。

### 6.6 模型选择与运行

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `model_selected` | 用户明确更改会话或默认模型 | `provider_key`、`model_key`、`selection_scope`、`entry_point` | P1 |
| `model_used` | 已接纳任务确定实际执行模型 | `session_id`、`turn_id`、`provider_key`、`model_key`、`selection_source` | P0 |
| `model_fallback_occurred` | 执行中切换到非最初模型 | `session_id`、`turn_id`、`from_model_key`、`to_model_key`、`error_category` | P1 |

`selection_source` 仅允许 `user_selected`、`session_default`、`app_default`、`system_routed`、`fallback`。模型排行必须同时展示任务成功率、耗时和选择来源，不能把默认配置偏差解释为用户偏好。自定义模型统一使用脱敏目录键，不上传服务地址或用户自定义别名。

### 6.7 知识、附件与成果

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `attachment_added` | 附件进入待提交列表 | `file_type_bucket`、`size_bucket`、`entry_point` | P1 |
| `attachment_processing_completed` | 附件解析进入终态 | `operation_id`、`file_type_bucket`、`success`、`duration_ms`、`error_category` | P1 |
| `knowledge_import_started` | 用户确认知识导入 | `operation_id`、`source_type`、`item_count_bucket` | P1 |
| `knowledge_import_completed` | 导入进入终态 | `operation_id`、`success`、`duration_ms`、`error_category` | P1 |
| `knowledge_search_completed` | 一次知识检索完成 | `session_id`、`turn_id`、`success`、`result_count_bucket`、`duration_ms` | P2 |
| `artifact_created` | 产生可预览的结构化成果 | `session_id`、`turn_id`、`artifact_type` | P1 |
| `artifact_exported` | 用户成功导出成果 | `session_id`、`turn_id`、`artifact_type`、`export_format` | P1 |

文件仅按受控类型和大小桶统计；不得上传文件名、路径、内容、知识条目标题或检索词。

### 6.8 重点工作模式

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `code_mode_started` | 代码模式会话成功创建或恢复 | `session_id`、`entry_point`、`provider_key` | P1 |
| `code_mode_finished` | 代码模式会话结束 | `session_id`、`status`、`duration_ms`、`error_category` | P1 |
| `scheduled_task_created` | 定时任务保存成功 | `schedule_type`、`task_type` | P1 |
| `scheduled_task_run_finished` | 一次计划执行结束 | `operation_id`、`status`、`duration_ms`、`error_category` | P1 |
| `team_session_started` | 多智能体/团队任务被接纳 | `session_id`、`member_count_bucket`、`entry_point` | P1 |
| `team_session_finished` | 团队任务结束 | `session_id`、`status`、`duration_ms`、`error_category` | P1 |

功能采用率以成功进入有效状态为准，例如定时任务采用应至少成功执行一次，不能只看创建次数。

### 6.9 满意度与价值代理

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `response_feedback_submitted` | 用户提交赞/踩或结构化原因 | `session_id`、`turn_id`、`rating=positive/negative`、`reason_code` | P1 |
| `response_regenerated` | 用户请求重新生成 | `session_id`、`source_turn_id` | P1 |
| `response_copied` | 用户复制助手输出 | `session_id`、`turn_id`、`content_type` | P2 |
| `followup_submitted` | 用户在成功任务后一定窗口内继续追问 | `session_id`、`previous_turn_id`、`interval_bucket` | P2 |

复制、导出、后续追问和反馈只能作为价值代理信号，不单独证明任务成功。反馈原因必须使用受控枚举，不采集用户填写的自由文本。

### 6.10 商业事件

以下事件只允许由账号、订阅或支付服务端依据真实业务状态产生，客户端可以产生页面浏览事件，但不得产生成功账务事件：

| 事件 | 权威生产方 | 核心属性 | 优先级 |
|---|---|---|---:|
| `plan_viewed` | 客户端/账号服务 | `account_id_hash`、`plan_key`、`entry_point` | P2 |
| `trial_started` | 订阅服务 | `account_id_hash`、`plan_key`、`trial_days` | P2 |
| `checkout_started` | 订单服务 | `account_id_hash`、`order_id_hash`、`plan_key` | P2 |
| `payment_succeeded` | 支付回调/订单服务 | `account_id_hash`、`order_id_hash`、`plan_key`、`currency`、`amount_minor` | P2 |
| `payment_failed` | 支付回调/订单服务 | 上述字段加 `error_category` | P2 |
| `subscription_renewed` | 订阅服务 | `account_id_hash`、`subscription_id_hash`、`plan_key` | P2 |
| `subscription_cancelled` | 订阅服务 | 上述字段加 `cancel_reason_code` | P2 |
| `refund_completed` | 支付回调/订单服务 | `account_id_hash`、`order_id_hash`、`amount_minor` | P2 |

金额使用最小货币单位整数；看板不得用随机数、固定倍率或客户端本地状态模拟收入、付费用户和续费数据。账号体系及商业服务未具备前，对应模块显示“暂无权威数据”，不得展示假数据。

## 7. 关键漏斗与分析看板

### 7.1 新用户激活漏斗

`app_first_open` → `onboarding_started` → `provider_setup_completed` → `task_submitted` → `task_admitted` → `task_first_output` → `task_finished(success)`

要求：

- 展示每步人数、转化率、中位耗时和主要失败分类；
- 支持按版本、平台、渠道、语言和首次模型供应商分组；
- 同一安装只取窗口内第一次到达每个节点；
- 允许跳过引导的用户直接进入后续节点，不强制伪造缺失事件。

### 7.2 核心任务漏斗

`task_submitted` → `task_admitted` → `task_first_output` → `task_finished`

要求展示：提交量、唯一活跃安装数、接纳率、首输出率、成功率、取消率、失败分类、P50/P90 首输出耗时及总耗时。

### 7.3 工具采用漏斗

`tool_impression` → `tool_detail_opened` → `tool_install_started` → `tool_install_completed(success=true)` → `tool_configuration_completed` → `tool_call_completed(success=true)`

按 `tool_key` 和 `tool_type` 展示，分别计算曝光到安装、安装到配置、配置到首个成功调用的转化与耗时。

### 7.4 语音输入漏斗

`voice_entry_clicked` → `voice_permission_result(granted)` → `voice_started` → `voice_recognition_completed` → `voice_message_submitted` → `task_finished(success)`

语音价值必须最终关联任务结果，单独的录音启动量只反映尝试意愿。

### 7.5 场景价值分析

`scene_impression` → `scene_selected` → `scene_submitted` → `task_finished` → 反馈/复制/导出

场景排行至少同时展示曝光、选择率、提交率、任务成功率、耗时和负向反馈率。

### 7.6 版本质量看板

- 新旧版本的任务接纳率、成功率、取消率；
- P50/P90 首输出和总耗时；
- 各错误分类占比；
- 埋点上报健康度；
- 按平台和架构分层，样本量不足时隐藏百分比或标记低可信度。

## 8. 当前实现与目标事件映射

截至本文版本，主线已有以下行为事件。此表用于迁移，不代表目标口径已经满足。

| 当前事件 | 当前状态 | 目标处理 |
|---|---|---|
| `task_started` | 常规助手在引擎接纳后发送 | 迁移为 `task_admitted`；补充更早的 `task_submitted` 和拒绝事件 |
| `task_finished` | 已覆盖正常终态和部分 forwarder 失败 | 保留名称，统一终态枚举、耗时和错误分类，检查所有模式仅发一次 |
| `voice_started` | 获得音频流并开始录音时发送 | 保留，补齐入口、权限、识别结果、提交和取消事件 |
| `scene_triggered` | 带场景的消息提交后发送 | 迁移为 `scene_submitted`，补齐曝光和选择事件，并写入 `turn_id` |
| `tool_install_completed` | 仅成功安装时发送 | 失败也必须发送同名结果事件，并补齐开始、配置和卸载事件 |
| `tool_call_completed` | 已有辅助函数，但主线未发现生产调用点 | 在统一工具执行出口接线；补齐开始事件、耗时和错误分类 |
| `model_used` | 常规助手接纳任务时发送 | 覆盖 Code/ACP 等所有执行模式，补齐选择来源、结果与回退事件 |

现有实现还存在以下迁移要求：

- `input_type` 已在结构中定义，但当前任务链路未稳定赋值；应在提交入口统一计算。
- 当前行为事件使用容量为 512 的内存队列，发送失败会跳过；P0 指标上线前应使用有界持久化 outbox、成功确认后删除，并公开丢弃计数。
- 当前前端命令只允许语音和场景两个事件；新增前端事件时继续使用白名单，禁止开放任意事件名或任意属性透传。
- 服务端事件白名单、校验、存储、统计 API、看板和隐私说明必须与客户端在同一发布里形成闭环。
- 行为统计与现有设备运营统计可以复用匿名设备凭证，但事件域、指标口径和权限应清晰分层。

## 9. 数据处理与存储要求

### 9.1 客户端

- 事件先写入有界持久化 outbox，再异步批量发送，不能阻塞任务和界面。
- 默认最多保留 30 天或 5,000 条，任一上限达到时删除最旧事件并增加本地丢弃计数。
- 服务端明确返回 accepted/duplicates/rejected 后，客户端只删除已确认事件。
- 网络错误采用指数退避和抖动；4xx schema 错误不得无限重试。
- 客户端时钟异常时仍上传，但标记 `clock_skew_bucket`，报表可按接收时间兜底。
- 埋点模块故障不得影响核心业务；业务成功也不得被上报失败改写。

### 9.2 服务端

- 对事件名、schema 版本、属性类型、枚举、长度、批大小和时间范围做严格校验。
- 服务端注入可信 `received_at`、`device_id` 和生产方信息。
- 明细事实表与聚合表分离；商业事实使用独立权威数据源。
- 原始行为事件建议保留 35 天，日聚合数据建议保留 13 个月；最终周期以隐私评审为准。
- 到期数据自动删除；账号或安装删除请求应同步清理可关联明细及后续聚合重算队列。
- 统计任务必须可重跑，指标 SQL/代码需版本化并有口径测试。

### 9.3 数据质量指标

以下指标属于遥测管道运维指标，不应通过同一条行为事件管道自我采集：

- 事件生成数、入队数、客户端丢弃数；
- 批次发送数、重试数、网络失败数；
- 服务端接受数、重复数、schema 拒绝数、限流数；
- 从 `occurred_at` 到 `received_at` 的延迟分布；
- `task_admitted` 无终态比例、重复终态比例；
- 开始事件无结果比例、结果事件无开始比例；
- 按版本的未知枚举和未知 schema 比例。

告警建议：P0 事件服务端拒绝率连续 15 分钟超过 1%，或已接纳任务 24 小时后无终态比例超过 0.5% 时告警。阈值上线后可按基线调整，但变更需留痕。

## 10. 看板权限与展示规范

- 管理员总览默认展示聚合数据，不提供会话正文或逐事件浏览。
- 设备明细只显示匿名 ID、版本、平台、粗粒度地区和汇总指标。
- 样本量小于既定隐私阈值时，不展示细分分组；建议初始阈值为 20 个安装实例。
- 所有图表标注时区、统计周期、主体类型、指标定义和最后更新时间。
- 无数据、数据延迟和埋点未上线必须分别呈现，不能统一显示为 0。
- 事件或口径发布变更时，在图表上标注切换日期，避免跨版本误读。
- 导出权限单独控制，导出文件不包含可直接识别个人的信息。

## 11. 分阶段实施计划

### 阶段 A：可信核心闭环（P0）

1. 冻结公共 schema、主体口径和隐私清单。
2. 完成用户控制、持久化 outbox、服务端校验与幂等。
3. 打通激活与核心任务事件。
4. 将工具调用完成事件接入统一执行出口。
5. 补齐工具安装失败、语音结果、场景任务关联和模型选择来源。
6. 上线激活、任务、工具及管道健康看板。

阶段 A 完成标准：可以可信回答“多少新安装在 24 小时内完成首次成功任务、任务在哪一步失败、工具是否真正被成功调用”。

### 阶段 B：功能采用与价值代理（P1）

1. 覆盖知识、附件、成果、代码模式、定时任务和团队协作。
2. 上线反馈、重新生成、复制和导出等价值代理。
3. 建立 D1/D7/D30 cohort 留存和版本质量对比。
4. 建立场景、语音、工具的完整漏斗。

### 阶段 C：商业与实验（P2）

1. 账号与订单服务提供权威商业事件后再上线商业看板。
2. 建立受控实验登记、分流、曝光和结果分析机制。
3. 在满足样本量和隐私阈值的前提下开展转化与长期价值分析。

## 12. 验收标准

### 12.1 产品与数据验收

- 每个 P0 指标能追溯到事件、触发时机、分母、分子、时区和去重规则。
- 看板使用“安装实例”和“账号”的准确称谓，不混称“用户”。
- 激活、任务、工具和语音漏斗能用固定测试数据复算并得到一致结果。
- `每活跃安装日任务数` 按任务总数除以活跃安装日总和计算。
- 商业模块在无权威数据时明确显示未接入，不出现模拟收入或随机数据。

### 12.2 客户端验收

- 每个 `turn_id` 最多一个 `task_submitted`、一个 `task_admitted` 和一个 `task_finished`。
- 成功、失败、取消、提交拒绝、应用退出和引擎断连均有明确终态或可审计补偿逻辑。
- 离线、弱网、重启、重复上传和队列满场景均有自动化测试。
- 关闭行为统计后不再生成或发送新事件。
- 自动化测试证明事件中不包含消息正文、文件路径、工具参数和原始错误。
- Web/Tauri/各操作系统不支持的能力返回明确状态，不伪造成功事件。

### 12.3 服务端验收

- 相同 `event_id` 重复提交只计一次。
- 未知事件、未知属性、非法枚举、超长字段、过期时间和超大批次被安全拒绝。
- accepted/duplicates/rejected 返回值与实际落库一致。
- 事件留存、删除请求、权限、限流和备份恢复经过验证。
- 指标计算有覆盖零活跃日、跨日、乱序、重复、迟到、版本切换和时区边界的测试。

### 12.4 发布门禁

- 产品、数据、客户端、服务端、安全/隐私负责人完成事件清单评审。
- 文档、客户端 schema、服务端白名单、指标定义和看板版本一致。
- 新版本先灰度验证事件量、拒绝率、完整率和业务性能，再逐步扩大。
- 埋点对任务延迟和资源占用的影响达到约定预算；建议发送逻辑不增加用户操作同步等待，常驻磁盘占用不超过已设上限。
- 回滚埋点服务或关闭开关不会影响任务、工具、语音等核心功能。

## 14. 变更治理

- 事件新增或修改必须同步更新本文、schema、客户端/服务端契约测试和指标字典。
- 事件负责人需要在发布前给出预期日量、用途、保留周期和下线条件。
- 连续两个正式版本无人消费且不影响法务、安全或账务的事件，应进入下线评审。
- 废弃事件至少保留一个正式版本兼容期，并在看板标注停止采集日期。
- 任何扩大采集范围、延长保留周期或关联账号身份的变更，必须重新进行隐私评审。

## 15. 待评审决策

以下事项在开发前必须形成明确结论：

1. 行为统计的默认启用策略，以及不同发行渠道是否一致。
2. 原始事件和聚合数据的最终保留周期。
3. 登录后安装主体与账号主体的关联授权和删除流程。
4. P0 事件的性能预算、离线队列容量和告警阈值。
5. 首期要覆盖的运行模式：普通助手、Code/ACP、定时任务和团队协作是否同步上线。
6. 场景、工具、模型目录键的维护负责人和版本治理方式。
7. 商业数据权威系统、币种口径、退款归因和权限边界。
