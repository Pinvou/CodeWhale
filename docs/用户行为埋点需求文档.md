## 1. 背景

当前行为埋点已经覆盖任务开始/结束、语音开始、工具安装完成、场景触发和模型使用等基础事件，但还不足以回答以下产品问题：

- 新用户是否完成了首次有效任务，在哪一步流失？
- 用户提交的任务是否真正成功，耗时和失败原因是什么？
- 语音、场景、工具、知识库、代码模式等能力是否被发现并形成稳定使用？
- 工具从曝光、安装、配置到实际调用的完整转化如何？
- 模型使用量来自用户主动选择、系统默认还是故障回退？
- 技术上的“任务完成”是否给用户带来了可感知价值？
- 版本发布后，核心成功率、留存和错误率是否发生异常变化？
- 商业转化是否真实发生，而非由前端模拟数据推导？

本需求在不采集会话正文和私人数据的前提下，建立统一、可追溯、可验收的行为分析体系。本文是产品与数据口径文档，不代表其中所有事件已经实现。

## 2. 目标与非目标

### 2.1 目标

1. 建立从首次打开、完成配置到首次成功任务的激活漏斗。
2. 建立任务、语音、场景、工具、模型及重点功能的使用与质量指标。
3. 能以安装实例为匿名主体计算活跃、留存、漏斗和版本质量。
4. 登录体系可用后，支持在获得明确授权的前提下计算跨设备账号指标。
5. 统一事件命名、属性、去重、版本、留存、删除和数据质量标准。
6. 为运营看板、版本复盘、功能决策和受控实验提供可信数据。

### 2.2 非目标

- 不记录用户输入、模型回复、会话标题、文件内容、文件名或文件路径。
- 不记录工具参数、工具输出、命令正文、原始错误堆栈、API Key、Token 或 Cookie。
- 不以埋点替代日志、崩溃分析、性能监控、安全审计或财务账本。
- 不使用行为数据自动评价单个员工、客户或用户的绩效。
- 不从客户端伪造订阅、支付、续费、退款等商业事件。
- 不把“任务技术完成”直接等同于“用户问题已解决”。

## 3. 产品指标体系

### 3.1 北极星指标与阶段代理指标

**目标北极星指标——周显性价值任务活跃安装数（WEVTA）**：北京时区自然周内，至少有一个技术成功任务，并且该任务在 30 分钟内产生明确价值信号的唯一安装实例数。明确价值信号包括：正向反馈、复制回复或导出成果，必须通过同一 `turn_id` 关联。

WEVTA 是可观测到的价值下界：用户阅读结果后直接离开也可能已经获得价值，因此不得把未产生价值信号解释为任务无价值。

**阶段 A 代理指标——周技术成功任务活跃安装数（WSTA）**：北京时区自然周内，至少产生一次 `task_finished(status=success, initiator_type=user)` 的唯一安装实例数；仅包含 `assistant`、`code` 和用户发起的 `team` 模式，排除 `scheduled` 和 `system`。

WSTA 只表示引擎正常完成并产生用户可见结果，不等同于用户问题已解决。阶段 B 的价值信号上线前使用 WSTA 观察核心链路规模，上线后必须与 WEVTA、负向反馈率共同展示。

同时观察以下护栏指标，避免通过降低任务门槛或重复触发虚增北极星指标：

- 提交成功率和已接纳任务成功率；
- 成功任务 P50/P90 总耗时；
- 任务取消率和失败率；
- 7 日成功任务留存率；
- 埋点拒绝率、丢弃率和重复率；
- 用户负向反馈率。

### 3.2 核心指标口径

| 指标 | 计算口径 | 说明 |
|---|---|---|
| 可观测新 cohort 数 | 首次出现 `analytics_cohort_started` 的唯一 `device_id` | 仅代表允许行为统计的安装实例，不外推为全部安装量 |
| 激活安装数 | cohort 开始后 24 小时内至少一次用户发起的成功任务的唯一 `device_id` 数 | 激活窗口固定为 24 小时 |
| 激活率 | 激活安装数 / 同期可观测新 cohort 数 | 按 `analytics_cohort_started` 日期归因 |
| 首次技术价值耗时 | `first task_finished(success).occurred_at - analytics_cohort_started.occurred_at` | 输出 P50/P75/P90，未激活者不进入耗时分布 |
| 日活跃安装数 | 当日至少一次用户发起的 `task_submitted` 的唯一 `device_id` 数 | 页面打开、计划任务和系统任务不算核心活跃 |
| 日技术成功活跃安装数 | 当日至少一次用户发起的成功任务的唯一 `device_id` 数 | 作为日级 WSTA 代理指标 |
| 任务接纳率 | `task_admitted` 数 / `task_submitted` 数 | 衡量提交后能否进入引擎 |
| 提交成功率 | 成功 `task_finished` 数 / `task_submitted` 数 | 同时反映提交拒绝和执行失败 |
| 已接纳任务成功率 | 成功 `task_finished` 数 / 已接纳且已结束任务数 | `cancelled` 和 `interrupted` 保留在分母，拒绝任务不进入该分母 |
| 提交拒绝率 | `task_rejected` 数 / `task_submitted` 数 | 与任务接纳率之和应为 100%，超时未决任务单独告警 |
| 首输出耗时 | `task_first_output - task_admitted` | 无首输出的失败任务单列 |
| 任务总耗时 | `task_finished - task_admitted` | 按模式、模型、版本和平台分组 |
| 人均任务数 | 期间任务数 / 期间唯一活跃安装数 | 只适合周期汇总 |
| 每活跃安装日任务数 | 任务总数 / 各自然日活跃安装数之和 | 禁止对含零活跃日的“每日比率”再次平均 |
| D1/D7/D30 留存 | 首次激活后的第 1/7/30 个北京自然日再次成功完成用户任务的 cohort 比率 | 采用精确日口径；未观察满对应天数的 cohort 不进入分母 |
| 功能采用率 | 使用某功能的唯一成功活跃安装数 / 同期成功活跃安装数 | 功能事件必须达到定义的“有效使用”节点 |
| 工具调用成功率 | 成功 `tool_call_completed` / 全部 `tool_call_completed` | 按工具类型、工具键、版本分组 |
| 正向反馈率 | 当前状态为 `positive` 的回合数 / 当前有明确反馈的回合数 | 按 `feedback_id` 取最新非清除状态；未反馈不视作正向或负向 |

任务数量按唯一 `attempt_id` 或 `turn_id` 去重。接纳率与拒绝率只计算已经观察满 24 小时的提交 cohort；待决任务进入完整性告警，不提前归为拒绝或接纳。涉及百分比的看板必须同时展示分子、分母和样本量。

### 3.3 主体口径

- 默认分析主体是服务端签发并通过上传凭证认证的匿名 `device_id`，看板必须标注“安装实例/设备”，不得展示为“用户”。
- 客户端本地 `installation_id` 只参与设备注册，不进入行为事实表，也不作为报表字段；服务端不得信任事件正文自行声明的 `device_id`。
- 行为分析的 `device_id` 必须代表一次安装身份，不得用硬件指纹将重装前后的行为强行合并。可以复用设备运营统计的注册与鉴权基础设施，但只有主体语义完全一致时才能复用同一个 ID。
- 登录后可增加服务端生成的 `account_subject_id`。该 ID 使用带服务端密钥和版本的 HMAC 或等价令牌化方案生成，不上传账号原始 ID，也不得使用可被字典反查的普通哈希。
- 服务端需维护满足删除请求所需的受控映射或可重算规则，并记录令牌版本；分析人员不得访问原始账号标识。
- 未经明确授权，不得用硬件指纹、IP、文件或会话内容推导跨安装身份。
- 同一账号跨设备去重仅用于账号指标；安装维度原始事实仍需保留。

## 4. 采集原则与隐私边界

### 4.1 数据最小化

只采集回答既定产品问题所需的结构化枚举、布尔值、受控标识和耗时。任何新增属性必须说明用途、取值范围、负责人和保留周期。

禁止字段包括但不限于：

- prompt、response、会话标题和摘要；
- 文件内容、文件名、绝对路径和知识库正文；
- 工具参数、命令、stdout、stderr 和原始错误消息；
- API Key、密钥、Token、Cookie、授权码、邮箱、手机号和真实姓名；
- 完整公网 IP、硬件序列号和可逆设备指纹；
- 未规范化的用户自定义工具名、服务器地址、模型服务地址等可能包含私人信息的自由文本；工具名仅允许上传小写字母、数字、下划线、点和连字符组成的规范化标识，最长 96 字符。

### 4.2 内测采集策略与控制面

- 内测阶段只要构建已配置行为统计服务，且用户没有显式关闭，客户端即默认开启匿名行为采集，不要求首次确认。
- 启停入口固定放在“设置 → 帮助反馈 → 数据管理”二级页面，不作为设置一级导航项；二级页面以中英日三语明确展示采集范围、留存期、当前状态和启停开关。用户关闭或重新开启的选择持久化，前端桥接与 Tauri 命令提供对应操作并在失败时明确反馈。客户端不提供本地或服务端数据删除入口。
- 应用启动后仅在默认策略允许或用户显式开启时，通过控制面创建或恢复 `collection_period_id`；取得服务端确认前不生成远端行为事件，所有客户端事件必须携带当前有效周期 ID。
- 首次启动因离线、限流或服务暂不可用而无法建立周期时，客户端在后台有界指数退避重试，不阻塞对话、工具、语音或其他业务操作，也不回溯补造尚未建立周期时的事件。
- 本安装首次成功建立采集周期时发送一次 `analytics_cohort_started(eligibility_source=first_open)`，以该时刻作为激活 cohort 起点；跨重启只发送一次。
- 既有安装若没有显式用户偏好，升级后按默认策略建立或恢复采集周期；用户已显式关闭的安装保持关闭，已显式开启的安装恢复开启，旧周期事件不得混入新周期。
- `PINVOU_BEHAVIOR_TELEMETRY_ENABLED=false` 仅作为构建或运维级紧急停采开关，不替代用户设置；未显式配置该值时功能默认可用。停采必须立即作废本地采集代际、禁止事件 worker、新注册和新周期，并清空旧周期 outbox 与临时生命周期状态；已有 End/删除请求仍由 control-only worker 完成，恢复配置后继续尊重用户持久化偏好，不得补传停采前事件。
- 正式安装包默认复用设备运营统计已发布的遥测基础地址和公开 enrollment 协议门槛，并内置行为事件接收地址；这些值不是客户端身份秘密，安装身份仍由随机注册秘密和服务端签发的设备凭证保护。环境变量只用于端点覆盖、测试和紧急停采；不得要求标准安装后的桌面进程依赖启动器临时注入才能启用采集。显式提供的覆盖取值不完整（如空地址或长度不足的令牌）时必须失败关闭；仅覆盖部分端点时，其余端点使用内置默认值。
- 服务端仍保留留存到期、管理员/合规删除、墓碑和备份恢复能力。客户端收到权威删除响应后必须立即停止采集、清空本地 outbox 和临时关联状态，并持久化阻断标记；后续启动不得自动重新注册或恢复采集。
- 内测阶段的默认采集仅使用匿名安装主体，不启用账号关联。跨设备账号分析属于 P2，需单独完成产品、法务/隐私和安全评审后另行定义。

### 4.3 安全与合规

- 全链路 HTTPS；上传接口需鉴权、限流、限制批大小并校验 schema。
- 看板和明细接口必须鉴权并遵循最小权限，不公开设备级明细。
- 日志不得打印完整事件包、凭证或被拒绝的原始自由文本。
- 行为数据与账号、支付数据的关联必须经过专门权限控制和审计。
- 正式上线前由产品、法务/隐私、安全和数据负责人共同批准数据清单。

## 5. 统一事件模型

### 5.1 命名与版本

- 事件名使用小写 `snake_case`，采用“对象_动作”结构，如 `task_submitted`。
- 已发布事件不改变原义；语义变化时增加 `schema_version` 或创建新事件。
- 属性名使用小写 `snake_case`，枚举值使用小写 `snake_case`。
- 时间均以 UTC Unix 毫秒上传；看板默认按北京时间自然日展示，并允许切换时区。
- 客户端事件的 `occurred_at` 必须位于服务端接收时间前 35 天至后 5 分钟范围内；更早事件返回 `too_old`，未来超限返回 `invalid_time`。受控服务端回填使用隔离的管理入口和 `backfill` 审计记录，客户端不得声明回填。
- 单个事件序列化后不得超过 8 KiB，单批最多 50 条；超限事件按单条拒绝并返回受控原因，不得连带拒绝同批有效事件。
- P0 和 P1 事件首期不得抽样；未来确需抽样时必须增加明确抽样率、稳定抽样键和指标加权方案，并重新评审指标口径。

### 5.2 公共字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `schema_version` | integer | 是 | 初始值 `1` |
| `event_id` | string | 是 | 客户端生成的全局唯一 ID，作为幂等键 |
| `event_name` | string | 是 | 受服务端白名单约束 |
| `event_source` | enum | 是 | `client` 或 `server` |
| `occurred_at` | integer | 是 | 客户端 UTC 毫秒时间 |
| `received_at` | integer | 服务端 | 服务端接收时间，不由客户端信任 |
| `device_id` | string | 服务端注入 | 服务端签发的匿名设备标识 |
| `account_subject_id` | string | 条件必填 | 登录客户端事件由身份网关服务端注入，客户端不得声明；账号、订阅和支付事件必填 |
| `collection_period_id` | string | 客户端必填 | 客户端自动启动或恢复行为统计时由控制面签发，周期失效后不可复用 |
| `producer` | string | 是 | 客户端固定为 `pinvou_agent`；服务端使用登记的服务键 |
| `producer_version` | string | 是 | 产生事件的客户端或服务版本 |
| `environment` | enum | 服务端注入 | `production`、`staging`、`development`、`test`；非生产数据不得进入生产指标 |
| `app_version` | string | 客户端必填 | 根目录 `VERSION` 对应版本 |
| `platform` | enum | 客户端必填 | `windows`、`macos`、`linux`、`web` |
| `arch` | enum | 客户端必填 | `x86_64`、`aarch64`、`unknown` |
| `channel` | enum | 客户端必填 | `stable`、`beta`、`dev`、`unknown` |
| `locale` | enum | 客户端必填 | 仅受支持语言代码，不上传自由文本 |
| `session_id` | string | 条件必填 | 会话内事件必填，使用内部随机 ID |
| `attempt_id` | string | 条件必填 | 从用户提交开始生成的任务尝试 ID；接纳前可能没有 `turn_id` |
| `turn_id` | string | 条件必填 | 任务被引擎接纳后及其后续链路必填 |
| `operation_id` | string | 条件必填 | 安装、导入、工具调用等开始/结果事件共用 |
| `attempt_index` | integer | 条件必填 | 同一逻辑操作的物理执行次数，从 `1` 开始 |
| `view_id` | string | 条件必填 | 曝光和点击事件所在页面实例的随机 ID |
| `entry_point` | enum | 条件必填 | 用户主动进入或发起功能时必填；计划和系统触发不适用 |
| `mode` | enum | 否 | `assistant`、`code`、`scheduled`、`team` 等 |
| `initiator_type` | enum | 任务必填 | `user`、`schedule`、`team`、`system` |
| `input_type` | enum | 否 | `text`、`voice`、`attachment`、`mixed`、`system` |
| `status` | enum | 否 | 事件规定的受控状态 |
| `duration_ms` | integer | 否 | 非负，服务端限制最大值 |
| `error_category` | enum | 否 | 失败事件必填，禁止上传原始错误 |
| `experiment_assignments` | object[] | 否 | 已登记的 `{experiment_key, variant_key, assignment_unit}`，不得包含自由文本 |

ID 采用 URL-safe 不透明随机字符串，只允许 `[A-Za-z0-9_-]`。`event_id` 随机熵不得低于 128 bit，并在全局建立唯一索引；`attempt_id`、`operation_id`、`view_id`、`batch_id`、`collection_period_id` 及各匿名对象 ID 的随机熵不得低于 96 bit。任何 ID 都不得嵌入时间以外的设备、账号、文件、场景或业务语义。

公共字段条件矩阵：

| 生产类型 | 必填上下文 | 禁止或不适用 |
|---|---|---|
| 桌面端/Web 客户端事件 | `device_id`（服务端依据凭证注入）、`collection_period_id`、`app_version`、`platform`、`arch`、`channel`、`locale` | 客户端不得在事件中自行指定可信 `device_id` 或账号代理 ID |
| 登录客户端事件 | 客户端事件字段；身份网关可在服务端补充 `account_subject_id` | 不上传原始账号 ID |
| 账号/订阅/支付服务事件 | `account_subject_id`、`producer`、`producer_version` | `device_id`、`app_version`、`platform`、`arch`、`channel`、`locale` 不强制且不得伪造 |

`device_id` 可以出现在上传请求的鉴权上下文中，但落入事件事实表时必须由服务端根据有效凭证覆盖或注入。

### 5.3 统一错误分类

`error_category` 只允许以下一级分类；需要细分时增加经过评审的二级枚举 `error_code`：

- `permission_denied`
- `authentication_failed`
- `configuration_missing`
- `network_unavailable`
- `timeout`
- `rate_limited`
- `provider_error`
- `model_error`
- `tool_error`
- `unsupported`
- `user_cancelled`
- `validation_failed`
- `internal_error`
- `unknown`

原始错误只进入本地诊断日志，并按现有日志脱敏规范处理。

### 5.4 事件关联与幂等

- 一次用户提交在客户端生成 `attempt_id`；引擎接纳后再增加 `turn_id`。提交和拒绝可只使用 `attempt_id`，接纳及之后的事件同时携带两者。
- 一次逻辑异步操作以 `operation_id` 串联开始和结果；物理重试沿用同一 `operation_id` 并递增 `attempt_index`，从而同时支持逻辑去重和重试分析。
- 对存在开始/结果事件的操作，每个 `(operation_id, attempt_index)` 必须恰有一个开始事件和一个结果事件。用户关闭界面或主动停止时，结果事件使用取消状态或 `error_category=user_cancelled`，不能静默缺失。
- 同一 `event_id` 重传时，服务端只接受一次并返回重复计数。
- 服务端按 `event_id` 去重，不以时间、设备或属性组合猜测重复事件。
- 事件乱序到达时按 `occurred_at` 还原漏斗；超过保留窗口的数据拒绝进入业务指标。

## 6. 事件字典

优先级定义：P0 为首期指标闭环必需，P1 为重点功能分析，P2 为优化和实验分析。表中“结果属性”为除公共字段外的必填或核心属性。

### 6.1 应用与激活

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `analytics_cohort_started` | 本安装首次具备行为统计资格且应用可交互，仅一次 | `eligibility_source`、`install_source`、`previous_version_present` | P0 |
| `app_opened` | 用户可交互主窗口就绪，每次冷启动一次 | `launch_type`、`startup_duration_ms` | P1 |
| `onboarding_started` | 首次引导首屏可见 | `entry_point` | P0 |
| `onboarding_completed` | 引导最后一步成功完成 | `duration_ms`、`provider_configured` | P0 |
| `onboarding_skipped` | 用户主动跳过 | `step`、`duration_ms` | P0 |
| `provider_setup_started` | 用户开始新增或修改模型供应商配置 | `provider_key`、`entry_point`、`operation_id`、`attempt_index` | P0 |
| `provider_setup_completed` | 凭据保存且最小可用性校验通过 | `provider_key`、`operation_id`、`attempt_index`、`duration_ms` | P0 |
| `provider_setup_failed` | 保存或校验失败 | `provider_key`、`operation_id`、`attempt_index`、`error_category` | P0 |
| `task_environment_ready` | 首次达到可以提交任务的状态，仅一次 | `readiness_source`、`provider_key` | P0 |

约束：`provider_key` 必须来自内置目录；自定义供应商统一记为 `custom`，不得上传名称、URL 或凭据。
供应商、模型和工具的受控键集合以 `docs/schemas/behavior-telemetry-registries.json` 为机器可读单一来源；客户端映射与服务端接收、历史迁移必须由一致性测试锁定。

### 6.2 核心任务链路

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `task_submitted` | 有效输入进入客户端发送流程；此时生成尝试 ID | `session_id`、`attempt_id`、`mode`、`initiator_type`、`input_type`、`entry_point`（用户触发时）、`has_attachment` | P0 |
| `task_admitted` | 引擎确认本轮被接纳并分配回合 ID | `session_id`、`attempt_id`、`turn_id`、`queue_duration_ms` | P0 |
| `task_rejected` | 提交后未被接纳且不会继续执行；与 `task_admitted` 互斥 | `session_id`、`attempt_id`、`error_category`、`stage` | P0 |
| `task_first_output` | 本轮首次出现对用户可见的文本或成果 | `session_id`、`attempt_id`、`turn_id`、`output_type`、`duration_ms` | P0 |
| `task_cancel_requested` | 用户主动请求取消正在运行的任务 | `session_id`、`attempt_id`、`turn_id`、`stage` | P1 |
| `task_finished` | 已接纳任务进入唯一终态 | `session_id`、`attempt_id`、`turn_id`、`status`、`duration_ms`、`error_category`（失败时） | P0 |
| `task_retry_requested` | 用户从失败或既有回复发起重试/重新生成；新任务必须生成新的 `attempt_id` | `session_id`、`attempt_id`、`source_turn_id`、`retry_reason` | P1 |

`task_finished.status` 仅允许：

- `success`：引擎正常结束且产生用户可见结果；
- `failed`：因系统、模型、工具或配置错误终止；
- `cancelled`：用户取消生效；
- `interrupted`：应用退出、引擎断连等造成未知终态。

状态机必须满足：每个 `task_submitted` 最终只进入 `task_rejected` 或 `task_admitted` 其中之一；每个 `task_admitted` 最终对应且只对应一个 `task_finished`。后台内部维护任务如果不代表用户意图，不得计入核心任务；必须采集时使用 `mode=system, initiator_type=system` 并从产品指标排除。

`mode`、`initiator_type`、`input_type` 和 `has_attachment` 在 `task_submitted` 时冻结，并复制到 `task_admitted`、`task_first_output` 和 `task_finished`，保证终态事件可以独立分组。成功 `task_finished` 必须存在且只存在一个 `task_first_output`；失败、取消或中断允许没有首输出。

客户端在向引擎发送前持久化 `task_submitted` 和待决状态；进程恢复时，未接纳的待决任务补记 `task_rejected(error_category=internal_error, stage=shutdown)`，已接纳但无终态的任务补记 `task_finished(status=interrupted, stage=shutdown)`。数据质量看板仍需展示补偿事件比例，不能用补偿掩盖生命周期缺陷。

### 6.3 语音输入

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `voice_entry_clicked` | 用户点击语音入口 | `session_id`、`operation_id`、`entry_point` | P1 |
| `voice_permission_result` | 系统麦克风权限请求返回 | `session_id`、`operation_id`、`voice_permission_status`、`error_category`（错误时） | P1 |
| `voice_started` | 已获得音频流并开始录音 | `session_id`、`operation_id` | P1 |
| `voice_recognition_completed` | 识别成功且生成非空文本 | `operation_id`、`duration_ms`、`recognizer_type` | P1 |
| `voice_recognition_failed` | 识别失败或结果为空 | `operation_id`、`duration_ms`、`error_category` | P1 |
| `voice_message_submitted` | 识别结果被实际提交为任务 | `operation_id`、`session_id`、`attempt_id` | P1 |
| `voice_cancelled` | 用户在提交前取消 | `operation_id`、`stage`、`duration_ms` | P1 |

不得上传录音、识别文本、文本长度的高精度值或可还原内容的特征。需要长度分析时使用 `length_bucket`：`1_20`、`21_100`、`101_500`、`500_plus`。

每次点击语音入口生成新的 `operation_id`。一次语音操作必须且只能到达以下一个终态：

- `voice_permission_result` 为 `denied`、`restricted` 或 `error`；
- `voice_recognition_failed`；
- `voice_message_submitted`；
- `voice_cancelled`。

`voice_permission_result(granted)`、`voice_started` 和 `voice_recognition_completed` 是中间状态。识别成功后用户关闭、清空或放弃文本时必须发送 `voice_cancelled(stage=recognition)`；进程异常导致终态缺失时进入数据完整性告警，不补造成功。

### 6.4 工具市场、安装与调用

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `tool_impression` | 工具卡片进入可视区域；同一 `view_id` 内同工具仅一次 | `view_id`、`tool_key`、`tool_type`、`entry_point`、`position_bucket` | P1 |
| `tool_detail_opened` | 用户打开工具详情 | `view_id`、`tool_key`、`tool_type`、`entry_point` | P1 |
| `tool_install_started` | 用户确认安装并开始执行 | `tool_key`、`tool_type`、`operation_id`、`attempt_index` | P0 |
| `tool_install_completed` | 安装进入成功或失败终态 | `tool_key`、`tool_type`、`operation_id`、`attempt_index`、`success`、`duration_ms`、`error_category`（失败时） | P0 |
| `tool_configuration_started` | 用户开始工具授权或配置 | `tool_key`、`tool_type`、`operation_id`、`attempt_index`、`entry_point` | P1 |
| `tool_configuration_finished` | 配置成功、失败或取消 | `tool_key`、`tool_type`、`operation_id`、`attempt_index`、`success`、`duration_ms`、`error_category`（失败或取消时） | P1 |
| `tool_uninstall_completed` | 用户完成卸载 | `tool_key`、`tool_type`、`operation_id`、`attempt_index`、`success`、`error_category`（失败时） | P2 |
| `tool_call_started` | 引擎准备执行一次工具调用 | `session_id`、`turn_id`、`operation_id`、`attempt_index`、`tool_key`、`tool_type` | P0 |
| `tool_call_completed` | 工具调用成功、失败或取消 | 上述字段加 `success`、`duration_ms`、`error_category`（失败时） | P0 |

约束：

- `tool_key` 只能使用已登记的稳定目录键；用户自建 MCP 映射为 `mcp_custom`，其他用户自建或未知工具映射为 `custom`/`unknown`。
- MCP、CLI、Skill 和内置工具分别使用 `mcp`、`cli`、`skill`、`builtin`。
- 新版客户端同时上传经过本地规范化的 `tool_name`，服务端按同一字符集再次校验；只记录名称标识，不记录参数、返回值、服务器地址、路径、命令或输入输出内容。不合规名称回退为稳定 `tool_key`。
- 历史 `custom`/`mcp_custom` 事件已丢弃原名且不可恢复，仅新版客户端产生的事件开始展示真实规范化名称。
- 安装成功不代表采用；“工具采用”必须至少发生一次成功 `tool_call_completed`。

### 6.5 场景入口

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `scene_impression` | 场景入口实际可见；同一 `view_id` 内同场景仅一次 | `view_id`、`scene_l1`、`scene_l2`、`entry_point` | P1 |
| `scene_selected` | 用户选择场景 | `view_id`、`scene_l1`、`scene_l2`、`entry_point` | P1 |
| `scene_submitted` | 携带场景标识的输入被实际提交 | `scene_l1`、`scene_l2`、`session_id`、`attempt_id` | P1 |

场景事件先以 `attempt_id` 关联 `task_admitted`，再取得 `turn_id` 关联后续任务成功率、首输出耗时和反馈率；只比较“触发次数”不能判断场景价值。

### 6.6 模型选择与运行

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `model_selected` | 用户明确更改会话或默认模型 | `provider_key`、`model_key`、`selection_scope`、`entry_point` | P1 |
| `model_used` | 已接纳任务确定实际执行模型 | `session_id`、`attempt_id`、`turn_id`、`provider_key`、`model_key`、`selection_source` | P0 |
| `model_fallback_occurred` | 执行中切换到非最初模型 | `session_id`、`attempt_id`、`turn_id`、`from_model_key`、`to_model_key`、`error_category` | P1 |

`selection_source` 仅允许 `user_selected`、`session_default`、`app_default`、`system_routed`、`fallback`。模型排行必须同时展示任务成功率、耗时和选择来源，不能把默认配置偏差解释为用户偏好。自定义模型统一使用脱敏目录键，不上传服务地址或用户自定义别名。

### 6.7 知识、附件与成果

| `attachment_processing_completed` | 附件解析进入终态 | `attachment_id`、`operation_id`、`attempt_index`、`file_type_bucket`、`success`、`duration_ms`、`error_category`（失败时） | P1 |
| `knowledge_import_started` | 用户确认知识导入 | `operation_id`、`attempt_index`、`source_type`、`item_count_bucket` | P1 |
| `knowledge_import_completed` | 导入进入终态 | `operation_id`、`attempt_index`、`success`、`duration_ms`、`error_category`（失败时） | P1 |
| `knowledge_search_completed` | 一次知识检索完成 | `session_id`、`turn_id`、`operation_id`、`attempt_index`、`success`、`result_count_bucket`、`duration_ms` | P2 |
| `artifact_created` | 产生可预览的结构化成果并生成匿名成果 ID | `artifact_id`、`session_id`、`turn_id`、`artifact_type` | P1 |
| `artifact_exported` | 用户成功导出成果 | `artifact_id`、`session_id`、`turn_id`、`artifact_type`、`export_format` | P1 |

文件仅按受控类型和大小桶统计；不得上传文件名、路径、内容、知识条目标题或检索词。

### 6.8 重点工作模式

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `code_mode_opened` | 代码模式工作区实际可见；每个页面实例一次 | `view_id`、`session_id`、`entry_point`、`provider_key` | P1 |
| `scheduled_task_created` | 定时任务保存成功 | `scheduled_task_id`、`schedule_type`、`task_type` | P1 |
| `scheduled_task_run_finished` | 一次计划执行结束 | `scheduled_task_id`、`operation_id`、`attempt_index`、`status`、`duration_ms`、`error_category`（失败时） | P1 |
| `team_mode_opened` | 团队协作界面实际可见；每个页面实例一次 | `view_id`、`session_id`、`member_count_bucket`、`entry_point` | P1 |

`code_mode_opened` 和 `team_mode_opened` 只衡量功能发现，Code/团队的有效采用和质量统一由 `task_*` 事件的 `mode` 分组派生，不再维护语义含混的模式“开始/结束”事件。定时任务采用应至少成功执行一次，不能只看创建次数。

### 6.9 满意度与价值代理

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `response_feedback_changed` | 用户设置、修改或清除反馈；同一回合按最新状态计算 | `feedback_id`、`session_id`、`turn_id`、`feedback_action`、`rating`（设置时）、`reason_code`（可选） | P1 |
| `response_copied` | 助手输出已成功写入系统剪贴板 | `session_id`、`turn_id`、`content_type` | P1 |

`feedback_id` 对同一回合保持稳定；`feedback_action=set` 覆盖此前状态，`clear` 清除当前状态。重新生成统一使用 `task_retry_requested(retry_reason=manual_regenerate)`，不重复采集响应级事件。复制、导出和反馈只能作为价值代理信号，不单独证明任务成功。反馈原因必须使用受控枚举，不采集用户填写的自由文本。后续追问通过同一会话内相邻 `task_submitted` 的时间和关联关系派生，不重复采集 `followup_submitted`。

### 6.10 商业事件

以下事件只允许由账号、订阅或支付服务端依据真实业务状态产生，客户端可以产生页面浏览事件，但不得产生成功账务事件：

| 事件 | 权威生产方 | 核心属性 | 优先级 |
|---|---|---|---:|
| `plan_viewed` | 客户端/账号服务 | `account_subject_id`（登录时）、`plan_key`、`entry_point` | P2 |
| `trial_started` | 订阅服务 | `account_subject_id`、`plan_key`、`trial_days` | P2 |
| `checkout_started` | 订单服务 | `account_subject_id`、`order_subject_id`、`plan_key` | P2 |
| `payment_succeeded` | 支付回调/订单服务 | `account_subject_id`、`order_subject_id`、`plan_key`、`currency`、`amount_minor` | P2 |
| `payment_failed` | 支付回调/订单服务 | 上述字段加 `error_category` | P2 |
| `subscription_renewed` | 订阅服务 | `account_subject_id`、`subscription_subject_id`、`plan_key` | P2 |
| `subscription_cancelled` | 订阅服务 | 上述字段加 `cancel_reason_code` | P2 |
| `refund_completed` | 支付回调/订单服务 | `account_subject_id`、`order_subject_id`、`currency`、`amount_minor` | P2 |

金额使用最小货币单位整数；看板不得用随机数、固定倍率或客户端本地状态模拟收入、付费用户和续费数据。账号体系及商业服务未具备前，对应模块显示“暂无权威数据”，不得展示假数据。

### 6.11 受控实验

| 事件 | 触发时机 | 核心属性 | 优先级 |
|---|---|---|---:|
| `experiment_exposed` | 用户首次实际看到或进入实验处理，按实验与分配主体只记录一次 | `experiment_key`、`variant_key`、`assignment_unit`、`entry_point` | P2 |

实验分配不等于曝光。默认按 `device` 分流；只有账号关联已经单独授权且实验明确要求跨设备一致时才能按 `account` 分流。实验周期内不得改变分配单位，分组使用服务端带密钥的稳定散列保证粘性，客户端不能自行选择分组。分析默认采用实际曝光口径，同时保留由实验平台计算的意向处理口径；实验键和分组键必须来自登记表，禁止客户端任意拼接。实验结束后仍须保留口径、起止时间、适用版本和护栏指标记录。

## 7. 关键漏斗与分析看板

### 7.1 可观测 cohort 激活漏斗

主漏斗：

`analytics_cohort_started` → `task_environment_ready` → `task_submitted` → `task_admitted` → `task_first_output` → `task_finished(success)`

准备状态分支：

```text
analytics_cohort_started
├─ 内置模型可用 ───────────────────────────────┐
├─ 企业策略预配置 ─────────────────────────────┤
├─ 既有配置迁移成功 ───────────────────────────┤→ task_environment_ready
└─ onboarding_started → provider_setup_completed ┘
```

要求：

- 展示每步人数、转化率、中位耗时和主要失败分类；
- 支持按版本、平台、渠道、语言和首次模型供应商分组；
- 同一安装只取窗口内第一次到达每个节点；
- 引导和供应商配置是诊断分支，不是所有安装必须经过的主漏斗节点；
- 允许跳过引导的用户直接进入后续节点，不强制伪造缺失事件；
- cohort 分母仅包含产生 `analytics_cohort_started` 的安装，不外推为全部安装。

### 7.2 核心任务漏斗

```text
task_submitted(attempt_id)
├─ task_rejected(attempt_id)
└─ task_admitted(attempt_id, turn_id)
   ├─ task_first_output(attempt_id, turn_id)
   └─ task_finished(attempt_id, turn_id)
```

要求展示：提交量、唯一活跃安装数、接纳率、首输出率、成功率、取消率、失败分类、P50/P90 首输出耗时及总耗时。

### 7.3 工具采用漏斗

`tool_impression` → `tool_detail_opened` → `tool_install_started` → `tool_install_completed(success=true)` → `tool_configuration_started` → `tool_configuration_finished(success=true)` → `tool_call_completed(success=true)`

按 `tool_key`、`tool_name` 和 `tool_type` 分组展示，避免同名工具跨稳定分类或类型误合并；分别计算曝光到安装、安装到配置、配置成功率、配置到首个成功调用的转化与耗时；失败和用户取消必须单列。缺少 `tool_name` 的历史事件继续显示 `custom`/`mcp_custom` 等稳定键，不推断原名。

### 7.4 语音输入漏斗

`voice_entry_clicked` → `voice_permission_result(granted)` → `voice_started` → `voice_recognition_completed` → `voice_message_submitted(attempt_id)` → `task_finished(success)`

语音价值必须最终关联任务结果，单独的录音启动量只反映尝试意愿。

### 7.5 场景价值分析

`scene_impression` → `scene_selected` → `scene_submitted` → `task_finished` → 反馈/复制/导出

场景排行至少同时展示曝光、选择率、提交率、任务成功率、耗时和负向反馈率。

### 7.6 版本质量看板

- 新旧版本的任务接纳率、成功率、取消率；
- P50/P90 首输出和总耗时；
- 各错误分类占比；
- 埋点上报健康度；
- 按平台和架构分层，样本量不足时隐藏百分比或标记低可信度。

### 7.7 价值指标看板

- WSTA 与 WEVTA 同时展示，明确前者是技术成功、后者是可观测价值下界；
- 展示成功任务到正向反馈、复制和成果导出的 30 分钟关联转化；
- 反馈按每个 `feedback_id` 的最新状态计算，修改和清除不得重复计数；
- 计划任务和系统任务从 WSTA/WEVTA 排除，单独展示自动化任务价值；
- 不得把未产生价值信号的任务标记为失败或低质量。

## 8. 当前实现与目标事件映射

截至本文版本，主线已有以下行为事件。此表用于迁移，不代表目标口径已经满足。

| 当前事件 | 当前状态 | 目标处理 |
|---|---|---|
| `task_started` | 常规助手在引擎接纳后发送 | 迁移为 `task_admitted`；在提交入口生成 `attempt_id`，接纳事件同时关联 `turn_id`；补充提交和拒绝事件 |
| `task_finished` | 已覆盖正常终态和部分 forwarder 失败 | 保留名称，统一终态枚举、耗时和错误分类，检查所有模式仅发一次 |
| `voice_started` | 获得音频流并开始录音时发送 | 保留，补齐入口、权限、识别结果、提交和取消事件 |
| `scene_triggered` | 带场景的消息提交后发送 | 迁移为 `scene_submitted`，补齐曝光和选择事件，并关联提交入口生成的 `attempt_id` |
| `tool_install_completed` | 仅成功安装时发送 | 失败也必须发送同名结果事件，并补齐开始、配置和卸载事件 |
| `tool_call_completed` | 已有辅助函数，但主线未发现生产调用点 | 在统一工具执行出口接线；补齐开始事件、耗时和错误分类 |
| `model_used` | 常规助手接纳任务时发送 | 覆盖 Code/ACP 等所有执行模式，补齐选择来源、结果与回退事件 |

现有实现还存在以下迁移要求：

- 当前主线已形成客户端生产、持久化 outbox、逐事件确认、服务端校验/存储、聚合 API 和看板闭环；各任务的实际实现状态以《用户行为埋点实施任务》为准。
- `input_type` 已在普通、ACP、团队、语音、场景、编辑重发和重新生成入口统一计算，并由权威任务状态机绑定到同一 attempt。
- 目标事件事实使用鉴权上下文注入的服务端 `device_id` 作为匿名安装主体；本地 `installation_id` 和客户端声明的主体均不进入事实表。
- 当前行为事件已使用有界持久化 outbox，事件同步落盘成功后才唤醒容量为 1 的后台发送信号；发送失败保留并退避，逐事件确认后删除；“设置 → 帮助反馈 → 数据管理”二级页面向用户展示采集说明和状态并提供持久化启停入口，不提供用户删除入口。
- 前端命令只允许冻结 schema 中经批准的事件和字段；Rust 在本地持久化前再次执行字段白名单，禁止任意事件名或任意属性透传。
- 服务端事件白名单、校验、存储、统计 API、看板和隐私说明已形成同版本闭环；后续发布继续遵循“服务端→客户端→看板”顺序。
- 行为统计复用安装语义的设备注册与鉴权机制，但事件域、管理员删除控制面、聚合接口和权限仍与设备运营诊断分层。
- 旧事件视为 legacy schema，不补造缺失的 `attempt_id` 或其他字段，也不混入新口径漏斗；迁移日期必须在看板标注，兼容期结束后按变更治理流程下线。

## 9. 数据处理与存储要求

### 9.1 客户端

- 事件先写入有界持久化 outbox，再异步批量发送；业务流程不得等待远端上报。P0 本地持久化耗时纳入性能预算，写入失败只增加诊断计数，不得阻断任务和界面。
- outbox 最多保留 30 天、5,000 条或占用 64 MiB，任一上限达到时删除最旧事件并增加本地丢弃计数。
- 服务端逐事件返回 `accepted`、`duplicate`、`retryable` 或 `rejected` 后，客户端只删除前两类记录。
- outbox 每条记录绑定生成时的 `collection_period_id`。周期被服务端结束、权威删除或运维停采时清理对应未发送事件；服务端对失效或不匹配的周期返回 `rejected(reason_code=collection_inactive)`，防止旧数据补传。
- 网络错误采用指数退避和抖动；4xx schema 错误不得无限重试。
- 客户端时钟异常时仍上传；服务端根据 `occurred_at` 与 `received_at` 计算 `clock_skew_bucket`，报表可按接收时间兜底。
- 埋点模块故障不得影响核心业务；业务成功也不得被上报失败改写。
- 在项目定义的最低支持硬件上，业务线程的单次本地入队耗时目标为 P95 不超过 10 ms、P99 不超过 50 ms；遥测模块 5 分钟窗口平均 CPU 增量不超过 0.5%，常驻内存增量不超过 16 MiB。
- 单批上传不得超过 50 条或 400 KiB，任一上限先到即发送；请求超时不超过 12 秒，失败后转后台退避，不占用用户操作等待链路。

### 9.2 服务端

- 对事件名、schema 版本、属性类型、枚举、长度、批大小和时间范围做严格校验。
- 服务端注入可信 `received_at`、`device_id` 和生产方信息。
- 服务端只接受属于当前设备且状态为 active 的 `collection_period_id`；周期启动和结束控制接口需使用设备凭证、防重放随机数和幂等请求 ID。
- 客户端与服务端生产方使用独立事件白名单；客户端入口不得接受支付、续费、退款等仅允许服务端产生的事件。
- 明细事实表与聚合表分离；商业事实使用独立权威数据源。
- 原始行为事件和任何包含 `device_id`、`account_subject_id` 或可逆主体贡献的数据最多保留 35 天；更短的地区法规或企业策略优先。
- 13 个月历史只允许保存不可逆聚合：不含主体 ID 或可逆映射、每个维度单元至少 20 个主体，并抑制稀有维度组合。无法证明达到匿名化标准的聚合数据只能保留 35 天。
- 聚合前按北京自然日裁剪单主体贡献：活跃主体每个维度单元最多计 `1`；任务提交和终态分别最多计 `100`；工具调用最多计 `500`；其他计数类事件按事件名分别最多计 `100`。看板展示被裁剪主体占比，修改上限必须提升指标口径版本。
- 到期数据自动删除。管理员/合规删除流程使用受控凭证确认安装主体；可关联明细、令牌映射和待发送数据在受理后 7 个自然日内删除，客户端不提供删除入口。
- 已通过隐私评审的不可逆聚合不做单主体重算；在获得该结论前不得生成 35 天以上的聚合。备份中的可关联数据最长 35 天到期清除，恢复后必须重新执行删除墓碑。
- 支付、退款和订阅账务记录继续由权威财务系统按适用法规保留，不复制为长期行为明细；行为分析侧只保存经批准的商业聚合，本文的 35 天规则不得覆盖或缩短法定账务留存。
- 统计任务必须可重跑，指标 SQL/代码需版本化并有口径测试。

### 9.3 数据质量指标

以下指标属于遥测管道运维指标，不应通过同一条行为事件管道自我采集：

- 事件生成数、入队数、客户端丢弃数；
- 批次发送数、重试数、网络失败数；
- 服务端接受数、重复数、schema 拒绝数、限流数；
- 从 `occurred_at` 到 `received_at` 的延迟分布；
- `task_admitted` 无终态比例、重复终态比例；
- 成熟窗口内 `task_submitted` 既无 `task_rejected` 也无 `task_admitted` 的比例；
- 成功 `task_finished` 缺少或重复 `task_first_output` 的比例；
- 默认周期建立失败、权威删除阻断和运维停采的安装数量及持续时间；
- 各指标达到单主体贡献上限的主体占比；
- 开始事件无结果比例、结果事件无开始比例；
- 按版本的未知枚举和未知 schema 比例。

初始告警阈值：P0 事件服务端拒绝率连续 15 分钟超过 1%，或已接纳任务 24 小时后无终态比例超过 0.5% 时告警。阈值调整必须提升监控配置版本并记录依据。

### 9.4 上传与逐事件确认协议

上传身份从 HTTPS 鉴权上下文获取。请求正文不把客户端声明的 `device_id` 作为可信事实。以下示例只展示批次信封，省略事件业务字段：

```json
{
  "batch_id": "batch_test_001",
  "events": [
    {
      "schema_version": 1,
      "event_id": "beh_test_001",
      "event_name": "task_submitted",
      "collection_period_id": "period_test_001"
    }
  ]
}
```

服务端必须逐事件返回结果，不能只返回汇总数量：

```json
{
  "batch_id": "batch_test_001",
  "results": [
    {
      "event_id": "beh_test_001",
      "status": "accepted",
      "reason_code": null
    }
  ]
}
```

`status` 仅允许：

- `accepted`：已持久化，客户端删除对应 outbox 记录；
- `duplicate`：此前已持久化，客户端删除对应记录；
- `retryable`：暂未接收，客户端保留并退避重试；
- `rejected`：永久 schema 或策略错误，客户端停止重试、增加有界拒绝诊断计数并从 outbox 删除对应记录。

`reason_code` 使用受控枚举，例如 `unknown_event`、`unsupported_schema`、`invalid_field`、`too_large`、`too_old`、`invalid_time`、`collection_inactive`、`rate_limited`。一条事件无效不得连带拒绝同批有效事件。客户端仅在本地记录 `delivery_attempt_count` 和最后一次受控失败原因，不把网络重试次数写入业务事件。

### 9.5 Schema 兼容与发布顺序

1. 先发布能接受新 schema 的服务端，再发布产生新事件的客户端，最后发布依赖新口径的看板。
2. 同一 `schema_version` 内只允许向后兼容的可选字段扩展；新增必填字段或改变语义必须提升版本。
3. 服务端至少兼容当前正式客户端及前一个仍受支持版本的 schema。
4. 未知事件或不支持的 schema 按单条返回 `rejected`，不得导致整批失败；同版本出现未知属性视为契约错误，不静默进入事实表。
5. 看板在事件完整率达到发布门槛前标记“数据建设中”，不得把缺失解释为 0。
6. 回滚顺序与发布顺序相反；旧客户端重传的合法旧 schema 在兼容期内仍可入库。

## 10. 看板权限与展示规范

- 管理员总览默认展示聚合数据，不提供会话正文或逐事件浏览。
- 行为分析看板不提供单安装、单账号、单会话或逐事件明细；设备级诊断继续使用独立的设备运营系统和专门权限，不在行为看板中通过主体 ID 联查。
- 样本量小于 20 个安装实例时不展示细分分组；提高阈值可以直接执行，降低阈值必须重新进行隐私评审。
- 所有图表标注时区、统计周期、主体类型、指标定义和最后更新时间。
- 无数据、数据延迟和埋点未上线必须分别呈现，不能统一显示为 0。
- 事件或口径发布变更时，在图表上标注切换日期，避免跨版本误读。
- 导出权限单独控制，导出文件不包含可直接识别个人的信息。

## 11. 分阶段实施计划

### 阶段 A：可信核心闭环（P0）

1. 冻结公共 schema、主体口径和隐私清单。
2. 完成内测默认采集与持久化启停生命周期、持久化 outbox、服务端校验与幂等。
3. 打通激活与核心任务事件；普通助手、Code/ACP 和用户发起的团队任务必须同步覆盖。
4. 将工具调用完成事件接入统一执行出口。
5. 补齐工具安装失败、模型选择来源和任务状态机完整性。
6. 上线激活、任务、工具及管道健康看板。

阶段 A 完成标准：可以可信回答“多少可观测新 cohort 在 24 小时内完成首次技术成功任务、任务在哪一步失败、工具是否真正被成功调用”。阶段 A 使用 WSTA，不展示 WEVTA。

### 阶段 B：功能采用与价值代理（P1）

1. 覆盖语音、场景、知识、附件、成果和定时任务；Code/ACP 与团队任务在本阶段补充专属采用指标。
2. 上线反馈状态、任务重试、复制和导出等价值代理，并启用 WEVTA。
3. 建立 D1/D7/D30 cohort 留存和版本质量对比。
4. 建立场景、语音、工具的完整漏斗。

### 阶段 C：商业与实验（P2）

1. 账号与订单服务提供权威商业事件后再上线商业看板。
2. 建立受控实验登记、分流、曝光和结果分析机制。
3. 在满足样本量和隐私阈值的前提下开展转化与长期价值分析。

## 12. 验收标准

### 12.1 产品与数据验收

- 每个 P0 指标能追溯到事件、触发时机、分母、分子、时区和去重规则。
- 看板使用“安装实例”和“账号”的准确称谓，不混称“用户”。
- 激活、任务、工具和语音漏斗能用固定测试数据复算并得到一致结果。
- WSTA 只包含 `initiator_type=user` 的 `assistant`、`code` 和用户发起的 `team` 任务；计划任务和系统任务不能混入。
- WEVTA 只按同一 `turn_id` 在 30 分钟内关联到的最新反馈状态、复制或导出计算，并明确标记为可观测价值下界。
- `每活跃安装日任务数` 按任务总数除以活跃安装日总和计算。
- 商业模块在无权威数据时明确显示未接入，不出现模拟收入或随机数据。

### 12.2 客户端验收

- 每个 `attempt_id` 恰有一个 `task_submitted`，并且最终只进入 `task_rejected` 或 `task_admitted` 其中之一。
- 每个已接纳 `turn_id` 恰有一个 `task_admitted` 和一个 `task_finished`，拒绝任务不得发送 `task_finished`。
- 成功、失败、取消、提交拒绝、应用退出和引擎断连均有明确终态或可审计补偿逻辑。
- 每个语音 `operation_id` 只产生一个规定终态；权限拒绝、识别失败、识别后放弃和消息提交均有契约测试。
- 离线、弱网、重启、重复上传和队列满场景均有自动化测试。
- 服务端确认首个采集周期前不产生待上传事件；应用默认后台建档，离线或服务失败时有界退避且不阻塞业务。
- 首次默认启用、显式关闭/开启的跨重启恢复和运维停采均有控制面测试；新周期不能上传旧周期事件，首次 cohort 事件不得重复。
- 客户端及前端桥接在“设置 → 帮助反馈 → 数据管理”二级页面提供三语告知和用户启停入口，不在一级设置导航暴露，也不提供删除入口；管理员删除、7 日清除、权威删除阻断自动恢复和备份墓碑重放均经过验证。
- 自动化测试证明事件中不包含消息正文、文件路径、工具参数和原始错误。
- Web/Tauri/各操作系统不支持的能力返回明确状态，不伪造成功事件。
- 最低支持硬件上的自动化或可复现基准满足 9.1 的入队延迟、CPU、内存和磁盘预算。

### 12.3 服务端验收

- 相同 `event_id` 重复提交只计一次。
- 未知事件、未知属性、非法枚举、超长字段、过期时间和超大批次被安全拒绝。
- 每个事件的 accepted/duplicate/retryable/rejected 返回值与实际落库一致，单条无效事件不影响同批有效事件。
- 客户端声明的 `device_id` 不得覆盖鉴权上下文注入的主体，服务端商业事件不伪造客户端字段。
- 事件留存、删除请求、权限、限流和备份恢复经过验证。
- 13 个月聚合只有在隐私测试证明不含主体键、满足最小群体 20 和贡献裁剪后才能启用；否则自动限制为 35 天。
- 指标计算有覆盖零活跃日、跨日、乱序、重复、迟到、版本切换和时区边界的测试。

### 12.4 发布门禁

- 产品、数据、客户端、服务端、安全/隐私负责人完成事件清单评审。
- 文档、客户端 schema、服务端白名单、指标定义和看板版本一致。
- 服务端兼容能力先于客户端事件发布；看板后于事件完整性验证发布。
- 新版本先灰度验证事件量、拒绝率、完整率和业务性能，再逐步扩大。
- 埋点对任务延迟和资源占用的影响达到 9.1 预算；发送逻辑不得增加远端网络等待，常驻磁盘占用不得超过已设上限。
- 回滚埋点服务或使用运维级停采配置不会影响任务、工具、语音等核心功能。

## 14. 变更治理

- 事件新增或修改必须同步更新本文、schema、客户端/服务端契约测试和指标字典。
- 事件负责人需要在发布前给出预期日量、用途、保留周期和下线条件。
- 连续两个正式版本无人消费且不影响法务、安全或账务的事件，应进入下线评审。
- 废弃事件至少保留一个正式版本兼容期，并在看板标注停止采集日期。
- 任何扩大采集范围、延长保留周期或关联账号身份的变更，必须重新进行隐私评审。

## 15. 已确定内测策略与后续外部条件

1. **采集默认值**：当前内测构建复用随安装包发布的公开遥测注册配置，在服务端可用且用户未显式关闭时默认开启匿名行为采集；“设置 → 帮助反馈 → 数据管理”二级页面提供三语说明和持久化启停开关，用户可随时关闭或重新开启；构建/运维级紧急停采能力继续保留。
2. **保留周期**：可关联数据最多 35 天；只有经隐私评审确认不可逆、满足最小群体和贡献裁剪要求的聚合数据才能保留 13 个月。
3. **账号关联**：内测阶段保持关闭；P2 若需启用，必须单独完成产品、法务/隐私和安全评审，且客户端不能自行上传账号标识。
4. **删除目标**：客户端不提供删除能力；管理员/合规删除受理后 7 个自然日内清除在线数据和主体映射，结果 30 天内可查询，备份最长 35 天到期并应用删除墓碑。
5. **性能预算**：使用 9.1 的入队延迟、CPU、内存、磁盘、批次和超时上限；任何放宽必须经过性能与隐私共同评审。
6. **目录治理**：产品负责人维护场景、工具、模型和实验键注册表；开发 Issue 必须指定具体负责人和目标版本，未指定不得开工。
7. **商业能力**：账号、订单和支付权威生产方、币种、退款及对账口径未通过专项评审前，商业模块保持禁用并显示“暂无权威数据”。

上述安全默认值可以被更严格的法规、企业策略或安全要求收紧，不能被单个功能开发者自行放宽。
