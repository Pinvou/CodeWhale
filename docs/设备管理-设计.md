# MegaCube 设备管理（设备管理）设计

状态：实现规范（本文档是各实现波次的契约）。留档 2026-10-09，第七轮评审修订 2026-10-16，第八/九轮评审修订 2026-10-21，第二十二轮评审修订 2026-10-24。

## 0. 背景与目标

- 现有「运行状态」（`features/monitor` + `MonitorView.jsx`）保留在所有非 MegaCube 平台，行为不变。
- 在 MegaCube 设备（本机：DMI `product_name = "LinSeer MegaCube"`，NVIDIA GB10，aarch64 Linux）上，导航原「运行状态」入口替换为「设备管理」：
  1. 更细的设备监控：传感器（温度/风扇/电压）、磁盘用量、网络流量、进程占用、GPU 扩展信息（驱动/CUDA/计算进程）、模型服务状态。
  2. AI 故障排查：快捷按钮 + 自定义提问，每个动作新建一个**普通新会话**（与用户手点「新对话」完全一致，默认模型），自动发送精心撰写的提示词模板，并跳转到聊天页。模板只读诊断优先、破坏性操作必须先征询。
  3. 模型管理：列出本机全部模型。**模型商店管理的模型一律禁用安装/移除**（显示"由模型商店管理" + 前往模型商店按钮）；商店之外的模型通过 AI 会话安装（由模型根据网络环境如大陆镜像/模型上架位置自行决定机制），移除走确定性后端命令（防误删）。

### 2.2 数据契约（serde 默认 snake_case；命令返回全部 `Result<T, String>`）

```rust
pub struct DeviceSnapshot {
    pub generated_at_ms: u64,
    pub os: OsInfo,
    pub sensors: Vec<SensorGroup>,        // 空则前端显示空态
    pub disks: Vec<DiskSnapshot>,
    pub network: Vec<NetIfaceSnapshot>,   // 含本次与上次采样间的速率
    pub processes: ProcessSummary,
    pub gpu_ext: Option<GpuExtSnapshot>,  // 无 NVIDIA 时 None
}
pub struct OsInfo { pub product_name: Option<String>, pub pretty_name: Option<String>, pub kernel: String, pub arch: String }
pub struct SensorGroup { pub chip: String, pub entries: Vec<SensorEntry> }
pub struct SensorEntry { pub kind: String /* temperature|fan|voltage|current|power */, pub name: String, pub value: f64 /* 归一化：°C/RPM/V/A/W */, pub critical: Option<f64>, pub max: Option<f64> }
pub struct DiskSnapshot { pub name: Option<String>, pub mount_point: String, pub fs_type: String, pub kind: String /* ssd|hdd|unknown */, pub total_bytes: u64, pub available_bytes: u64, pub is_removable: bool }
pub struct NetIfaceSnapshot { pub name: String, pub iface_type: String /* ethernet|wifi|loopback|bridge|virtual|other */, pub is_up: bool, pub mac: Option<String>, pub rx_bytes: u64, pub tx_bytes: u64, pub rx_bytes_per_sec: f64, pub tx_bytes_per_sec: f64 }
pub struct ProcessSummary { pub top_cpu: Vec<ProcInfo>, pub top_memory: Vec<ProcInfo> }   // 各取前 8
pub struct ProcInfo { pub pid: u32, pub name: String, pub cpu_pct: f32, pub memory_bytes: u64 }
pub struct GpuExtSnapshot { pub driver_version: Option<String>, pub cuda_version: Option<String>, pub compute_processes: Option<Vec<GpuProcInfo>> }   // None = nvidia-smi 查询失败/不可知（十六轮评审：与"真的零进程"区分，前端显式提示"查询暂不可用"）
pub struct GpuProcInfo { pub pid: u32, pub name: String, pub used_mib: u64 }
```

采样实现要点：
- 温度：sysinfo `Components`（Linux 即 hwmon 温度）；风扇/电压/电流：linux.rs 直接遍历 `/sys/class/hwmon/hwmon*/`（`fanN_input` RPM、`inN_input` mV→V、`currN_input` mA→A、`powerN_input` µW→W，label 取 `*_label` 否则 `chip + 通道号`）。温度阈值映射（第八/九轮评审修订）：critical ← `tempN_crit`；max ← `tempN_highest` 历史峰值（无 highest 的芯片回退为当前读数；sysinfo 0.36 提供不了 `tempN_max`——上游已注释掉该输入，`Component::max()` 给的是内核记录的自启动历史峰值，实现只保留严格高于当前读数的峰值 `component_peak_above_current`，前端以独立 peakLabel 展示、不冒充临界阈值）。chip 名取 hwmon `name`。
- 磁盘：sysinfo `Disks`；过滤 `squashfs`、`overlay`（容器叠层，每容器一份假磁盘）、挂载点前缀 `/snap/`、`/boot/efi` 保留但排后；`kind` 用 `DiskKind`。传感器/磁盘/网络/进程输出一律确定性排序（sysinfo Components 在 Linux 由 HashMap 聚合、迭代序逐拍漂移，不排序会击穿 bridge 显示等价抑制）。
- 网络：sysinfo `Networks`（跨刷新保留状态，`received()/transmitted()` 为增量 → 除以采样间隔秒数得速率；首次采样速率记 0）；类型判断：`lo`→loopback，有 `wireless` 子目录→wifi，`br-`/`docker`/`veth`/`virbr` 前缀→bridge/virtual，`enp`/`eth`/`enx`→ethernet，`wl`→wifi，`tun`/`tap`/`wg`→other(vpn 归 other)，其余 other；`is_up` 用 operstate（linux.rs 读 operstate，**down 家族**（down/lowerLayerDown/notPresent/dormant）判断开，`unknown` 不算 down——回环/VPN 口恒为 unknown；读不到默认 true）。
- 进程：sysinfo `System`（**持久实例放 `DeviceState`**，两次刷新间算 CPU%；`refresh_processes_specifics` 只刷 cpu+memory，系统级 `refresh_memory` 不调用——内存页由内嵌 MonitorView 负责）；按 cpu_pct / memory 排序各取 8，`name` 截断 40 字符。
- GPU 扩展：一次裸跑 `nvidia-smi` 同时解析表头的 `Driver Version:`/`CUDA Version:`（驱动查询+CUDA 兜底两次调用会让挂死场景的最坏预算翻倍），`/proc/driver/nvidia/version` 兜底驱动；CUDA 版本优先 `/usr/local/cuda*/version.json` 的 `cuda.version`（多版本按 (major,minor) **数值**序取最新），version.json 缺失/不可解析时回退表头解析；计算进程 `nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv,noheader,nounits`。
- 服务探测独立命令（不进 2s 快照）。

服务探测：ollama → `GET {127.0.0.1:11434}/api/tags`（1.5s 超时，`reqwest`）；vllm → `127.0.0.1:8000/8001/8002 /v1/models` 任一 200；lmstudio → `127.0.0.1:1234 /v1/models`；docker → `HiddenCommand` `docker info --format {{.ServerVersion}}`（候选路径列表见 `platform::os::docker_candidates`，timeout 3s，失败即 not running）。`running=false` 时 `detail` 给一句中文人话原因，`reason` 给稳定机器码（`timeout`/`connection_refused`/`network_error`/`client_init_failed`/`http_status`/`not_detected`/`docker_exit`/`docker_unavailable`/`docker_task_failed`，`code` 携带 HTTP 状态或退出码）——前端按机器码映射三语 tooltip，中文 detail 只进 doctor 上下文（二十一轮）。GPU 探测复用 monitor 的 `GPU_PROBE_TIMEOUT = 10s`/候选（最坏 2 次调用 × 3 候选 ≈ 60s，nvidia-smi 挂死时排查卡等待预算一并拉长；带 3s TTL 缓存 `gpu_ext_cached`、try_lock 不排队——与 monitor 侧缓存并存属已披露的后续架构项，代码注释声明）；外部模型 Ollama 删除 `DELETE /api/delete` 预算 30s（§4）。

  ```js
  const openDeviceDoctorChat = useCallback(async (prompt) => {
    if (!bridge.available || !prompt) return false;
    if (!bridge.chat?.sendMessageToSession) return false;
    try {
      // 失败重试复用同一已物化会话（round-21），复用前按当前会话列表校验
      // 仍存在——用户删掉该会话则清 ref 重新物化（round-22，防死 sid 循环）。
      let reused = lastFailedDoctorSidRef.current;
      if (reused && !(bsRef.current?.sessions || []).some(s => String(s.id) === reused)) {
        lastFailedDoctorSidRef.current = null; reused = null;
      }
      const sid = reused || (await bridge.sessions.materializeSession());
      lastFailedDoctorSidRef.current = null;
      if (!sid) return false;
      const sent = await runBrowserUiTransition(async ({ isCurrent }) => {
        if (!isCurrent()) return false;
        // 先发送再跳转：发送失败时用户还留在设备管理页，toast 才有着落。
        // 会话钉定投递（第七轮评审）：transition 在 serialize 通道排队，
        // sendMessage 按"当前活动会话"投递会被先入队的 switchToSession 切走。
        const result = await bridge.chat.sendMessageToSession(sid, prompt);
        if (!result?.accepted) return false;
        if (result.completion && !(await result.completion)?.ok) return false;
        // 落定后复查只门视图切换（第九轮评审）：不把已离开设备页的用户拽进
        // 聊天；此时消息已真实送达，返回值仍按已送达报 true。
        if (isCurrent()) {
          setCodeModeOn(false); closeMobileSidebar();
          setCurrentView('chat'); setActiveChat(sid);
        }
        return true;
      }, { channel: 'session', hideMode: 'workspace', serialize: true, sessionTarget: sid, sessionBaseline: null });
      return sent === true;
    } catch (error) {
      // 失败记住已物化的会话 sid 供重试复用（发送成功后清空）；死 sid 已在
      // 入口被存在性复查拦下（round-22）。
      if (usedSid) lastFailedDoctorSidRef.current = usedSid;
      console.warn('[device-manager] doctor chat failed', error);
      return false;
    }
  }, [...]);
  ```

## 4. 外部模型（安装/移除）

- 注册表目录：`~/.pinvou3/device/external-models.d/*.json`，上限 256 条文件（读写两侧同限）、单条记录 64KB（二十一轮补记数值边界），schema：
  ```json
  { "schema": 1, "id": "m-ab12cd34", "name": "qwen3-30b", "kind": "ollama|openai_endpoint|llamacpp|vllm|other",
    "base_url": "http://127.0.0.1:11434/v1", "model": "qwen3:30b",
    "weights_path": null, "installed_at": "RFC3339", "note": "" }
  ```

  `weights_path` **一律填 null**（与 doctor.rs 安装模板一致）：Ollama 等运行时自管
  存储的模型由运行时删除，登记端不替它记路径；只有用户自管权重目录的类别
  （llamacpp 等）才填绝对路径，且自建目录须在家目录第三层或更深——1-2 层深的
  目录会被移除守卫 3 拒绝删除。
- `get_external_models()`：解析注册表（坏文件跳过并进 warnings）+ 探测 Ollama `/api/tags`（reachable 时列出全部 ollama 模型，去重已注册者标 `registered:true`——去重按**有效身份**匹配：显式 `model` 优先、缺失才回退展示 `name`，与 status 探测同一把尺子，展示名命中会把 daemon 真实存在的另一个模型当重复行隐藏；身份归一只把**缺省 tag** 补 `:latest` 并大小写折叠，**显式 tag 原样保留**——`qwen3:8b` 与 `qwen3:30b` 是两个模型，另一个 tag 不得被去重隐藏，未安装的显式 tag 也不得冒充 available；商店边界的去 tag 兜底是防误删口径，不用于身份判断）。（`/api/tags` 响应 1MB 上限、条目 1024 上限，超限截断，round-22 补记）返回 `{ models: Vec<ExternalModel>, warnings: Vec<String> }`；`ExternalModel { id, name, kind, base_url, model, weights_path, status /* 由可达性探测：available|unreachable */, registered: bool, source: registry|ollama }`。

- `device_remove_external_model(id, delete_weights, confirm_name)` 守卫链（顺序执行，任何一条不过返回人话 Err）：
  1. 确认名一致（双侧 trim 后比较；移除按 `<id>.json` 直取记录，文件名与 id 不一致的存量记录有界扫描按内容 id 兜底命中）。

## 5. 故障排查提示词（`device_doctor_prompt`）

  2. **沟通要求**：中文；结论先行；避免术语（必须用时括号给白话解释）；每步说明"我在查什么、为什么"；结尾给"下一步建议"（区分"无害可放心"与"需要你确认"）。
  3. **安全规则（硬约束）**：本轮以只读诊断为主；任何安装/删除/升级/写文件/杀进程操作，必须先解释影响并征得用户明确同意；禁止 `rm -rf` 带通配符或模糊路径；禁止触碰 `~/.pinvou3/`（应用自身数据目录；**唯一例外**：装模型流程第 6 步经用户同意后写入 `~/.pinvou3/device/external-models.d/` 注册表文件）、系统目录（/etc /usr /boot /var/lib）、磁盘分区；`apt` 只做查询（`apt list --upgradable` 等），除非用户明确要求升级且同意后也优先 `apt upgrade`，禁止 `dist-upgrade`；需要 sudo 时先解释为什么；下载前先查磁盘剩余空间；探测网络用短超时。
  4. **设备上下文**：注入实时 JSON（os/内核/架构、CPU/内存/swap、每磁盘总量可用、GPU 名/温度/显存/驱动/CUDA、当前活动模型与健康、ollama 等服务可达性、传感器摘要）。由后端采样组装（`get_device_snapshot` + `features::monitor` 复用），保证模型不瞎猜。上下文按**逐字段白名单**拼装（`app/commands/device.rs` 的类型化投影）：快照结构体新增字段不显式挑明不外发；MAC 地址在白名单外（结构性剔除），家目录前缀与 `/media/<用户名>/`、`/run/media/<用户名>/` 段经脱敏层改写，反引号清洗防 JSON 围栏破坏。
  5. **本次任务清单**（per kind 检查项，例）：
     - `packages`：`apt list --upgradable`、`snap refresh --list`；逐类解释；**不执行升级**。
     - `dependencies`：`pip3 check`、`dpkg --audit`、`apt-get check`（dry-run 语义）、python 多版本冲突线索。
     - `cuda`：`nvidia-smi`、驱动版本 vs `/usr/local/cuda*/version.json`、`nvcc --version`、`ldconfig -p | grep -i cuda` 关键库、（若有 python+torch）`torch.cuda.is_available()`。
     - `services`：ollama/vllm/LM Studio 端口探测、docker 容器里商店模型运行态、当前活动模型端点健康。
     - `hogs`：`ps` 排序（RSS/CPU）top、`du` 限深扫家目录（排除 /proc /sys /dev）、`journalctl --disk-usage`、snap 旧版本、`docker system df`；**只分析给清理建议，不删除**。
     - `install_model`：完整引导流程（见 6）。
     - `custom`：清单替换为"按安全规则自由诊断用户问题"。
  6. **输出契约**：排查类以 Markdown 小节给出【结论】【证据（命令+关键输出）】【建议】；不得虚构命令输出。

## 6. `install_model` 引导模板要点（AI 决定机制）

1. 若用户没说要装什么：一次只问一个问题（想要什么模型/干什么用/多大体量可接受）。
2. 环境盘点（只读）：已有哪些运行时（ollama / llama.cpp / vllm / docker / LM Studio）；磁盘剩余；显存/统一内存规模。
3. 网络探测（短超时，只读）：`hf.co`、`hf-mirror.com`、`modelscope.cn`、ollama registry 可达性 → **由此自行决定下载源**（大陆网络优先 hf-mirror/ModelScope）。
4. 方案与确认：给出推荐（运行时+模型+来源+预计体积），**经用户确认后**再动手；方案必须避开模型商店已提供的同款（提示去商店）。
5. 执行约束：优先用户级安装（不 sudo 装系统包，除非确认）；下载断点续传；校验和（如可得）；不删除/不覆盖任何既有模型与数据。
6. 收尾：启动服务→探测端点→（此步是安全规则中「禁触 `~/.pinvou3/`」的**唯一豁免**）**写注册表文件** `~/.pinvou3/device/external-models.d/<id>.json`（**文件名必须等于 `<id>.json`**——移除按内容 id 直取文件；文件名对不上时只能靠有界兜底扫描找回，注册表目录超上限时会漏；写文件命令只允许 `mkdir -p`、`cat >`、`chmod 600` 三步）→ 引导用户回设备管理页点"刷新"，用"接入品悟"加入对话。
