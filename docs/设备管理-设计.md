# MegaCube 设备管理（设备管理）设计

状态：实现规范（本文档是各实现波次的契约）。分支 `feat/megacube-device-manager`。

## 0. 背景与目标

- 现有「运行状态」（`features/monitor` + `MonitorView.jsx`）保留在所有非 MegaCube 平台，行为不变。
- 在 MegaCube 设备（本机：DMI `product_name = "LinSeer MegaCube"`，NVIDIA GB10，aarch64 Linux）上，导航原「运行状态」入口替换为「设备管理」：
  1. 更细的设备监控：传感器（温度/风扇/电压）、磁盘用量、网络流量、进程占用、GPU 扩展信息（驱动/CUDA/计算进程）、模型服务状态。
  2. AI 故障排查：快捷按钮 + 自定义提问，每个动作新建一个**普通新会话**（与用户手点「新对话」完全一致，默认模型），自动发送精心撰写的提示词模板，并跳转到聊天页。模板只读诊断优先、破坏性操作必须先征询。
  3. 模型管理：列出本机全部模型。**模型商店管理的模型一律禁用安装/移除**（显示"由模型商店管理" + 前往模型商店按钮）；商店之外的模型通过 AI 会话安装（由模型根据网络环境如大陆镜像/模型上架位置自行决定机制），移除走确定性后端命令（防误删）。

### 2.2 数据契约（serde 默认 snake_case；命令返回全部 `Result<T, String>`）

```rust
pub struct DeviceSnapshot {
    pub generated_at_ms: u64,
    pub os: OsInfo,
    pub sensors: Vec<SensorGroup>,        // 空则前端显示空态
    pub disks: Vec<DiskSnapshot>,
    pub network: Vec<NetIfaceSnapshot>,   // 含本次与上次采样间的速率
    pub processes: ProcessSummary,
    pub gpu_ext: Option<GpuExtSnapshot>,  // 无 NVIDIA 时 None
}
pub struct OsInfo { pub product_name: Option<String>, pub pretty_name: Option<String>, pub kernel: String, pub arch: String }
pub struct SensorGroup { pub chip: String, pub entries: Vec<SensorEntry> }
pub struct SensorEntry { pub kind: String /* temperature|fan|voltage|current|power */, pub name: String, pub value: f64 /* 归一化：°C/RPM/V/A/W */, pub critical: Option<f64>, pub max: Option<f64> }
pub struct DiskSnapshot { pub name: Option<String>, pub mount_point: String, pub fs_type: String, pub kind: String /* ssd|hdd|unknown */, pub total_bytes: u64, pub available_bytes: u64, pub is_removable: bool }
pub struct NetIfaceSnapshot { pub name: String, pub iface_type: String /* ethernet|wifi|loopback|bridge|virtual|other */, pub is_up: bool, pub mac: Option<String>, pub rx_bytes: u64, pub tx_bytes: u64, pub rx_rate_bps: f64, pub tx_rate_bps: f64 }
pub struct ProcessSummary { pub top_cpu: Vec<ProcInfo>, pub top_memory: Vec<ProcInfo> }   // 各取前 8
pub struct ProcInfo { pub pid: u32, pub name: String, pub cpu_pct: f32, pub memory_bytes: u64 }
pub struct GpuExtSnapshot { pub driver_version: Option<String>, pub cuda_version: Option<String>, pub compute_processes: Vec<GpuProcInfo> }
pub struct GpuProcInfo { pub pid: u32, pub name: String, pub used_mib: u64 }
```

采样实现要点：
- 温度：sysinfo `Components`（Linux 即 hwmon 温度）；风扇/电压/电流：linux.rs 直接遍历 `/sys/class/hwmon/hwmon*/`（`fanN_input` RPM、`inN_input` mV→V、`currN_input` mA→A、`powerN_input` µW→W，label 取 `*_label` 否则 `chip + 通道号`，`tempN_crit/max` 映射 critical/max）。chip 名取 hwmon `name`。
- 磁盘：sysinfo `Disks`；过滤 `squashfs`、挂载点前缀 `/snap/`、`/boot/efi` 保留但排后；`kind` 用 `DiskKind`。
- 网络：sysinfo `Networks`（跨刷新保留状态，`received()/transmitted()` 为增量 → 除以采样间隔秒数得速率；首次采样速率记 0）；类型判断：`lo`→loopback，有 `wireless` 子目录→wifi，`br-`/`docker`/`veth`/`virbr` 前缀→bridge/virtual，`enp`/`eth`/`enx`→ethernet，`wl`→wifi，`tun`/`tap`/`wg`→other(vpn 归 other)，其余 other；`is_up` 用 operstate（linux.rs 读 `/sys/class/net/<i>/operstate == "up"`，sysinfo 无此信息时默认 true）。
- 进程：sysinfo `System`（**持久实例放 `DeviceState`**，两次刷新间算 CPU%；`refresh_processes` + `refresh_memory`）；按 cpu_pct / memory 排序各取 8，`name` 截断 40 字符。
- GPU 扩展：`nvidia-smi --query-gpu=driver_version --format=csv,noheader` + `/proc/driver/nvidia/version` 兜底；CUDA 版本优先 `/usr/local/cuda*/version.json` 的 `cuda.version`（取字典序最大的版本目录），失败再 `nvidia-smi` 表头解析；计算进程 `nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv,noheader,nounits`。
- 服务探测独立命令（不进 2s 快照）。

## 4. 外部模型（安装/移除）

- 注册表目录：`~/.pinvou3/device/external-models.d/*.json`，schema：
  ```json
  { "schema": 1, "id": "m-ab12cd34", "name": "qwen3-30b", "kind": "ollama|openai_endpoint|llamacpp|vllm|other",
    "base_url": "http://127.0.0.1:11434/v1", "model": "qwen3:30b",
    "weights_path": null, "installed_at": "RFC3339", "note": "" }
  ```
  `weights_path` **一律填 null**（与 doctor.rs 安装模板一致）：Ollama 等运行时自管
  存储的模型由运行时删除，登记端不替它记路径；只有用户自管权重目录的类别
  （llamacpp 等）才填绝对路径。示例里那种 2 层深的路径即使登记了也会被移除
  守卫 3（HOME 内 ≥3 层）拒绝删除。
- `get_external_models()`：解析注册表（坏文件跳过并进 warnings）+ 探测 Ollama `/api/tags`（reachable 时列出全部 ollama 模型，去重已注册者标 `registered:true`）。返回 `{ models: Vec<ExternalModel>, warnings: Vec<String> }`；`ExternalModel { id, name, kind, base_url, model, weights_path, status /* 由可达性探测：available|unreachable */, registered: bool, source: registry|ollama }`。
- `device_register_external_model`：校验 name 非空、URL 可解析且 http(s)；**拒绝** name 与模型商店 `get_store_model_by_name` 冲突（防把商店模型登记成外部）。写文件返回记录。
- `device_remove_external_model(id, delete_weights, confirm_name)` 守卫链（顺序执行，任何一条不过返回人话 Err）：
  1. `confirm_name == record.name`（防误删）。
  2. 商店边界：name 命中 `get_store_model_by_name` → Err"该模型由模型商店管理，请在模型商店中操作"；weights_path 位于**任一**商店权重根（`store_weights_roots()`：store 数据根 `~/.pinvou3/model-store/` + 设置里自定义的 `models_dir`）之下 → 同上。登记端对 weights_path 做同款路径检查。守卫 1/2 的纯逻辑抽成 `removal_boundary_error`（商店名单与权重根判断以闭包注入），测试矩阵直打。
  3. weights_path 删除守卫：必须绝对路径、必须在 `$HOME` 之下、路径深度 ≥ 3、目录存在、不得是 `$HOME` 本身；命中即 `fs::remove_dir_all` 仅该目录。
  4. `kind == "ollama"` → `DELETE {ollama_host}/api/delete {"name": model}`（失败收集 warning 不阻断注册表清理）。
  5. 删注册表文件；返回 `RemoveOutcome { removed_registry: bool, removed_weights: bool, ollama_deleted: bool, warnings: Vec<String> }`。
- 商店模型的"移除/安装"从前端即禁用；后端两条命令再各自守卫（纵深防御）。

## 5. 故障排查提示词（`device_doctor_prompt`）

- 模板常量在 `features/device/doctor.rs`（仿 `features/scheduled/tasks.rs` 的 `SCHEDULED_TASK_CHAT_PROMPT`），`kind ∈ {packages, dependencies, cuda, services, hogs, install_model, custom}`，未知 kind → Err；`custom` 必须带 `question`（trim 非空，≤2000 字符）。
- 组装结构（全中文，面向零基础用户）：
  1. **角色**：MegaCube 一体机的设备管家，服务对象是不懂 Linux/AI 的小白。
  2. **沟通要求**：中文；结论先行；避免术语（必须用时括号给白话解释）；每步说明"我在查什么、为什么"；结尾给"下一步建议"（区分"无害可放心"与"需要你确认"）。
  3. **安全规则（硬约束）**：本轮以只读诊断为主；任何安装/删除/升级/写文件/杀进程操作，必须先解释影响并征得用户明确同意；禁止 `rm -rf` 带通配符或模糊路径；禁止触碰 `~/.pinvou3/model-store/`、系统目录（/etc /usr /boot /var/lib）、磁盘分区；`apt` 只做查询（`apt list --upgradable` 等），除非用户明确要求升级且同意后也优先 `apt upgrade` 而非 `dist-upgrade`；需要 sudo 时先解释为什么；下载前先查磁盘剩余空间；探测网络用短超时。
  4. **设备上下文**：注入实时 JSON（os/内核/架构、CPU/内存/swap、每磁盘总量可用、GPU 名/温度/显存/驱动/CUDA、当前活动模型与健康、ollama 等服务可达性、传感器摘要）。由后端采样组装（`get_device_snapshot` + `features::monitor` 复用），保证模型不瞎猜。
  5. **本次任务清单**（per kind 检查项，例）：
     - `packages`：`apt list --upgradable`、`snap refresh --list`；逐类解释；**不执行升级**。
     - `dependencies`：`pip3 check`、`dpkg --audit`、`apt-get check`（dry-run 语义）、python 多版本冲突线索。
     - `cuda`：`nvidia-smi`、驱动版本 vs `/usr/local/cuda*/version.json`、`nvcc --version`、`ldconfig -p | grep -i cuda` 关键库、（若有 python+torch）`torch.cuda.is_available()`。
     - `services`：ollama/vllm/LM Studio 端口探测、docker 容器里商店模型运行态、当前活动模型端点健康。
     - `hogs`：`ps` 排序（RSS/CPU）top、`du` 限深扫家目录（排除 /proc /sys /dev）、`journalctl --disk-usage`、snap 旧版本、`docker system df`；**只分析给清理建议，不删除**。
     - `install_model`：完整引导流程（见 6）。
     - `custom`：清单替换为"按安全规则自由诊断用户问题"。
  6. **输出契约**：排查类以 Markdown 小节给出【结论】【证据（命令+关键输出）】【建议】；不得虚构命令输出。

## 6. `install_model` 引导模板要点（AI 决定机制）

1. 若用户没说要装什么：一次只问一个问题（想要什么模型/干什么用/多大体量可接受）。
2. 环境盘点（只读）：已有哪些运行时（ollama / llama.cpp / vllm / docker / LM Studio）；磁盘剩余；显存/统一内存规模。
3. 网络探测（短超时，只读）：`hf.co`、`hf-mirror.com`、`modelscope.cn`、ollama registry 可达性 → **由此自行决定下载源**（大陆网络优先 hf-mirror/ModelScope）。
4. 方案与确认：给出推荐（运行时+模型+来源+预计体积），**经用户确认后**再动手；方案必须避开模型商店已提供的同款（提示去商店）。
5. 执行约束：优先用户级安装（不 sudo 装系统包，除非确认）；下载断点续传；校验和（如可得）；不删除/不覆盖任何既有模型与数据。
6. 收尾：启动服务→探测端点→**写注册表文件** `~/.pinvou3/device/external-models.d/<slug>.json`（给出精确 schema 与一条可复制的写文件命令）→ 引导用户回设备管理页点"刷新"，用"接入品悟"加入对话。
