# 实时留存技术隐私影响评估

记录日期：2026-10-21。范围：PR #2014 的首次成功日起算实时 D1/D7/D30 与持久最小留存依据；指标版本 `behavior-v1.5`。方法：按实际服务端接收、派生、保存、聚合、停采、删除和离线恢复代码逐项核对。本记录是工程技术评估，不是法律意见、人工签字或发布批准；尚未执行生产部署/历史回算。独立代码审核与实际验证结果应随该 PR 记录，不能以本文代替执行结果。

## 触发原因与目的

需求文档第 14 节规定“任何扩大采集范围、延长保留周期或关联账号身份的变更，必须重新进行隐私评审”。本次虽未新增客户端采集字段或账号关联，但把可关联安装的最小留存事实从原始事件最多 35 天的窗口独立出来，保留至主体删除，明确触发保留周期延长评审。

目的仅为避免原始事件按年龄/容量清理后，已发生的 D1/D7/D30 留存和分母消失。统计以安装实例为主体，不等同自然人或账号；随机安装标识仍能关联该安装，不应称为不可逆匿名数据。

## 数据流与最小化核对

| 环节 | 本次实现及边界 | 可核对代码 |
|---|---|---|
| 输入 | 复用已认证安装及有效采集周期的行为事件；仅派生 `initiator_type=user`、`mode=assistant/code/team`、`task_finished(status=success)`。不新增正文、路径、模型、工具或账号字段 | `telemetry-service.js` 的 `appendBehaviorEvents`；`telemetry-primitives.js` 的 `isSuccessfulCoreUserTask` |
| 派生 | 安装须在当前设备清单内且为 `installation_id`；身份字段矛盾、无效日期、`day < 1`、尚未发生的未来事件不形成留存。只保存北京自然日，不保存成功的精确时刻 | `retention-store.js` 的 `observe` |
| 单安装存储 | `device_id`、`first_success_day`、`successful_days`、`history_complete`；最多首次成功日起 31 个成功日期，后续日期不扩大集合。支持乱序与更早成功重锚 | `retention-facts.json` 的行结构及加载校验 |
| 全局元数据 | 格式版本、`initialized_at`、`metric_version_started_at` 与独立初始化标记；不含单安装任务内容。两种时间分别用于历史完整性和本版首次成功启用记录，不能互换 | `RetentionFacts` 构造/保存与 overview 元数据 |
| 输出 | 行为概览仅返回 D1/D7/D30 聚合数量、比例和完整性信息；不足 30 个合格安装不显示留存率，分子/分母仍展示。API 不导出留存行或主体标识，不开放新的单安装联查或导出 | `RetentionFacts.metrics`、`behaviorOverview`、`web/stats.html` |
| 离线回算 | 经运维停写确认后读取已有日志/备份，排除删除主体、仅保存同一最小结构；默认只读，显式 `--apply --offline` 才写，输出汇总而非安装身份，不恢复原始事件到在线日志 | `scripts/backfill-retention.mjs` |

只持久保存 D1/D7/D30 三个布尔值不足以支持更早成功迟到后重锚，需要保留首 31 天的成功日期。继续只依赖 35 天日志无法满足长期保留已发生留存的需求；长期保存整份原始事件则保留更多字段。当前有限日期集合是本次准确重锚和单主体可删除需求下的取舍，不是任何未来用途的无限保留授权。

## 保留、权限与删除核对

- 原始行为/管道明细的 35 天上限与容量限制不放宽。最小依据不按年龄自动删除，会在安装长期未再次使用时继续存在；“最多 31 个日期”限制每安装数据量，不能解释为“最多保留 31 天”。总安装数仍受登记容量控制。更严格的地区或企业保留策略优先，当前没有专门的按年龄自动清除最小依据开关。
- 文件使用私有原子写入，普通文件权限收紧为 `0600`，目录按现有私有目录策略管理；留存依据/标记读取、在线库存私有文件检查和遥测原子写目标拒绝 symlink/非普通文件。离线回算只读的设备清单、墓碑及原始日志/备份源没有同等链接拒绝策略，仍须由操作方核实来源及真实目标，不能把写入保护当作所有输入路径的沙箱。Windows 的访问隔离仍依赖部署目录 ACL，不能把 POSIX mode 位当作完整 Windows ACL 验证。备份、离线工具与机器管理员同样可能读到可关联日期，须使用受控存储和最小权限。
- 既有 `behavior_analyst` 仅访问行为聚合，`operations_admin` 才能访问设备运营明细。现有低样本数量展示没有因为本次修改自动获得匿名化保证；有其他已知信息的管理员仍可能推断个别安装是否成功使用过产品。本文不认可单安装定向分析或把这些结果当作不可逆匿名的 13 个月聚合。
- 用户停采/结束采集周期阻止新的有效事件进入，不自动删除已收集的留存依据；关闭采集不等于撤销已保存记录。客户端没有本次新增的删除入口，现有管理员/合规删除流程仍需有效安装凭证。凭证无法取得的历史登记不能通过直接编辑文件擅自清除，应按现有合规处置流程处理。
- 在线删除先保存 tombstone，再从留存依据、原始事实和设备映射清除安装；成功状态仅在对应保存完成后返回。中途存储失败不能当作已完成，恢复后继续依据墓碑排除该主体。启动、查询及回算必须使用有效设备清单，清单未知时失败关闭，不能按空库存删除所有留存。
- tombstone 使用服务端密钥摘要阻止旧安装重新登记和旧备份恢复；它是防恢复状态，不能当作可随原始事件窗口清除的普通日志。恢复必须保留当前 tombstone 和相同 pepper，不得用旧备份覆盖删除状态。
- 在线删除与恢复时应用墓碑不等于所有离线备份字节已擦除。最小依据备份仍可关联安装，须纳入管理员/合规删除和备份生命周期管理；恢复过滤只防止重新上线，不免除离线副本的访问与删除责任。本实现不控制外部备份介质，也不证明其已按要求删除；原始明细备份的最长 35 天约束保持不变。

## 技术结论与剩余风险

本次延长保留的工程理由成立：保存有限的、可随主体删除的安装日期依据能让历史留存不随原始日志清理消失，同时避免保存全部事件内容。用途限于已声明的实时留存；没有扩大客户端事件字段、账号关联、分析角色权限或导出范围。按上述边界实现并验证时，可满足该指标的技术最小化与可删除要求。

仍存在长期可关联日期、管理员交叉推断、关闭采集不删除历史、离线备份处置依赖运维、凭证遗失影响删除受理，以及存量历史无法补证等风险；不得把每安装有界、比例抑制或随机标识等同不可关联/无风险。没有人工/法务审批证据写入本记录，也没有替相关负责人作发布批准。既有《用户行为埋点运维验收》要求的产品、数据、安全/隐私负责人发布批准及更严格当地策略继续适用。

复核应覆盖：原始日志清理和重启后留存不消失；删除后在线事实消失且旧备份不能恢复；未知/损坏设备清单不触发破坏性清理；保存失败的查询不伪装成零；行字段/31 日期上限和私有存储；API 无安装标识、比例低样本抑制；真实口径时间持久化与页面动态显示。对应测试位于 `remote-control-relay/test/` 的留存、回算、遥测及 stats UI 套件，实际执行结果以本次 PR 验证记录为准。

新增用途、延长到其他字段、改变主体关联、放宽小样本规则或取消删除约束时，需要重新按需求第 14 节评估，不沿用本记录结论。
