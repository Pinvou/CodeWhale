# Evidence image validator candidate

This isolated executable is **disabled by default**. Billing calls it through the opt-in original-document upload path. The [site acceptance runbook](../../deploy/runbooks/formal-product-admission-acceptance.md) provides an explicit isolated Linux Compose overlay. The executable exits without creating a socket unless `EVIDENCE_IMAGE_VALIDATOR_ENABLED=true` and the Linux-only socket and peer settings are supplied. The standalone Dockerfile has no inherited HTTP health check; deployment supplies the sandbox and resource limits.

Set `EVIDENCE_IMAGE_VALIDATOR_SOCKET` to an absolute socket path in a pre-existing, worker-owned, non-world-accessible directory. Every ancestor must be owned by root or the worker and not group/other writable. The worker refuses an existing path; it does not unlink the endpoint at startup or shutdown. Deployment must provide a securely replaced empty socket directory on restart; otherwise startup fails closed. Set `EVIDENCE_IMAGE_VALIDATOR_ALLOWED_UID` to the non-root, dedicated Billing process UID, distinct from the worker UID. The socket directory must be mounted only into Billing and this worker, with group access configured without granting directory write to the caller. SO_PEERCRED authenticates a kernel UID, not a workload identity; uniqueness of that UID and mount isolation require deployment verification. Checking a pathname cannot eliminate replacement races by another process with the worker UID or privileged host access. The Billing upload client authenticates the server UID using SO_PEERCRED on the connected socket before sending any original bytes. Cross-container positive and negative identity tests remain required.

The daemon admits one request at a time across all formats, rejects excess connections, and has a 45-second socket and child deadline. A connection carries one request: a 60-byte header containing protocol magic, type byte (1 PNG, 2 JPEG, 3 PDF), three zero reserved bytes, 16-byte request nonce, 32-byte SHA-256 of the input, and a big-endian uint32 length, followed by exactly that many bytes (1 through 10 MiB). `PIV1` accepts only PNG and JPEG; `PIV2` accepts all three types. The candidate Billing client continues to send `PIV1` for images and sends `PIV2` for PDF; it does not downgrade a PDF request. The peer must keep its write side open until the response: EOF, half-close, extra input or disconnection cancels the child. A response has 56 bytes: the request's magic, one status byte (1 valid, 2 invalid, 3 unavailable, and 4 password required for PDF), three zero bytes, the request nonce and calculated SHA-256. With the PDF candidate disabled, a PDF request returns unavailable. Short reads, mismatches, unknown status, unexpected response bytes, untrusted server identity, timeout and any missing response must be treated as unavailable. No request may be interpreted as financial or authorization evidence on its own. The candidate client uses a random nonce, verifies the response binding and EOF, and does not automatically replay the business operation.

Each accepted request starts a one-shot child with no inherited environment; disconnect or timeout cancels, kills and waits for it. Linux requests a parent-death signal. The decoded output is discarded, original bytes are not re-encoded, and the implementation does not intentionally write them to files or logs. This does not prove absence of copies, swap, core dumps, kernel buffers or sensitive values in an external observer. Disable swap/core dumps and restrict traces and host access in the deployment. The caller's and worker's separate buffers are part of the resource budget.

Image validation uses Go's standard PNG/JPEG DecodeConfig followed by full Decode, with overflow-safe 40,000,000-pixel admission. Standard decoders have documented tolerant parsing behavior. APNG control and frame chunks are rejected by parsing PNG chunk boundaries before the standard decoder; text or compressed data containing the same byte sequences do not count as chunks. Billing integration must show a localized instruction to upload a static PNG, JPEG or PDF. PNG accepts and preserves decodable trailing bytes after IEND and follows the Go decoder for unknown chunks and extra image data; chunks through IEND are checked for CRC and APNG markers. JPEG parsing follows the Go decoder, including its tolerance of trailing data. The current local tests do not prove that every valid 40-million-pixel image will complete within a given memory or time budget.

PDF support is a separate, default-off research candidate. If `EVIDENCE_PDF_CANDIDATE_ENABLED=true`, the supervisor invokes the fixed executable `/opt/pinvou/pdf/bin/python3` with `-I -B /opt/pinvou/pdf/pdf_validator.py`; it does not use a shell or accept a caller-supplied path. One child handles one PDF through its standard-input pipe and returns a single status byte; raw diagnostic output is discarded. The Python child requires pikepdf 10.17.0 and qpdf 12.4.2, opens with `attempt_recovery=False`, checks syntax and applicable linearization, and rejects warnings observed during its checks and close. That setting does not guarantee that qpdf performs no recovery: for example, it may recover a truncated stream and emit a warning. The child supplies an empty password; a file that opens with it can be accepted if the other checks pass, while a file requiring a nonempty password is rejected with the password-required status. Other parser errors are invalid and runtime/dependency failures are unavailable. The intended user-facing policy is to ask users to re-export PDFs with structure or stream warnings, and to distinguish files requiring a password. UI integration is not implemented. The checks do not establish that every PDF specification field or every possible warning has been checked. This is format validation, not malware or content security scanning.

Python warnings are converted to exceptions and rejected at the first propagated warning, without collecting their text. This does not bound native qpdf or pikepdf allocations or lists returned by their checks: many damaged streams can accumulate many native diagnostics. A real independently limited worker cgroup, timeout and resource testing remain required before activation.

The original image-only Dockerfile does not contain Python or PDF dependencies. A separate `Dockerfile.evidence-validator-pdf` and `pdf-requirements.lock` define an opt-in image candidate: the Dockerfile pins official multi-architecture Python and Go image indexes, installs only hashed wheels from a local named `pdf-wheels` build context with the network disabled, checks dependency closure and checks pikepdf/qpdf versions. Source distributions are prohibited. The build as a whole is **not offline**: fetching base images and downloading Go dependencies from the official Go proxy may use the network. Go verifies module checksums and the compile itself runs without network access; the image does not automatically download or install packages at runtime. A verified BuildKit version and bit-for-bit build reproducibility remain to be established. The local Windows virtual environment used in tests is not a deployment dependency. Base index digests and wheel hashes do not establish native license compliance, vulnerability status or a complete SBOM. The amd64 PDF image was built and passed basic container validation in [CI job 122720332200](https://github.com/Pinvou/pinvou3/actions/runs/40659993285/job/122720332200), fixed at head `2fad692934c601f43a185662acd6e9ce36c06044`. This is historical evidence, not validation of subsequent changes. The arm64 PDF image, image-only Dockerfile and production deployment remain unverified. Although the opt-in flag exists in the candidate, **do not enable it** until dependency review and the isolation and resource conditions below are independently established. No PDF input is intentionally written to disk, but in-memory copies and the operating-system exposures described above remain possible.

Use `prepare_pdf_image.py --audit-dir <audit-directory> --platform linux/amd64` (or `linux/arm64`) for a preflight without invoking Docker. It checks the selected architecture's four wheel files against the lock and the fixed architecture, filename and hash bindings in `pdf-wheel-bindings.json`. An authorized build can add `--build --output <new-oci-archive>`; each invocation supplies only the selected architecture's four wheels, copied and rechecked into a temporary flat directory, and explicitly passes `--build-context pdf-wheels=<directory>` to BuildKit. Use separate invocations for the two architectures. Do not invoke the Dockerfile without that explicit local context: BuildKit may otherwise resolve `pdf-wheels` as an image. Do not pass the audit root directly as the context: its wheels are in architecture subdirectories and pip's `--find-links` does not recurse. Preflight is not an image build. The historical amd64 CI job above exercised preflight and then built separately with Docker buildx `--load`; this helper's `--build` archive-publication path, arm64 and the intended production host still require Linux validation.

The build writes its archive in a private temporary directory under the output parent and publishes it with an atomic hard link that fails if the destination name already exists, including a symlink. Unsupported hard links also fail closed. The destination is never deleted by the entry point. The caller must use a trusted output parent whose ancestors cannot be renamed or replaced by another principal during the build: parent path resolution and later filesystem operations are not protected by directory handles. Normal errors and interrupts clean the temporary directory; an uncatchable termination can leave it behind for manual inspection. This publication mechanism and filesystem behavior require validation on the intended Linux host.

Before activation, independently review the Billing client and test peer UID checks in both directions; verify the no-half-close protocol and cancellation end to end. Render and deploy an opt-in sidecar/worker with a separate cgroup, non-root distinct UIDs, read-only filesystem, no secrets, constrained process/CPU/memory and restricted network. A 2 GiB worker limit is only a measurement starting point, not a proven bound. A Kubernetes sidecar shares its Pod network namespace, so NetworkPolicy alone does not establish worker-only network denial. Verify real deployment enforcement, supervisor/child OOM behavior, Linux parent death, node pressure and timeout cleanup, plus 40-million-pixel 16-bit/Adam7 PNG and progressive/CMYK JPEG under the intended limits. Validate no plaintext disk or core dumps and original-byte preservation. Existing Billing memory/admission limits and original PDF behavior must remain unaffected. If any of these cannot be established, keep the feature disabled.
