# Expired hold proof workload grant

The installed Billing expired-hold-recovery worker calls the configured HTTPS Token endpoint through HTTPExpiredHoldProofClient using Billing's projected workload credential. Token's POST /internal/v1/holds/expiry-proof requires the exact internal.token.hold-expiry.prove permission. The retained Helm and Compose model-token receiver rules now grant that existing scope only to the already controlled billing-service identity; the production Token rules template already has the correct grant and remains unchanged.

This does not add an identity, wildcard, token lifetime, financial operation or proof bypass. All earlier grants, closure permissions, actor and audience constraints remain. Missing or mismatched proof still retains the existing uncertain-funds/manual-review behavior; an authorization grant is not evidence that a hold is safe to release.

The normal account-platform Node contract glob renders Helm remote/native KMS, retained Compose remote/native and the production models composition with the existing real renderers. Removing either original missing source grant and rendering again must fail its exact caller/subject/receiver scope assertion. Render tests require PINVOU_TEST_KMS_HELM=1 and PINVOU_TEST_KMS_COMPOSE=1 plus installed tools; CI already supplies both and missing tools fail rather than count as rendered evidence. A separate serviceauth test uses real TLS JWKS, signed JWTs and installed GinMiddleware/Require to verify exact grant success and missing scope, wrong subject/caller/issuer/audience and static-token rejection. These tests do not run a real hold settlement, PostgreSQL recovery or deployment.
