# 账号平台目标需求基线

> 状态：已确认目标需求，未注明实现状态
>
> 校准日期：2026-08-22
>
> 当前实现、提交、测试、部署版本和已知差距见 `implementation-status.md`

本文只定义产品目标、领域规则和可验收结果，不用当前 Provider 或当前代码能力反向删减通用需求。具体厂商协议只能出现在 Adapter、部署配置和运维文档中。

## 0. 需求编号治理

- `[REQ-ID-01]` 每个规范性能力必须拥有一个稳定 `target_requirement_id`，且一个编号只能对应一个可独立验收的能力；细化步骤、状态转换和示例作为该能力的验收条件，不创建含义重叠的编号。
- `[REQ-ID-02]` 已存在的 `ID/ACC/TOK/BILL/PAY/UI/ADM/NFR` 编号保持原有语义，新能力只能从相应编号空间末尾追加。
- `[REQ-ID-03]` 编号一经发布不得复用、重排或改变含义；验收边界发生实质变化时必须追加新编号，旧编号保留并标记 `RETIRED` 或 `REMOVED`、注明替代编号，不得把旧编号授予其他能力。
- `[REQ-ID-04]` 实现状态记录必须包含 `target_requirement_id`、状态、源码提交、测试证据、部署版本和已知差距；一项实现影响多个目标需求时逐一列出，不能使用无编号文字代替映射。
- `[REQ-ID-05]` 本文中带方括号编号的表格行、标题或列表项是规范性要求；同一编号在后文再次出现表示补充同一能力的验收条件，不表示新能力。

编号空间：`CORE-*` 核心不变量、`SCOPE-*` 产品边界、`ID-*` 身份认证、`ACC-*` 账号与组织、`TOK-*` 模型调用、`BILL-*` 计费权益、`PAY-*` 支付、`UI-*` 用户界面、`ADM-*` 运营管理、`NFR-*` 非功能要求。`CR-*` 仅是历史需求变更记录，不是目标能力编号。

## 1. 产品范围与核心不变量

账号平台为个人用户和组织用户提供统一身份、活动计费上下文、权益、模型调用、支付、用量和管理能力。平台管理员管理账号、组织、角色、定价、支付异常、模型路由、核对、审计和服务状态。

必须保持以下不变量：

1. `[CORE-01]` 配置中的 Identity Provider 是认证、密码、登录会话、Refresh Token 和会话撤销的事实源。
2. `[CORE-02]` Account Service 是业务用户、当前用户名/手机号映射、组织关系、角色权限及聊天和计费活动上下文的事实源。
3. `[CORE-03]` Commerce Provider Mapping 只维护用户或组织与外部商城客户的映射，不参与通用认证和授权。
4. `[CORE-04]` Billing 的不可变平衡账本是余额、债务、权益和资金调整的唯一事实源。
5. `[CORE-05]` 模型供应商密钥只在 Token Gateway 受控边界内解密，普通用户和普通管理接口只能看到凭据元数据。
6. `[CORE-06]` 外部支付、模型调用或网络结果不确定时保存证据并进入可核对状态，不猜测成功，不自动重复高风险请求。
7. `[CORE-07]` 跨服务变更通过幂等 Saga、Outbox/Inbox 和人工修复收敛，不宣称跨数据库原子事务。

明确边界：

- `[SCOPE-01]` 用户在桌面本地模型设置中配置的本地模型或第三方云模型完全绕过账号平台、平台钱包和 Token Gateway，不纳入本需求管理。
- `[SCOPE-02]` 个人中心不实现用户自有供应商 Key、自管 Token Account、共享策略或路由管理。
- `[SCOPE-03]` 平台托管 Token Account、路由和供应商凭据属于内部运营能力，普通用户不可见、不可修改。
- `[SCOPE-04]` 旧 `llmapi_hub` 身份、设备账号、旧 New API 用户 Token、旧模型列表和运行时回退路径全部移除；本地独立模型不属于旧内置路径。
- `[SCOPE-05]` 旧模型路径迁移的实现范围仅限品悟客户端代码、客户端运行时资源、客户端配置与凭据迁移、客户端测试、迁移工具及直接相关文档；不得据此修改 Account、Billing、Token Gateway、Identity Provider、New API 等服务端代码、数据库、接口契约或部署。客户端切换所需的服务端能力缺失时必须阻止切换并报告缺口，不能越界补写服务端实现。

## 2. 参与者与权限边界

| 参与者 | 目标能力 |
|---|---|
| 未登录用户 | 密码登录、短信登录、手机注册、滑块验证和忘记密码。 |
| 个人用户 | 使用个人聊天和计费上下文，查看个人权益与用量，充值和管理本人资料。不能创建顶层组织。 |
| 组织成员 | 使用管理员授予的组织额度；能否管理组织资源由显式目标组织、角色权限和作用域决定。 |
| 组织所有者 | 每个有效组织恰好一人；负责所有权转让和最高组织治理。 |
| 企业管理员 | 可多人；管理成员、节点、普通组织角色、成员额度和组织权益购买。 |
| 平台管理员 | 通过 Account 平台权限管理跨租户资源；不受聊天和计费活动上下文影响。 |
| 运维人员 | 通过受限网络和工作负载身份管理 Identity Provider、数据基础设施、模型网关与部署，不等同于平台管理员。 |
| 服务身份 | 服务账号、后台任务和 Event Relay 的非人类身份，只拥有明确的最小内部权限。 |

角色、权限码、作用域、授权生命周期和服务身份矩阵以 `role-system-design.md` 为准。

## 3. 身份、注册和账号生命周期

### 3.1 注册与登录

| target_requirement_id | 目标需求 | 验收标准 |
|---|---|---|
| ID-01 | 密码登录支持手机号或用户名 | 两种标识解析到同一 Account 用户；密码只由 Identity Provider 校验，客户端不持久化密码。 |
| ID-02 | 支持手机号加短信验证码登录 | 仅支持中国大陆手机号；验证码用途与注册、改手机号、找回密码隔离。 |
| ID-03 | 手机注册必须填写用户名、手机号和两次一致密码 | 前后端独立校验用户名、手机号、密码规则和两次密码一致性。 |
| ID-04 | 获取短信前完成一次性滑块挑战 | 挑战在覆盖登录框的弹层中完成，服务端校验、防重放并绑定短信用途。 |
| ID-05 | 发注册短信前预检用户名、手机号和密码 | 唯一性与密码规则不通过时不调用短信 Provider；接口必须限流并控制枚举风险。 |
| ID-06 | 短信请求限流 | 同手机号至少 60 秒一次、最多 5 次/小时；服务端为准，前端显示倒计时。 |
| ID-07 | 短信挑战一次性且可过期 | 默认 5 分钟有效、最多 5 次核验，成功后不可复用。 |
| ID-08 | 短信核验不泄露验证码 | 使用托管核验时平台只保存 Provider 挑战标识和状态元数据；使用平台生成模式时验证码只保存不可逆摘要并按过期策略清除。 |
| ID-09 | 注册不能留下不可登录的半成品账号 | Identity 或 Account 创建失败时使用可恢复 Saga 收敛；Identity 与 Account 均成功后账号必须可登录，钱包初始化不再决定注册是否成功。 |
| ID-10 | 登录成功后支持自动登录 | Refresh Token 只保存在系统凭据库，启动时通过 Identity Provider 刷新。 |
| ID-11 | 失败后停止自动登录 | 用户登出、刷新失败或凭据错误时删除持久化 Refresh Token，不回退历史缓存。 |
| ID-12 | 密码支持常用英文符号 | 8–128 位可打印 ASCII，至少包含一个字母和一个数字；服务端执行最终校验。 |
| ID-13 | 短信登录反枚举 | 未知手机号与已知手机号返回一致外部响应，并配合统一耗时、限流和审计。 |
| ID-14 | MFA 与账号申诉 | 除密码和短信外的 MFA、人工账号申诉不属于当前交付范围；不得用不完整占位流程宣称支持。 |
| ID-15 | 短信 Provider 可替换 | 业务层只管理挑战、用途、风控和结果；支持厂商托管验证码及平台生成验证码后由厂商发送两种模式。 |
| ID-16 | Billing 故障不得删除已验证身份 | Identity 与 Account 已成功后，禁止因钱包初始化失败、超时或 Billing 暂时不可用补偿删除已验证手机号身份。 |

|---|---|---|
| ACC-01 | RETIRED：首次登录同步建立业务用户和个人钱包 | 注册改为先持久创建 Account，再异步初始化钱包；保留本编号且不得复用，现行规则见 ACC-28、BILL-30。 |
| ACC-18 | Identity Provider 管理适配 | Account 只依赖用户创建、删除、资料同步、密码重置和会话撤销端口，厂商管理协议仅存在于 Adapter。 |
| ACC-19 | 外部 Commerce Customer 开通 | 对需要外部客户的 Provider 异步开通并保存供应商中立映射；未完成只阻止依赖该映射的支付。 |

| ACC-29 | PROVISIONING 能力门禁 | PROVISIONING/REPAIR_REQUIRED 用户可登录和管理本人资料，但不能调用任何平台模型或创建充值订单。 |
| ACC-30 | Provisioning 超时转人工修复 | 钱包初始化在 SLA 内保持 PROVISIONING 并自动重试；只有超过 SLA 才进入 REPAIR_REQUIRED。 |

### 3.2 注册 Provisioning Saga

```text
Identity verified and created
  -> Account committed(status=PROVISIONING)
  -> Wallet ensure requested through Outbox
  -> Wallet ready
  -> Account status=ACTIVE

Wallet not ready within SLA
  -> Account status=REPAIR_REQUIRED
  -> automated/manual idempotent repair
  -> Wallet ready
  -> Account status=ACTIVE
```

规则：

1. `[ACC-28]` Identity 与 Account 提交成功是注册成功边界。注册接口返回稳定 `user_id` 和 `account_status=PROVISIONING`；若钱包在响应前已经确认就绪可以返回 `ACTIVE`，不得因后续 Billing 结果把已经返回的账号改写为“注册失败”。
2. `[BILL-30]` Account 提交 `PROVISIONING` 时通过 Outbox 发出幂等钱包初始化请求；Billing 使用稳定用户 ID 确保唯一钱包并返回可重复消费的完成事件。Billing 短暂不可用时异步退避重试，注册请求不直接依赖 Billing 可用性。
3. `[ACC-29]` `PROVISIONING` 和 `REPAIR_REQUIRED` 都允许登录、登出、刷新会话、查看初始化状态及管理用户名、手机号和密码；Token Gateway 对个人和组织平台模型调用返回稳定 `ACCOUNT_PROVISIONING` 或 `ACCOUNT_REPAIR_REQUIRED`，支付下单返回对应稳定原因码。桌面本地独立模型不受影响。
4. `[ACC-30]` Provisioning SLA 从 Account 成功提交时开始，配置必须版本化并保存到任务快照；SLA 内失败只能保持 `PROVISIONING` 和自动重试，超过 SLA 才能转为 `REPAIR_REQUIRED`、进入运营队列并允许人工重试。
5. `[ID-16]` Account 一旦成功提交，钱包初始化失败、超时、Billing 熔断或事件积压都不得触发 Identity 删除、手机号释放或 Account 删除。只有用户注销、安全处置或“Identity 已创建但 Account 从未成功提交”的注册补偿可以停用或删除 Identity。
6. `[UI-12]` 客户端必须把 `PROVISIONING` 显示为“账号已创建，服务初始化中”，把 `REPAIR_REQUIRED` 显示为“账号已创建，初始化需要处理”，并允许用户登录和管理资料；不得显示密码错误、注册失败或诱导重复注册。

### 3.3 资料修改 Saga（ACC-22）

Account 使用 `identity_change_requests` 协调用户名和手机号修改：

```text
REQUESTED
  -> VERIFIED
  -> ACCOUNT_PENDING_RESERVED
  -> IDENTITY_UPDATE_PENDING
  -> IDENTITY_UPDATED
  -> ACCOUNT_COMMITTED
  -> COMMERCE_SYNCING       # 仅手机号
  -> COMPLETED

不可自动收敛 -> REPAIR_REQUIRED
```

规则：

以下各项都是 `ACC-22` 的验收条件：

1. Account 先保存 `PENDING` 映射、预约规范化后的唯一值并记录资料版本；同一用户同一字段只允许一个未完成请求。
2. 用户名修改需要重新认证；手机号修改需要重新认证并验证新手机号。
3. Identity Provider 更新后、Account 正式提交前，身份解析通过变更请求把新标识映射到原稳定用户 ID，避免产生第二个业务用户。
4. Account 通过 CAS 把 `PENDING` 映射转为正式映射；失败时优先向前重试，不自动覆盖已经生效的 Identity 标识。
5. 用户名或手机号提交成功后都撤销其他登录会话和 Refresh Token，当前操作会话按安全策略重新认证。
6. 手机号提交后异步同步 Commerce Mapping。同步失败不回滚登录或 Account 资料，允许模型调用，但暂停依赖该 Mapping 的新支付。
7. 所有步骤使用稳定幂等键，普通用户只看到业务状态和恢复动作，不看到 Provider 原始错误或外部客户 ID。

### 3.4 忘记密码与注销

| target_requirement_id | 目标需求 | 验收标准 |
|---|---|---|
| ACC-14 | 用户可修改用户名 | 使用资料变更 Saga、唯一值预约和重新认证；提交后撤销其他会话。 |
| ACC-15 | 用户可修改手机号 | 使用资料变更 Saga、重新认证和新手机号短信验证；提交后撤销其他会话并异步同步 Commerce Mapping。 |
| ACC-16 | 用户可通过手机号短信找回密码 | 验证成功后由 Identity Adapter 重置密码并撤销全部既有会话；管理员不能设置或查看用户密码。 |
| ACC-20 | 用户可主动注销账号 | 个人余额和未清应收均为零、无本人未完成付款/退款、无未结算 Hold，且已转让全部组织所有权时才允许注销。 |
| ACC-21 | 注销记录去标识化并保留三年 | 标识安全释放后允许复用；Account 使用随机墓碑值，Commerce Mapping 转为 `DETACHED`，法定记录通过不可逆内部主体 ID 保留三年，法律保全除外。 |
| ACC-22 | 资料修改使用可恢复 Saga | PENDING 映射、Identity 更新、Account CAS 提交、会话撤销及 Commerce 同步均可幂等重试或进入人工修复。 |

`[ACC-20]` 补充验收：普通成员不因组织余额被阻止注销；注销时终止其成员关系。

`[ACC-21]` 补充验收：历史授予保留为不可反查审计记录；同一用户名或手机号重新注册时生成新用户 ID，不恢复旧权益、成员关系或账本。

## 4. 组织、角色和额度分配

### 4.1 组织生命周期

| target_requirement_id | 目标需求 | 验收标准 |
|---|---|---|
| ACC-02 | 一个用户可属于多个组织 | 成员关系独立保存，任何组织权限和额度都按目标组织隔离。 |
| ACC-04 | 无组织用户不显示组织入口 | 用户没有任何有效组织成员关系时，个人中心不显示组织页签或组织入口。 |
| ACC-05 | 个人用户不能创建顶层组织 | 只有拥有平台组织创建权限的管理员可以创建顶层组织。 |
| ACC-06 | 管理员管理组织生命周期 | 支持创建、搜索、启停和逻辑删除，全部执行服务端权限检查并写审计。 |
| ACC-07 | 组织树形子节点管理 | 支持创建、重命名、删除和调整父节点，必须防环并保护有关联资源的节点。 |
| ACC-08 | 名称修改显式进入编辑态 | 组织和节点名称只有在用户主动启动编辑后才可提交修改。 |
| ACC-09 | 成员与角色管理 | 支持添加、移除成员以及按组织/节点作用域分配和撤销普通角色。 |
| ACC-10 | 唯一所有者安全转让 | 每个有效组织恰好一个所有者；所有权只能通过专用幂等事务转让，普通管理员可多人。 |
| ACC-11 | 查看角色和用户关联 | 管理后台可查看角色定义、用户平台角色、组织成员角色和有效期；个人中心只查看本人角色。 |
| ACC-12 | 组织邀请 | 支持手机号、用户名和一次性链接，具备过期、撤销、一次性消费、反枚举和接受时身份绑定。 |
| ACC-13 | 权限码与作用域授权 | 平台/组织角色使用权限码、明确作用域和默认拒绝；不以客户端隐藏按钮代替服务端授权。 |
| ADM-11 | 角色授权自动回收 | 角色绑定支持开始/到期时间并自动回收。 |
| ADM-12 | 审批角色兼任和交叉审批 | 允许运营/审批角色兼任和交叉审批，但禁止自审，不额外要求双人审批。 |

### 4.2 聊天和计费活动上下文

1. `[ACC-03]` 桌面与 Web 共用一条用户级活动上下文和单调递增的 `context_version`；该上下文只表示聊天和计费使用个人钱包还是某个组织钱包。
2. `[ACC-23]` 组织管理 API 必须显式携带 `target_organization_id`，按目标组织、成员关系、权限码和作用域授权；打开或管理组织不切换聊天和计费上下文。
3. `[ACC-24]` 平台后台权限完全不受聊天和计费活动上下文影响。
4. `[ACC-25]` 切换前已成功创建 Hold 的模型调用保存活动上下文、钱包、授权和版本快照，始终按请求开始快照结算。
5. `[ACC-26]` 成员被移除或组织停用后，若该组织是其活动上下文，Account 自动切回个人并递增版本。
6. `[ACC-27]` 所有已认证业务 API 返回 `context_version`；组织管理响应同时返回目标组织的 `authorization_version`。客户端收到更高版本时丢弃旧额度、权限、路由和组织缓存。

### 4.3 组织权益购买与成员分配

1. `[BILL-13]` 企业管理员在线购买组织权益；订单保存实际付款管理员和受益组织，支付成功后只创建组织权益包及组织钱包账本，不进入付款人个人钱包。
2. `[BILL-11]` 成员额度是组织权益的限额授权，不是钱包转账。员工不能自主领取，管理员可以给自己分配。
3. `[BILL-18]` 管理员分配时必须同时选择具体权益包和 `BASE` 或 `BONUS` 组成；系统不得把不同包或不同组成合并为无法追溯的总额。
4. `[BILL-19]` 权益组成只有 `BASE` 和 `BONUS`，不定义“增量包积分”类型。增量商品仍由其权益包内的 BASE/BONUS 组成表达。
5. `[BILL-20]` 批量分配按成员逐项执行独立事务，部分失败不回滚成功项；每项返回幂等结果和失败原因。
6. `[BILL-21]` 授予不能原地改额；只能撤回未消费、未被 Hold 占用的部分后重新分配。
7. `[BILL-22]` 成员移除后，未消费授予转为 `SUSPENDED` 并继续占用原权益，不回组织池；在原有效期内重新加入同一组织时恢复，过期时间不变。
8. `[BILL-23]` 显式撤回成功的未消费额度返回原权益组成；成员移除导致的暂停不是撤回。

### 4.4 组织安全逻辑删除（ACC-17）

以下均为 `ACC-17` 的验收条件。删除采用“先停用、再预检、后逻辑删除”，任一条件存在时禁止删除：

- 组织钱包余额不为零或存在未清应收。
- 存在有效权益包或未结算 Hold。
- 存在未完成付款、退款、拒付或未关闭对账差异。
- 存在待核对模型用量。
- 存在暂停但尚未到期的成员授予。
- 存在未完成所有权转让、邀请或资料修复任务。
- 存在未收敛的额度分配、Token 路由或外部 Commerce 任务。

组织停用后禁止新上下文激活、新分配、新购买和新 Hold，并将受影响的聊天和计费上下文切回个人。最终删除使用带版本许可的幂等命令完成，只写 `DELETED`，不物理删除账本、订单和审计。

### 5.1 模型状态

模型可用性分为两个模型级状态和一个请求级实时判定：

- `[TOK-18] CATALOG_VISIBLE`：目录展示状态。模型已发布到目录、允许面向用户展示且具备基本展示元数据；该状态不判断当前个人/组织上下文、余额、成员授予或具体请求预算。
- `[TOK-19] RETIRED：INVOKABLE`：旧状态同时混合上下文资格和请求级预占能力，无法作为稳定模型状态；保留本编号且不得复用，替代能力见 TOK-23、TOK-24、TOK-25。
- `[TOK-23] CONTEXT_ELIGIBLE`：当前聊天和计费上下文的身份权限、组织成员状态、模型策略、调用协议和可命中路由允许使用该模型；不包含钱包余额、权益剩余、并发占用或具体请求预算，因此不承诺请求一定能够创建 Hold。
- `[TOK-24] RESERVABLE`：针对一次具体请求的协议参数、协议预占公式、计量单位价格、钱包、权益、成员授予和并发占用，在创建 Hold 的同一实时决策中计算；只有 Hold 原子创建成功，本次请求才是 `RESERVABLE`。
- `[TOK-25]` 客户端展示的“可调用”只能是基于最近上下文和余额摘要的非权威提示，不得作为授权或预占结果。Gateway 必须在每次请求时重新判断 `CATALOG_VISIBLE`、`CONTEXT_ELIGIBLE` 并实时创建 Hold，不信任客户端状态或旧缓存。

Gateway 对每个失败阶段返回稳定原因码和最新 `context_version`、模型目录版本；不得暴露供应商凭据或内部路由细节。客户端不得在 Hold 创建前把 `RESERVABLE` 保存为模型的持久状态。

### 5.2 平台托管模型调用

1. `[TOK-01]` 桌面聊天携带与个人中心一致的 OIDC 身份调用 Token Gateway，不接受客户端提供付款主体、角色或钱包。
2. `[TOK-20]` Gateway 提供受支持协议的兼容入口，模型目录必须声明 Chat、Embedding、Rerank、图像或其他协议能力；未声明的协议不得推断可用。
3. `[TOK-04]` 首次平台调用幂等创建平台托管 Token Account 和默认路由，普通用户不可见、不可修改。
4. `[TOK-07]` 路由按作用域、优先级、模型和健康状态确定选择；出现同优先级歧义时拒绝调用并告警。
5. `[TOK-25]` 即使客户端刚显示“可调用”，Gateway 仍按当前目录、上下文版本、权限、策略和路由重新判断；客户端提交的状态字段必须忽略。
6. `[TOK-24]` Gateway 只在具体请求的 Hold 原子创建成功后调用上游；预算、余额、授予或并发占用不足时不得先调用模型再补记 Hold。
7. `[TOK-12]` 模型请求使用稳定幂等键；同一幂等键必须返回既有结果或当前核对状态。
8. `[TOK-14]` 网络结果不确定时不得自动向上游重发，只能查询原请求证据。
9. `[TOK-13]` 普通用户可查看自己的用量历史和费用，不得看到真实凭据、内部结算操作或供应商运维信息。
10. `[TOK-26]` 每种模型调用协议必须发布不可变、版本化的预占公式，声明可使用的请求参数、模型元数据和计量单位；Chat、Embedding、Rerank、图像及后续协议不能共享一个硬编码 Token 公式。
11. `[TOK-27]` 预占公式引用的请求参数或可选模型参数缺省时统一按数值 `0` 计算；常量不属于缺省参数。公式版本、计量单位定义或所需单价缺失属于配置错误，必须拒绝创建 Hold，不得把缺失配置按零价处理。

### 5.3 品悟客户端旧模型数据迁移

1. `[TOK-28]` 品悟客户端必须在启用唯一新内置模型路径前执行版本化、一次性且幂等的本地数据迁移。迁移输入至少覆盖客户端持久化的旧 `llmapi_hub` 设备身份、旧 New API 用户/Token/模型绑定、旧登录与模型目录缓存、当前内置模型选择，以及系统凭据库中的对应旧凭据引用。
2. `[TOK-28]` 迁移必须先盘点并生成不含密钥明文的结果报告，再以可中断恢复的方式写入新配置 schema 和完成标记；进程中断或重复启动不得产生重复账号、重复模型、重复凭据或损坏配置。只有新配置持久化并通过校验后，才可清除旧活动引用和旧凭据；清理失败必须可重试并明确提示，不得继续使用残留凭据。
3. `[TOK-28]` 本地独立模型和用户自配第三方云模型的配置、凭据及选择必须原样保留，不得迁入账号平台或误删。旧内置模型无法映射到新目录时，清除其“当前选择”并要求用户重新选择 `CATALOG_VISIBLE` 模型，不得静默改为其他模型。
4. `[TOK-28]` 历史会话保存的模型显示快照必须继续可读，但从历史会话发起的新请求只能按当前新目录重新解析；迁移不得把旧服务端账号、余额、Token Account 或模型数据复制到客户端或新服务端，也不得把旧 New API API Key/Token 作为新账号平台凭据复用。

### 5.4 品悟客户端模型路径切换验收

1. `[TOK-29]` 客户端切换前必须通过准入检查：本地迁移可成功完成、账号平台配置完整、OIDC 登录入口可用、Gateway 模型目录可获取，并且新建平台模型请求能够进入 Token Gateway。任一项失败时保持当前版本未切换状态或阻止发布，不得在新版本运行时回退旧路径。
2. `[TOK-29]` 切换必须以客户端配置 schema 版本和构建能力为边界一次完成：新构建只注册新内置模型路径，旧 `llmapi_hub` 身份开通、设备账号、旧 Token、旧模型列表及旧 New API 直连命令不再可调用；账号平台不可用时显示明确错误。
3. `[TOK-29]` 发布验收至少覆盖全新安装、仅含旧内置模型数据的升级、仅含本地独立模型的升级、两类模型混合升级、迁移中断后重启、旧凭据清理失败、旧模型无法映射、未登录、账号平台不可用及历史会话读取。每个场景必须记录输入 schema、迁移结果、请求实际目的端、测试版本和日志证据。
4. `[TOK-29]` 新版本不提供旧路径开关或双运行回退。需要发布级回退时，只能回退到上一客户端构建并使用切换前的客户端配置备份；回退演练必须证明不会覆盖切换后的新格式数据，并由发布负责人基于验收证据作出 Go/No-Go 决策。

### 5.5 模型定价

1. `[BILL-04A]` 平台管理员可以设置全局默认价格和模型覆盖价格；每个策略支持统一价格或 `Asia/Shanghai` 时区的完整 24 小时分段价格，区间使用半开区间 `[start, end)` 且不得重叠。
2. `[BILL-05]` 价格分别包含输入、缓存输入和输出 Token 单价，按每百万 Token 和整数最小记账单位计算。
3. `[BILL-04]` 支持未来生效、结束、冲突校验和发布前预览；同一模型同一时刻只能命中一个最终价格。请求以 Hold 创建时命中的价格版本结算，即使长调用跨越价格时段也不换价，历史核对不得使用最新价格覆盖。
4. `[BILL-29]` 计价使用版本化计量单位定义，不再把 Token 作为唯一计量维度。首批单位包括 `INPUT_TOKEN`、`CACHED_INPUT_TOKEN`、`OUTPUT_TOKEN`、`IMAGE`、`REQUEST`、`DOCUMENT`，并允许以供应商中立代码追加其他单位。
5. `[BILL-29]` 每个计量单位版本声明单位代码、最小计量精度、单价分母和舍入规则；价格版本保存各单位的整数单价。预占、实际用量、账单和核对均保存单位版本、数量、单价及费用，不得用当前定义重算历史请求。

### 5.6 协议预占、动态 Hold、续租、负余额与应收（TOK-08、TOK-26、TOK-27、BILL-17、BILL-24、BILL-26–BILL-29）

```text
参数值(parameter) = 请求或模型元数据中的明确值；缺省时为 0
预占单位数量(unit_quantity) = protocol_reservation_formula_version(parameters, model_metadata)
单位预占费用(unit_cost) = round(unit_quantity * versioned_unit_price / price_denominator)
初始 Hold = sum(unit_cost)
```

协议公式示例只用于说明抽象，不固定具体商业价格：Chat 可以产生 `INPUT_TOKEN`、`OUTPUT_TOKEN`、`IMAGE` 和 `REQUEST`；Embedding 可以产生 `INPUT_TOKEN` 和 `REQUEST`；Rerank 可以产生 `INPUT_TOKEN`、`DOCUMENT` 和 `REQUEST`；图像协议可以产生 `IMAGE` 和 `REQUEST`。公式未引用的单位数量为零，实际结算仍以 Adapter 返回并归一化后的真实计量单位数量为准。

规则：

1. `[TOK-21]` Hold 创建成功的时刻是“请求开始”；活动上下文、授权、权益组成、价格、计量单位、协议预占公式、模型元数据和估算器版本都保存快照。
2. `[TOK-08]` 请求超过协议或模型限制时在创建 Hold 前拒绝；预占公式需要 `INPUT_TOKEN` 而模型没有 Tokenizer 或适用的版本化估算器时同样拒绝，不要求非 Token 协议机械配置 Tokenizer。
3. `[TOK-26]` 协议公式只能输出该协议声明的非负计量单位数量；公式求值必须确定、可复现并受资源限制，不得执行任意代码或调用外部网络。
4. `[TOK-27]` 未提供 `max_output_tokens`、图像数量、文档数量或其他公式参数时，该参数为 `0`；这项规则取代历史“缺省最大输出 1,000,000 Token”的预占默认值。
5. `[TOK-22]` 长调用在到期前续租 Hold；续租失败时停止仍可控制的输出并进入人工复核。
6. `[BILL-26]` 实际费用超过 Hold 时先追加预占；追加成功后结算，追加失败时停止仍可控制的输出并按实际费用结算。实际用量结算、拒付、退款冲销或受审计修复导致钱包低于零时，Billing 必须在同一事务中同时更新账本派生的 `wallet_balance` 负数投影，并创建或增加独立 `receivable` 的未清金额；普通预占不得主动制造负余额。
7. `[BILL-26]` 每笔应收保存钱包、债务类型、来源业务和证据引用、原始金额、已清偿金额、未清金额及状态；同一钱包的未清应收总额必须等于 `abs(min(wallet_balance, 0))`，`DEBT_BLOCKED` 的 BONUS 不进入该可用余额投影。任何差异进入人工复核，禁止直接改余额掩盖差异。
8. `[BILL-24]` 个人钱包为负时只禁止个人上下文创建新 Hold 和模型对话，不得阻止该用户使用其他正常组织授予的额度；组织钱包为负时只冻结该组织上下文，不得冻结用户个人上下文或其他正常组织上下文。登录、查看账单、充值、还款和必要的组织管理仍允许。
9. `[BILL-27]` 只有现金充值产生的 `BASE`、退款追回和受审计人工还款可以减少应收；每笔清偿必须显式分配到一个或多个应收 ID，并写独立账本分录和应收分配记录。允许来源超过未清应收的部分才可形成可用 `BASE`，钱包余额非负、应收清零且不存在其他冻结原因后恢复对应上下文调用。
10. `[BILL-28]` `BONUS` 不得清偿任何应收。现金拒付应收形成时，受影响钱包内未被既有 Hold 占用的未消费 `BONUS` 转为 `DEBT_BLOCKED`；既有 Hold 后续释放的 `BONUS` 以及债务期间新入账的 `BONUS` 也进入 `DEBT_BLOCKED`，均不计入可用积分。清偿完成后仅激活仍在原有效期内的剩余 `BONUS`，不得延长到期时间。
11. `[BILL-17]` 权益到期时直接释放并移除不确定 Hold，不恢复过期可用积分；之后才确认的真实用量记入平台损失复核，不形成用户或组织负余额，也不得扣其他权益或其他上下文钱包。

| BILL-06 | 充值创建有有效期权益包 | 权益包保存来源订单、BASE/BONUS、起止时间和余额。 |

| BILL-08 | 权益到期处理 | 到期后禁止新使用并以可审计任务处理未消费余额和 Hold。 |
| BILL-09 | 人工积分调整审批 | 申请、审批、拒绝和入账分离并可审计。 |
| BILL-10 | 管理员查看账本详情 | 按权限查询钱包、分录、Hold、调整、债务和对账。 |
| BILL-11 | 组织成员额度手动分配 | 员工无自主领取接口；分配、撤回、占用和消费全部审计。 |
| BILL-12 | BASE/BONUS 分项核算展示 | 每个组成分别显示总额、剩余、预占、已用和到期时间。 |
| BILL-13 | 组织权益在线购买入账 | 订单明确付款用户和受益组织，成功后只增加组织权益和组织钱包。 |
| BILL-14 | 人工赠送积分 30 天到期 | 每次人工赠送形成独立 BONUS 组成，不允许无期限人工赠送。 |
| BILL-15 | 退款冲销权益和账本 | 退款一次性冲销原订单全部剩余可退款 BASE，并写平衡账本。 |
| BILL-16 | RETIRED：包含增量包积分的同日消费顺序 | 增量包积分类型已从目标模型移除；保留本编号且不得复用，现行顺序见 BILL-25。 |

### 6.1 权益展示和消费

1. `[BILL-12]` 权益包分别记录和展示 `BASE`、`BONUS` 的总额、剩余、预占、已用和到期时间，并展示当前上下文可用总积分。
2. `[BILL-14]` 人工赠送积分形成独立 `BONUS` 组成，自入账起 30 天到期。
3. `[BILL-07]` 不同到期日的权益先按最早到期时间消费。
4. `[BILL-25]` 同日到期时依次消费 `BONUS`、`BASE`；组成仍相同时按入账时间和稳定 ID 排序。
5. `[BILL-15]` 赠送积分不可退款；展示页面必须说明来源、到期顺序和即将到期提醒。

### 6.2 普通退款（PAY-33、PAY-21）

1. `[PAY-33]` 普通退款必须绑定原支付订单、原 Provider 支付流水和该订单创建的具体权益包；不接受用户或管理员输入退款金额，每次只能退还该订单执行时的全部剩余可退金额。
2. `[PAY-33]` 剩余可退金额使用原订单实付金额减去已确认退款及尚未终结退款占用金额计算，并且必须与原权益包剩余可退款 BASE 对应现金金额、Provider 返回的剩余可退金额一致；任一事实不一致时拒绝发起并进入人工复核，不得自动改成较小金额。
3. `[PAY-33]` 同一订单同时只允许一个未终结退款请求；退款请求冻结计算时的剩余可退金额和原商品版本，失败后可以幂等重试，成功后该订单剩余可退金额必须为零。
4. `[PAY-22]` 发起退款后先冻结对应权益包，禁止其新分配和新 Hold，直到退款完成、失败或解除冻结。
5. `[PAY-24]` 存在该权益包关联 Hold、已消费权益或无法撤回的组织授予时拒绝普通退款；可撤回的未消费组织授予必须先从原组成撤回。
6. `[PAY-25]` 退款始终退回原支付渠道，不得转入钱包或其他支付渠道。
7. `[PAY-32]` Provider 不支持退款时，普通用户和管理员业务页面隐藏退款入口，不得只改本地状态模拟成功。
8. `[PAY-21]` Provider 确认退款后，在同一 Billing 事务中冲销原订单剩余可退款 BASE 权益、写平衡账本并更新退款记录；不得冲销其他订单、权益包或上下文，跨 Provider 状态通过幂等 Saga 收敛。

### 6.3 拒付和被动退款

`[PAY-18]` 拒付、渠道强制退款等被动资金事实必须入账。即使剩余 BASE 不足，也允许受益个人或组织钱包形成负余额，并按 BILL-26 同时登记独立应收后进入人工复核。不得扣减其他用户、其他组织、其他订单或无关权益包；应收清偿和 BONUS 隔离分别遵守 BILL-27、BILL-28，调用冻结遵守 BILL-24。

### 7.1 下单主体

1. `[PAY-03]` 个人购买保存 `payer_user_id`，受益主体为同一用户；Provider 需要外部客户而 Mapping 尚未完成时，只阻止依赖该 Mapping 的支付，不阻止登录、模型调用或组织管理。
2. `[PAY-20]` 组织购买保存 `payer_user_id` 和 `beneficiary_organization_id`；到账后只增加受益组织权益。
3. `[PAY-26]` 组织购买使用实际付款管理员的 Commerce Mapping 下单；组织级 Mapping 仅在 Provider 支持企业客户时启用，不作为通用购买前提。
4. `[PAY-04]` 服务端按受信 `product_id` 派生 Provider、SKU、金额和权益；客户端不能覆盖任何资金或权益事实。
5. `[PAY-05]` 二维码、支付金额和外部订单引用只能采用 Provider 实际返回值，不得本地伪造。

### 7.2 订单和资金状态（PAY-27、PAY-28）

核心状态：

```text
CREATED
  -> PAYMENT_PENDING
  -> CLOSE_REQUESTED
  -> LOCALLY_CLOSED_EXTERNAL_PENDING
  -> PROVIDER_CLOSED

任一未支付状态 --供应商确认收款--> PAID 或 LATE_PAID
PAID/LATE_PAID -> PARTIALLY_REFUNDED -> REFUNDED
PAID/LATE_PAID/PARTIALLY_REFUNDED -> CHARGEBACK
无法安全归并 -> REVIEW_REQUIRED
```

- `[PAY-27] CLOSE_REQUESTED`：用户或系统已经请求关闭，但尚未获得足够的外部事实。
- `[PAY-27] LOCALLY_CLOSED_EXTERNAL_PENDING`：本地不再展示二维码，Provider 仍可能收款；这不是外部支付终态。
- `[PAY-28] LATE_PAID`：订单在本地关闭或超时后收到 Provider 确认付款，资金和权益处理与 `PAID` 相同，但保留晚到标记。
- `[PAY-28]` 本地关闭后允许创建新订单。每个具有不同 Provider 支付流水的成功订单都各自幂等到账；同一支付流水的重复回调、查询或账单记录只能入账一次。

### 7.3 支付证据优先级（PAY-29）

所有回调、主动查询和账单记录先写入不可变 `payment_evidence`，至少保存 Provider、Adapter 版本、外部订单号、支付/退款流水号、金额、币种、Provider 事件时间、接收时间、序列号或版本及证据摘要。

以下均为 `PAY-29` 的验收条件，状态按资金事实强度单调推进：

1. 已确认退款或拒付事实高于已确认支付事实。
2. 已确认支付事实高于关闭、过期、未支付或处理中事实。
3. 关闭、过期或未支付证据不能把 `PAID`、`LATE_PAID`、`PARTIALLY_REFUNDED`、`REFUNDED` 或 `CHARGEBACK` 降级。
4. 渠道本身不决定优先级；签名回调、主动查询和账单只要达到同一证据等级，都按 Provider 序列号、版本或事件时间排序。
5. 同等级证据无法排序、同一流水关联多个订单、金额/币种不一致或出现非法状态跃迁时，不覆盖既有强事实，转为 `REVIEW_REQUIRED`。
6. 回调是主要实时收敛入口；主动查询补偿漏回调和不确定状态；每日账单用于独立对账，三者共用同一个状态归并器和幂等键。

### 7.4 主动关闭和查询退避（PAY-09、PAY-11、PAY-30）

Provider 支持关单时调用外部关单并核验；不支持时进入 `LOCALLY_CLOSED_EXTERNAL_PENDING`，继续服务端查询。默认查询计划如下，Provider Adapter 可以声明更慢的最小查询间隔，调度器取二者较大值并加入抖动、合并同一订单并发查询：

| 订单年龄 | 默认查询间隔 |
|---|---:|
| 0–10 分钟 | 10 秒 |
| 10 分钟–2 小时 | 1 分钟 |
| 2–24 小时 | 10 分钟 |
| 24–72 小时 | 1 小时 |

获得 Provider 已关闭、已过期或已支付终态后停止主动查询。72 小时仍无可确认终态，或查询持续失败/证据冲突时转 `REVIEW_REQUIRED` 并停止高频查询；每日对账仍继续发现晚到支付。查询期限、Provider 订单有效期和最后复核时间必须保存在订单快照中，不能由客户端决定。

### 7.5 对账与人工复核（PAY-12、PAY-18、PAY-19、PAY-31）

1. 每日获取 Provider 账单，对 Provider 账单、内部订单/支付流水、退款记录和 Billing 账本入账进行四方核对。
2. Provider 支持账单 API 时自动拉取；只支持文件时使用受控文件导入；完全不提供账单时标记 `RECONCILIATION_DEGRADED`，使用查询快照做替代核对，但不得宣称已完成供应商账单核对。
3. 每条差异保存分类、严重度、状态、责任人、证据、修复动作、复核结果和审计。
4. 拒付、重复支付、晚到支付冲突、退款失败、金额不符和非法状态跃迁进入统一人工复核队列。
5. 修复只能通过幂等领域命令和账本分录完成，不允许管理员直接改表。

| ADM-05 | 系统运行状态 | 配置驱动展示服务健康、事件积压、任务和最近错误。 |
| ADM-06 | 审计筛选、详情和导出 | 按操作者、主体、资源、动作、时间和结果查询。 |
| ADM-07 | Identity Provider 安全管理入口 | 不暴露公网，只允许受限网络、VPN 或 SSH 隧道。 |
| ADM-08 | 首个超级管理员初始化 | 幂等创建 admin 和一次性初始凭据，首次登录强制改密。 |
| ADM-09 | Break-glass 恢复 | 只通过受控离线命令恢复，立即告警并写不可删除审计。 |
| ADM-10 | 服务身份最小权限 | 服务账号、任务和 Relay 使用独立短期凭据，不继承人类角色。 |
| ADM-11 | 角色授权自动回收 | 角色到期、临时授权和紧急授权到期时自动失效并撤销缓存。 |
| ADM-12 | 审批角色兼任和交叉审批 | 允许角色兼任及两人交叉审批，但任何操作者不得审批自己的申请。 |

### 8.1 个人中心

1. `[UI-01]` 桌面用户入口常显；未登录时在 Popover 内完成密码登录、短信登录和手机注册，不跳外部浏览器。
2. `[UI-02]` 登录后显示概览、当前聊天和计费上下文、额度、权益包和用量；组织入口的显示遵守 ACC-04。
3. `[UI-06]` 登录后提供用户名、手机号、密码恢复及账号生命周期相关的资料设置入口。
4. `[UI-04]` 个人中心只展示当前聊天和计费上下文的额度。
5. `[UI-05]` 组织上下文只展示该成员获得的有效授予、权益组成和到期明细。
6. `[UI-07]` 桌面 Popover 提供打开 Web 个人中心的受信入口；URL 不携带 Access Token、Refresh Token 或其他凭据，浏览器使用自己的 OIDC 会话。
7. `[UI-08]` Web 个人中心提供个人充值入口。
8. `[UI-11]` 组织管理页中具有采购权限的管理员提供组织购买入口。
9. `[UI-03]` 不向普通用户展示模型准备、内部结算状态、供应商凭据、Token Account 或核对运维信息。

### 8.2 平台后台

后台按权限提供用户、组织、角色与权限、Billing 运营、模型与路由、支付复核、系统运行和审计页面：

- `[ADM-02]` 角色页查看角色定义、用户关联、组织成员角色、有效期和授予来源，支持授权与撤销。
- `[ADM-03]` Billing 页管理版本化计量单位、各单位价格、账本、负余额、独立应收及其清偿分配、Hold、人工调整、订单、退款、对账和复核。
- `[ADM-04]` Token Gateway 页管理模型协议及其预占公式版本、平台/组织 Token Account、路由、凭据有效性、用量证据和人工核对；凭据只显示类型、状态、更新时间和指纹。
- `[ADM-05]` 系统运行页配置驱动展示 Account、Billing、Gateway、Portal、Identity Provider、Model Gateway、NATS 和 Event Relay 健康、积压、任务和最近错误。
- `[ADM-06]` 审计支持按操作者、主体类型、资源、动作、时间和结果筛选、查看详情和导出。
- `[ADM-07]` Identity Provider 管理入口不暴露公网，只允许通过受限网络、VPN 或 SSH 隧道访问。

## 9. 超级管理员与服务身份

1. `[ADM-08]` 部署自动初始化用户名 `admin` 的首个超级管理员，使用密码学安全随机源生成一次性 8 位密码，通过交互式终端或受限 Secret 告知部署者；首次登录只能改密，初始凭据短期失效且不得进入普通日志。
2. `[ADM-09]` 全部超级管理员失效时，通过仅限主机/集群受控身份执行的 Break-glass CLI 创建短时紧急授权或恢复账号；不得提供公网恢复 API。执行后立即告警并写不可删除审计，记录运维工作负载身份、原因、目标和有效期。
3. `[ADM-10]` 服务账号不进入人类角色和组织成员表。每个服务使用独立、可轮换的短期 mTLS/OIDC 工作负载身份和最小权限。
4. `[ADM-10]` 后台任务继承所属服务身份，不拥有人工审批权限；Event Relay 只能读取/确认所属 Outbox 并向允许的 Subject 发布。服务审计记录 `actor_type=SERVICE`、服务名、任务类型和 `job_run_id`，不能伪装成人类操作者。
5. `[ADM-12]` 同一用户可以兼任计费运营员和审批员，也允许两人互相审批对方的申请，但任何人都不能审批自己的申请；大额调整、退款和组织删除不额外要求双人审批，仍须完整审计。

## 10. Provider 隔离要求

短信、Identity、Commerce、Payment、Model Gateway 和系统探针统一遵守：

以下共享验收条件分别适用于 NFR-12、NFR-13、NFR-14、NFR-15 和 NFR-17，不创建含义重叠的新能力编号：

1. 领域服务、核心状态机、数据库核心字段、公开 API 和普通用户 UI 使用供应商中立名称；厂商 Action、签名、Endpoint、请求头、状态码、响应结构、错误文本和重试限制只存在于对应 Adapter。
2. NFR-12、NFR-13 和 NFR-14 的历史记录保存创建时的 Provider ID、Adapter 版本和脱敏外部引用，不能用当前 Provider 解释旧记录。
3. 替换 Provider 不修改业务 Handler、公开 API、桌面业务流程或核心账本结构，只替换 Adapter、配置和映射。
4. 每个 Adapter 使用同一合同测试验证成功、拒绝、超时不确定、重复、乱序、状态映射和敏感信息保护。

`[NFR-16]` Provider 能力通过 capabilities 返回；不支持退款时按 PAY-32 隐藏入口，不支持其他操作时按本需求定义的降级路径执行，不能伪造成功。

## 12. 核心验收场景

### 12.1 上下文与权限

- `[ACC-23]` Web 管理组织不会切换桌面聊天和计费上下文。
- 联合验收 ACC-03、ACC-25、ACC-27：桌面切换聊天上下文后 Web 显示同一版本；已经创建 Hold 的请求仍按旧快照结算。
- `[ACC-13]` 修改请求中的角色、付款人、组织或钱包 ID 不能越权。
- 联合验收 ACC-23、ACC-24：平台后台权限不随聊天上下文改变；组织管理命令只按显式目标组织授权。

### 12.2 组织额度和删除

- 联合验收 BILL-11、BILL-18：管理员必须选择权益包及 BASE/BONUS 组成，员工不能自主领取。
- 联合验收 BILL-20、BILL-22：批量分配部分失败时成功项保留；成员移除后授予暂停且不回池，重新加入且未过期时恢复。
- `[BILL-01]` 个人钱包不能为组织请求兜底，组织钱包不能为个人请求兜底。
- `[ACC-17]` 任一删除阻断项存在时组织保持停用但不能进入 `DELETED`。

### 12.3 模型和计费

- 联合验收 TOK-18、TOK-23、TOK-24：`CATALOG_VISIBLE` 模型即使当前上下文不符合资格或具体请求无法创建 Hold 仍可展示；`CONTEXT_ELIGIBLE` 不等于请求已经 `RESERVABLE`。
- `[TOK-25]` 客户端“可调用”提示过期、上下文切换、路由失效或余额被并发请求占用时，Gateway 必须以请求时重新判断和 Hold 原子创建结果为准。
- `[BILL-04]` 请求跨价格时段仍按 Hold 创建时价格结算。
- 联合验收 TOK-08、TOK-26、TOK-27、BILL-29：每种协议用自己的版本化计量单位和预占公式；缺省公式参数为 0，所需公式、单位定义或价格缺失时拒绝创建 Hold。
- 联合验收 BILL-24、BILL-26：追加预占失败可以同时形成钱包负余额和独立应收；只冻结负数钱包对应上下文，个人负余额不影响正常组织额度，组织负余额不影响个人或其他组织额度。
- 联合验收 BILL-27、BILL-28：只有现金充值 BASE、退款追回或人工还款可以清偿应收；BONUS 不得清偿现金拒付应收，债务未清时也不得成为可用积分。
- 联合验收 TOK-11、TOK-14：Gateway 网络失败不自动重复调用上游；原请求通过证据核对收敛。

### 12.4 支付和退款

- `[PAY-28]` 本地关闭后可以创建新订单，旧订单晚到付款按 `LATE_PAID` 单独幂等到账。
- 联合验收 PAY-06、PAY-29：同一支付流水的回调、查询和账单重复出现时只入账一次。
- 联合验收 PAY-27、PAY-29：未支付证据不能覆盖已支付、已退款或已拒付事实；金额冲突进入人工复核。
- 联合验收 PAY-24、PAY-33：普通退款绑定原订单和权益包且只能退完当前全部剩余可退金额；有消费、Hold 或不可撤回授予时被拒绝。
- 联合验收 PAY-18、BILL-24、BILL-26、BILL-27、BILL-28：拒付余额不足时双记受益钱包负余额和独立应收，不扣其他权益；只冻结对应上下文，并按限定来源清偿。
- 联合验收 PAY-12、PAY-19：每日四方对账差异具有状态、责任人、修复动作、复核结果和审计。

### 12.5 品悟客户端旧模型路径迁移与切换

- 联合验收 SCOPE-01、SCOPE-04、SCOPE-05、TOK-28：迁移只处理客户端拥有的数据；旧内置路径数据被清理或转换，本地独立模型保持不变，服务端数据和代码零变更。
- `[TOK-28]` 对相同旧配置连续执行两次迁移、在每个持久化步骤后模拟中断并重启，最终新配置和凭据状态必须一致且无重复；报告不得包含密码、API Key、Access Token 或 Refresh Token 明文。
- `[TOK-29]` 所有升级场景均必须证明平台模型请求只发往 Token Gateway；账号平台不可用、用户未登录或模型无法映射时明确失败或要求用户操作，不向旧 New API 发送请求。
- 联合验收 TOK-28、TOK-29、NFR-09：切换证据齐全后才删除客户端迁移临时备份和旧凭据；新构建不包含运行时旧格式解析、旧服务调用或兼容开关。

## 13. 明确禁止的行为

- `[PAY-04]` 禁止客户端提交或覆盖充值金额、SKU、权益、付款人、受益组织或支付成功状态。
- `[PAY-05]` 禁止本地随机生成真实 Provider 支付二维码。
- 联合验收 PAY-09、PAY-31、PAY-32：禁止 Provider 不支持时仅修改本地状态模拟关单、退款或对账成功。
- 联合验收 CORE-05、TOK-06：禁止普通用户查看真实供应商密钥、模型网关管理凭据或内部服务 Token。
- 联合验收 SCOPE-02、TOK-05：禁止在个人中心新增用户供应商 Key、自管 Token Account、共享策略或路由管理。
- `[TOK-14]` 禁止 Gateway 因网络失败自动重发模型请求。
- `[ACC-10]` 禁止有效组织没有所有者或同时存在多个所有者。
- `[ACC-23]` 禁止组织管理动作隐式切换聊天和计费上下文。
- `[BILL-01]` 禁止个人与组织钱包、权益、路由或审计互相兜底或混用。
- `[PAY-13]` 禁止把开发支付模拟器或 Mock Model Gateway 描述为生产能力。
- 联合验收 SCOPE-01、TOK-28：禁止以旧路径迁移为由删除、改写或上传本地独立模型和用户自配第三方模型的配置及凭据。
- 联合验收 SCOPE-05、TOK-29：禁止为完成客户端切换而修改账号平台服务端、数据库、接口或部署；发现服务端前置能力不满足时必须阻止切换。
