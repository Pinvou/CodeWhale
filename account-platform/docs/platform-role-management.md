# Platform role administration

ADM-05 restores the existing `/admin/v1/roles` and `/admin/v1/role-bindings` GET, POST and DELETE entry points, the authenticated Portal BFF allowlist and the actual Admin roles workspace. The catalog and association page expose PLATFORM facts only, with the existing 500-row repository bound and optional exact target user-ID filter. Organization membership/role management retains its existing separate entry points.

The delivered permission vocabulary now includes the already seeded `platform.roles.read` and `platform.roles.assign`. Writes retain the original `ACCOUNT_ROLE_BINDING_GRANT` and `ACCOUNT_ROLE_BINDING_REVOKE` AuditOnly classifications, policy version 1, no second approver, and no new permission. The platform HTTP repository revalidates the current active human and live assignment authority inside the write transaction, after UUID-ordered USER locks and assignment locks. Expiry uses the current database clock after lock waits. Ordinary grant/revoke cannot administer PLATFORM_SUPER_ADMIN, OWNER, PERSONAL or unassignable roles; dedicated high-privilege lifecycle/recovery remains separate. A disabled target cannot receive a grant, while revoking an existing target grant remains possible.

PLATFORM_AUDIT_PII_EXPORT retains its existing expiry requirement, at most 24 hours from starts_at, existing 10–500-byte reason validation and recent-authentication check. A canonical HTTP 401 RECENT_AUTHENTICATION_REQUIRED is an explicit pre-write rejection. A first invocation can offer the existing sign-in entry after that rejection. It is not evidence about an earlier uncertain invocation; unknown state always retains the original command and cannot guide automatic cross-page retransmission.

A grant freezes target, role, organization/unit scope, normalized microsecond time bounds, reason, actor and idempotency key. Both original AdminGrantRoleBinding repository branches now compare the full intent before replay (Issue #1931). An omitted start reuses the original grant time. The existing assignment plus its transactionally written original audit supply the facts; no historical SQL identity or row is rewritten. The admin key is serialized and checked across admin target/scope namespaces, so changing target cannot manufacture a new grant under the old key. Ambiguous legacy duplicate keys, absent audit proof or a reason not provable from an old audit fail closed for controlled review. Other existing organization command writers retain their own key namespace. No organization HTTP entry point was added to consume the old generic Admin method.

Same-key replay returns the current persisted projection, including revoked/expired state, without an additional grant, authorization version, grant audit or event. Different actor/body/scope/time facts conflict without those effects. Revoke requires current assign authority and returns the authoritative revoked/expired projection; it never grants or revives a role. USER precedes direct assignment mutation in the existing expiry worker as well, preventing its projection/FK writes from reversing the new management writer's lock order. Expiry eligibility and policy are unchanged.

The UI verifies current authenticated user, permission and live client epoch before dispatch, binds grant ACKs to actor/target/role/time/source and revoke ACKs to the original binding/revoking actor, retires late reads on owner/selection/epoch/authorization changes and prevents concurrent mutations. Unknown ACKs retain one original immutable command per client/human in memory, including navigation away/back using that client. Only original-key retry or authoritative read is available; fields/new commands remain blocked. Successful ACKs remain successful when a subsequent refresh fails.

The Web workspace restores the role catalog, localized names and descriptions, grouped permission details, separate grant-management view with twenty-row pagination, binding detail drawer and reviewed grant wizard from the original UI. Complete user codes use the existing exact `user-code-lookups` endpoint; username/display-name search uses the user directory. Both are available only with `platform.users.read`; operators without that permission can enter an exact user ID. The wizard freezes the reviewed command before confirmation and retains the same dispatch/ACK safeguards. Catalog search and grant-list filters/pagination are read-only and retain their state across the two role views. `role_view=catalog|bindings` and the existing `role_user_id` filter are reflected in navigation; workspace changes reset the page below the fixed header. Clearing or restoring `role_user_id` through browser history also refreshes the applied filter, and user-detail shortcuts explicitly open grant management. A late ACK does not navigate away from another workspace. Replayed grant ACKs report the returned current status, including revoked or expired; they never imply a fresh active grant. An uncertain command visibly retains its original target even when the read-only list filter changes. The catalog still exposes PLATFORM roles only; organization roles remain in organization management.

There is no new sessionStorage/localStorage retention. Full-page reload, sign-out or a new client loses local uncertain-command memory: inspect authoritative role associations and audit before deciding another action. No automatic cross-reload recovery, replacement-key retry or real browser reauthentication E2E is claimed. All three languages state this boundary. The Portal build is generated through the project npm command; the integration author rebuilds final combined assets. The mounted Admin UI is exercised in controlled browser fixtures, including cancellation/focus, responsive layouts, changed authority, unknown ACKs and failed post-ACK reads. Production role grants and real browser reauthentication are not part of that fixture evidence.

Formal tests use published Account migrations and real account_service runtime roles in disposable UUID databases. They exercise actual Account HTTP, actual Portal session/CSRF proxying, current-authority revocation, original-key/full-intent replay and no-effects, PII/time/source bounds, lock-wait expiry, USER/assignment expiry ordering and explicit no-write reauthentication. The frontend tests exercise the actual Admin client over controlled loopback HTTP and the state/ACK contracts. The identity verifier, human actors and external browser environment remain controlled; no site deployment or real credentials were used. The old Issue #1931 remains open until the maintainer reviews/merges the fix; this work does not close it automatically.
