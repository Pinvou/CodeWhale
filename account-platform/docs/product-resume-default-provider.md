# 默认健康渠道的商品恢复

渠道控制行缺失仍表示既有的 `AVAILABLE / version 0`，与渠道管理和下单门禁一致。商品恢复草稿仅读取这个虚拟初始状态，不新增控制行，也不改变双人审批、目录准入、可信探测或商品暂停条件。

`PAYMENT_PRODUCT_RESUME` 的共享审批证明编码允许这一渠道字段为 0，并严格要求 normalized、critical、financial 三处事实一致。商品、目录、准入和映射版本仍必须为正；`PAYMENT_PROVIDER_RESUME` 仍只接受已持久暂停的正版本，不共享商品恢复的例外。现有策略/证明版本、封闭字段集合、规范整数格式和历史非零证明摘要均不变。Account 与 Billing 的证明、授权事件生产者和消费者继续使用同一编码实现。

执行冻结了版本 0 的审批时，恢复事务在原有目录与控制锁序内，尝试插入一个 `AVAILABLE / version 1` 控制行。只有本事务插入成功才能匹配虚拟版本 0；已存在行或并发创建行不能被当作同一个快照，须重新申请审批。插入与商品恢复、执行记录、Outbox 同属原串行化事务，任何后续验证失败都会一起回滚。既有非零版本控制行继续按原版本精确核验，渠道暂停不会被本操作解除。

执行记录保留审批时实际观察的 `provider_control_version=0`，不篡改为事务内新建行的版本。并发暂停通过相同唯一键及串行化事务参与冲突判定；恢复不得覆盖它，不吞掉数据库冲突，不自动重做资金或审批操作。

`TestProductResumeDefaultProviderPostgres` 使用一次性 PostgreSQL 数据库和真实领域入口验证草稿零写入、缺行成功恢复、失败整笔回滚、已存在可用/暂停行的旧快照拒绝、真实并发暂停，以及已有可用版本的正对照。新增闭环使用生产异常观察、认领和失败确认写入器重建 owner 事实，再经过真实证明编码、Account 共用解码、新的执行探测和领域恢复，保留原版本 0。`TestProductResumeDefaultProviderProof` 验证旧投影、证明和新授权事件的编解码，以及越界版本、不一致事实和非规范零值的拒绝。探测事实由生产观察写入器生成；支付订单及渠道响应为受控数据。这些验证不等于 Account HTTP/IdP 双人审批、真实渠道付款或部署验收。
