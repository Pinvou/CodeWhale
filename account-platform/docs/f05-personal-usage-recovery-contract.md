# F05 个人用量与原调用取消回执

个人用量列表和详情按已持久化的用户身份及个人资源范围授权：目标 `user_id` 必须匹配，`organization_id` 必须为空。历史详情不绑定创建调用时的登录会话，因此重新登录后仍可查看自己在列表中看到的个人记录。原调用的冻结 session、供应商及幂等重放行为保持不变；此处不扩大组织调用能力。

`GET /v1/me/usage-requests`、`GET /v1/me/usage-turns` 和 `GET /v1/usage-requests/{usage_request_id}` 继续要求个人上下文及 `personal.usage.read`。详情原有状态、金额、序列及时间字段保持兼容。另一用户或组织资源返回 404。

`POST /v1/usage-requests/{usage_request_id}/cancel` 使用 Bearer 用户身份、稳定用户权限 `personal.usage.cancel` 和稳定的取消 `Idempotency-Key`（16–128 字符），无请求体。依据 TOK-38，原调用用户可以停止自己的个人或组织调用；当前上下文切换或原组织成员关系失效不会撤销这一降低后续成本的动作，但身份自身仍必须通过现有授权，不能借取消绕过禁用或权限拒绝。

HTTP 从持久调用读取原用户及原组织，不能使用调用者当前上下文或输入指定组织。个人仓储入口继续只接受空组织；组织调用经独立入口，在与派发共用的行锁下精确复核原用户及显式原组织。历史可选快照字段缺失不改变持久资源所有权。个人列表与详情仍按原上下文隔离，不因原调用取消恢复而扩大读取权限。

派发后的取消仅停止投递，返回 `UNSUPPORTED` 等真实状态，不能推断供应商执行停止或释放预约资金。未派发取消仍复用持久取消、可信预约恢复及释放确认流程。200 是当前持久回执；202 表示释放回执未知，应继续查询并沿原命令恢复。组织调用的未知释放继续保留原有恢复或人工核查状态；本次不扩大个人预约到期证明、24 小时释放政策或其资金权限，也不能从 Billing 已释放但回执未知推断 Token 已确认释放。

## 丢失 usage header 的只读恢复

成功接受调用时，模型接口提供 `X-Pinvou-Usage-Request-ID`。丢失该响应头时，客户端可使用原调用身份查询：

- `GET /v1/usage-requests/by-idempotency-key`
- `Authorization: Bearer <用户身份>`
- `Idempotency-Key: <原模型调用键>`，16–128 字符，服务端去除两端空白后计算原 SHA-256 身份。
- 权限为稳定用户权限 `personal.usage.cancel`；当前上下文选择或原组织成员关系失效不影响原用户回执恢复，身份自身的权限拒绝仍返回 403。

200 仅返回 `usage_request_id`、`execution_status`、`delivery_status`、`cancel_status`、`settlement_status`，不返回模型请求内容、凭据或密钥。查询作用域固定为原稳定用户及原调用键，目标必须属于当前用户；个人与组织调用都只能恢复自己的原事实。另一用户复用相同原始键不能读取或取消别人的调用。此 GET 不写取消命令、不执行模型调用、不释放资金；响应为 `Cache-Control: no-store`。

404 `TOKEN_NOT_FOUND` 只表示当前无法找到属于该用户的原调用事实（个人或组织），不能证明原请求没有效果。客户端须保留原调用及取消身份，继续查询或提示未知状态；不得通过重发模型 POST、创建新键或猜测 usage ID 恢复。权限不足、无效键及暂时错误也不提供无效果保证。

## 追加预约回执未知的结算证据

可信最终用量超过原预约、但追加预约收到传输或服务错误时，继续遵循既有 `TRUSTED_FINAL_USAGE` 结算规则，不把未知回执当成余额不足，也不据此判定追加预约没有发生。Token 在流式和普通 JSON 的持久响应/结算快照中记录 `additional_reservation`：`status=ACK_UNKNOWN`、原预约上限、可信实际金额及既定结算规则。正常提交、提交等待和恢复均保留该证据；不保存原始错误文本、凭据或上游私人数据。

这项记录供财务核查和恢复使用，不新增或伪造 `WALLET_INSUFFICIENT` 用户提示，不更改超额形成应收的既有资金策略。只有真实钱包或成员额度不足才使用已有提示协议；新增通用用户提示不在本次契约调整内。

## 管理员集合与预约到期

管理员分页关闭时的用量集合使用与分页集合相同的安全摘要，保留用量 ID、模型、执行/投递/取消/结算状态、金额和必要时间；不输出用户会话、钱包、凭据、供应商请求、请求指纹或原始证据。详情与证据继续使用分别授权的入口。

到期时间不证明未派发。旧 `ExpireHolds` 内部入口显式返回 `ErrHoldExpiryProofRequired`，不释放资金；真实后台仅使用带可信 Token 证明的恢复 worker。没有可信未派发证明的过期预约保留 ACTIVE 状态及预约余额，并登记独立 MANUAL_REVIEW 恢复记录；可信释放已提交但回执丢失时，原持久恢复记录继续确认该 RELEASED 预约，不重复放款。已过期预约续租返回 409 `BILLING_CONFLICT`，数据库时钟围栏拒绝时，金额分配和租约事件一并回滚。只有已持久阻断派发、可信释放及本地确认闭环才能完成恢复。

流式逐 chunk 查询的性能观察跟踪于 Issue #1595；本次保留既有取消投递检查。

## 活派发所有者与错误响应回放

原派发租约上限仍为10分钟，上游预算仍为2小时。真实领取的本地所有者每4分钟续租，覆盖调用到回执持久化的收口；每次续租写入限时10秒，不重新领取、解密意图或派发。过期或异主所有者不能续活、写入流或覆盖恢复状态。恢复扫描只提供候选，锁内重新核对所有者、租约和执行状态；已有完整回执或结算不能被迟到的扫描降为未知。

完整回执已经持久化的结算等待或已确认终态正常停止续租；未证明收口的 REVIEW 等失活状态必须取消原上游，不能静默退出续租。该机制不改变原预约续租、释放或结算权限，也不新增整体收口时限。

非成功上游响应沿用2MiB完整读取限制。超限或中途读取失败不把前缀作为完整响应持久化或回放；保留已获 HTTP 状态及既有适配器可信的生成前拒绝证据。可信生成前拒绝仍按原预约身份释放，未知用量继续核查；未知释放回执不得宣称本地已释放。

## 已派发但缺上游引用的24小时截止

另有一项独立于未派发到期证明的保留策略：仅已由持久意图真正派发、未捕获上游请求引用，且原个人预约、模型、价格及请求冻结事实完整有效的调用，按原 `started_at` 满24小时处理。仍处于有效执行预算/租约内的任务不据此释放；错误预约、价格、快照、历史适配身份、无有效派发记录、有效最终用量及确定结算冲突继续人工核查。

Token先持久化原 usage/hold 身份的待释放意图，随后在Billing原wallet→hold锁下校验完整冻结前置条件并恢复同一预约释放。200必须包含原身份的 RELEASED 回执；未知回执保留同一意图重试，不声称资金已释放。不新建预约、不改键、不重新调用模型、不以取消投递推断供应商停止。

确认释放后，Token在同一事务登记不可变平台损失、禁止迟到用量再向客户扣款、完成该预约释放状态并停止自动对账。原投递/取消事实保留。迟到数字仅作为证据，不延长内容留存、不重开结算、不允许管理员重试制造新客户扣款。若Billing原COMMITTED事实先赢得资金锁，则不会把该事实伪报为释放或退款；保留确定冲突人工核查。

扩额入口在任何 Billing RPC 前核验截止意图，迟到扩额回执也不能改写 Token 已冻结的原金额。该预检查不构成跨库原子授权：已经通过检查的扩额若先在 Billing 提交，完整冻结金额校验会拒绝释放，保留原意图及确定冲突人工核查，不放宽金额检查、不伪报客户资金释放或平台损失。

滚动升级须先升级 Billing，再启用 Token 的此恢复路径：旧 Billing 会拒绝新的冻结前置条件字段，不能把拒绝当成释放成功。已有待释放意图时，须保留识别该意图及禁迟扣事实的 Token worker 直至恢复闭合，不能回退到不识别这些事实的旧 worker；正常旧释放调用及原迁移身份不变。

取消记录中的 `cancel_reconciliation_deadline` 当前只持久化元数据，没有独立运行时截止消费者；它不触发自动释放，也不替代上述未派发证明或已派发缺引用的 24 小时策略。保留原值及迁移身份，不因字段名称推导新的资金处置规则。到期恢复的慢证据公平调度、串行对账旧领取写回隔离由 Issue #1903 分别跟踪，本轮未修；现有资金证明、幂等与终态围栏保持，尚不能宣称多实例慢批次容量验收通过。

## 已捕获引用的原24小时缺证决定

普通对账已持有上游引用、满原24小时且本轮查询无结论时，必须在同一usage行锁内重读现有可信数字及绑定的历史Lookup证据。领取快照、本轮查询失败和000015复制的普通非数字metadata都不能证明没有可信用量；有效最终数字（包括零）、既有结算或矛盾数字均阻止缺证释放并保留人工核查，不能任选数字扣款。

供应商明确拒绝且无用量的Lookup、适配器已确认的生成前拒绝也在同一行锁下发布。先发布的真实拒绝事实阻止另建缺证决定，保持原拒绝释放及其RPC错误语义；若截止决定先持久化，迟到拒绝仅保留审计并在原Release RPC前停止，不因拒绝结果绕过人工恢复门闩。拒绝事实不伪造零用量，也不授权选数扣款。

无可信用量时，先以原usage/hold/wallet/price/最大额及原provider/adapter/reference摘要持久化独立的captured-reference释放决定，同事务关闭既有stopped门闩，提交成功后本调用才有一次原Hold Release RPC许可。Prepare提交失败或结果未知不得发RPC。读到历史intent本身不授发送权：错误、未知ACK或进程crash（包括持久化后尚未发RPC）都保持人工恢复，不增加后台扫描、自动开闩或ACK重试。原missing-reference的个人完整快照资格及自动ACK恢复仍是独立分支，不能把本决定放进它的循环。

确认只接受原usage/hold/wallet、price的精确nil/非nil语义、最大额及RELEASED状态的完整有界回执，不给ORG或历史格式套用PERSONAL完整pricing证明。成功后仍为原REVIEW/REVIEW及TRUSTED_USAGE_DEADLINE_EXCEEDED平台损失，原用量、投递、取消及财务身份不改；未确认不写已释放损失。迟到数字仅保留审计，不能Extend/Commit、重开对账或被新waiver取代。

人工恢复通过已有TOKEN_USAGE_RECONCILIATION_RETRY权限、预检、当前版本/证据水位CAS及审计，对同一usage/hold和原intent显式重新排队。每个新的受权人工命令最多开闩一次；已完成governed command原键重放只返回原结果，不再次排队。恢复仍失败时需新人工命令继续原决定，不能改成新usage、新本金决定或改选迟到数字扣款。先已存waiver/missing-reference决定与旧loss继续归原所有者，旧loss不回填、不追扣。

若原正额扩额已提交而ACK丢失，Token最大额可能仍旧。仅在严格200同Hold RELEASED回执确认后，若最大额更大，可用原固定final-extension操作ID、lease900和差额发一次既有操作回执验证。Billing必须命中原精确fingerprint，且旧ACK身份及最大额与释放回执相等、减去原additional后精确等于冻结最大额；证明随原确认/loss保存，原intent不改。正常等额不加请求；任何不匹配、旧版本操作事实不同、201、未知或错误仍人工，不枚举或自动重试，不从扩额证明重构可信用量。终态旧操作重放不扩额、续租或新增Billing回执。
