# F02 支付与退款恢复边界

本文件说明本轮修复的恢复行为，不代表真实渠道或生产部署验收。

## 创建支付订单

相同请求及 `Idempotency-Key` 绑定同一订单，首次创建返回 HTTP 201，重放返回 HTTP 200；订单 ID、金额与既有 JSON 字段保持兼容。渠道处理尚未完成时可以返回待处理订单，但不能将这个无支付链接的中间结果固化成永久成功回执。渠道完成后重放返回持久完成回执。

只有持久状态证明尚未开始渠道创建时才能启动创建。已经开始但结果不确定时按原商户订单号查询，不把“不知道结果”解释为“没有创建”。客户端遇到响应丢失须保留原键与原请求，不另建订单。

## 异常处置

`POST /admin/v1/payment-anomalies/{case_id}/resolve` 要求既有管理权限、当前有效认领、至少八字符的 `Idempotency-Key`，以及包含 `resolution` 和至少十字符 `reason` 的 JSON。处置意图绑定案件、操作者、键、动作及理由；不能用另一操作者或相反动作替换尚未完成的金融处置。金融效果已提交但案件回执失败时，恢复读取对应持久效果，不重复记账。

界面只提供案件类型允许的动作。未知类型不提供处置选项。人工理由不是渠道证据。

意图受理后尚未完成的错误统一返回 HTTP 503 和 `COMMAND_RESULT_UNKNOWN`，客户端保留原幂等键及请求事实并重试。受理前的参数、权限或绑定冲突仍按原 4xx 拒绝；不能把受理后的不确定结果当作允许创建新键。

## 退款对账

`REFUND_FAILURE` 支持 `RECONCILE_REFUND`。服务使用原商户退款号调用明确声明退款幂等能力的受信任渠道；只有匹配退款号、金额及明确终态的结果才能扣销或释放原预留。成功结果还必须有渠道退款标识。未知结果、字段不匹配或缺少能力时保留人工复核及资金预留。

对账仍受拒付、强制退款与应收余额围栏约束，不能借“对账”绕过另一金融处置。渠道调用有超时限制，并在一致的钱包、订单、退款锁边界内重新核验。`DISMISS` 只处理案件，不宣称释放退款资金；`ESCALATE_FINANCIAL_REPAIR` 保持待处理状态。

当前渠道身份及版本必须匹配订单冻结的渠道身份及版本，否则拒绝外呼。共同资金门闩与渠道调用使用最长 30 秒的 context；取消后必须释放事务锁，不阻止其他金融处置继续处理。

## 同源强制退款处置预算

不同供应商退款号仍分别保存原始证据并进入人工审核；收到第二笔事实不等于允许再次全额扣销或新增应收。处置在共同钱包、订单与来源包锁内核验已应用回执及累计现金预算，累计不得超过原付款。无法证明来源、历史处置或互斥关系时保持人工审核，不改写旧资金事实。

按用户选择，本轮交易已有成功普通退款后又收到强制退款时，保留新证据及冻结状态，转人工核实，不继续处置资金；未完成普通退款的未知结果也不能被强制退款覆盖。完整混合退款金额与积分模型另行实现并验证。

同源分批强制退款的权益增量按累计比例目标与此前目标的差计算，不对每一笔独立向上取整。BASE 预算计入应收原始额度，偿还应收不会恢复处置预算；BONUS 不足保持既有不追加追偿的行为。

每次已审处置保留不可变 `FORCED_REFUND` journal。权益增量为零时 journal 没有 posting，仅作为现金预算及幂等重放的审计回执，不写零额 posting，不新增积分扣除或应收。旧记录没有可信回执时不能把版本或终态当作已完成或零效果的证明。已确认拒付同样需要匹配来源的不可变回执才能返回完成重放。

## 支付通知来源

通过受信任渠道验签的通知，在入队时保存服务端确定的渠道身份与版本，不能使用通知正文自报值。处理时将持久来源与订单冻结渠道、处理实例渠道一并核对；即使先由另一渠道入队、再切回原渠道，也不能将该通知记到原订单。重复通知 ID 必须保持原来源及支付事实。

历史通知没有可靠来源时不按当前配置回填。已完成回执保持只读；待处理通知保留原事实，停止自动入账并等待人工对账，不能把缺失来源解释为可信证据。

## 旧拒付数据

旧 `RESOLVED` 记录没有可靠区分确认拒付与驳回。按照用户决策保留原状态和证据，禁止自动资金处置，等待人工核实。兼容迁移不得猜测、映射或临时替换这类状态。对这类旧行保留尚未验证的状态约束时，必须披露并通过独立数据库测试证明新写仍受约束；人工确认和后续约束验证属于另行跟踪事项。
