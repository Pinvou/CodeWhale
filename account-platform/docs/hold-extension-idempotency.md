# 追加预留金额的操作幂等

`POST /internal/v1/holds/extend` 保留原工作负载鉴权与增量金额语义。
正增量必须携带非零 `operation_id` UUID；同一次逻辑追加的传输重试与恢复复用该 ID，
另一笔独立追加使用另一 ID，即使金额相同。不能按金额或 hold ID 去重。
`additional_microcredits=0` 仍是普通续租，operation ID 省略或为空 UUID；非零 ID 被拒绝。

请求事实包括 usage、hold、操作身份、追加金额及规范化的租期秒数。
省略或 0 秒仍归一为 900 秒，显式租期保持 30–1800 秒。
时间戳和本次接收时间不属于请求身份，重试不能用刷新时间绕过重复检测。

Billing 在既有 `idempotency_records` 的独立 `usage.hold.extend` scope 中，
与钱包、权益分配、hold 及租约事件在同一事务保存原请求摘要和完整成功 Hold 回执。
不覆盖成功记录；已有成功 ID 与任何不同事实冲突，且零额外财务效果。
完全回滚且没有成功回执的失败请求不永久占用 ID，这与原成功回执模式一致。
不修改迁移、旧租约事件、余额政策或已存在的失败／结算收敛流程。

成功重放返回第一次成功的 Hold 快照，不再次冻结余额、累加最大值或续长租期。
即使后来有别的追加、续租、到期或结算，原成功回执也只表示该操作的历史结果；
它不能替代当前 hold 状态、签名到期证明、精确最大值及定价事实核验，
也不能用于推断尚未派发或授权释放余额。
该 scope 沿用既有长期财务成功回执存储方式，查询不按 expires_at 失效，
不能套用响应内容的 30 天清理规则或清理后复用操作 ID。

新操作保留 Serializable、钱包先于 hold 的锁序、租约到期与可用余额门禁。
仅确定整个事务已回滚的序列化冲突或该回执插入竞争可有界重试；
首次请求的租约截止固定，不随本地重试刷新。未知提交结果不能当成未执行再次累加，
后续尝试仍使用原 ID 读取回执。没有新增自动 HTTP 重试。

当前 Token 只有最终用量追加一个逻辑槽，使用已持久化的 usage、hold 身份及版本域
派生稳定 UUID；不把金额、当前额度上限、时间或客户端字段用于产生新身份。
JSON 与 SSE 共用该槽。普通定时续租不使用该槽。
明确成功 ACK 后，本地只把上限单调投影到已校验的实际用量目标，
同 ACK 重放不再次累加，较低目标不降低已有上限，截止释放栅栏继续生效。
恢复结算仍沿用既有幂等 Commit，不重新派发模型或新增收款动作。

公开财务 PostgreSQL 门禁保留原 Token 全包，并必跑本地上限投影回归；
另以真实 Billing 运行角色执行追加幂等、原个人 hold、锁后时钟和过期续租回归。
这不等于真实供应商、支付、跨部署升级或发布验收。
