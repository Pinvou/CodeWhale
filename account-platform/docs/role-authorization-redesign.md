# 管理后台「角色与权限」全新设计评审稿

> 状态：交互与业务设计评审稿
> 日期：2026-09-01
> 范围：角色目录、权限查看、角色授权、授权记录，以及用户/组织详情中的角色信息去重

## 1. 结论

当前页面不应继续以“角色卡片全集 + 内嵌授权表单 + 长授权记录”的单页形态扩展。新方案将页面改名为「角色与权限」，形成两个主工作区：

1. **角色目录**：唯一、权威地展示角色定义及其权限。
2. **授权管理**：查询有效/历史授权，通过引导式流程新增或撤销授权。

角色变更审计不再挤在主工作区内，而是进入现有「审计与导出」页面的独立筛选视图。用户详情与组织详情不再重复渲染完整角色目录，只展示当前对象的有效角色、作用域和权限摘要，并提供跳转到角色目录的入口。

## 2. 当前问题与评审意见

### 2.1 功能闭环

| 问题 | 评审结论 | 新设计处理 |
|---|---|---|
| 只见角色、不见权限 | 成立。角色接口已经返回 `permissions`，但界面没有使用，导致管理员无法判断角色实际能力 | 角色目录增加权限数量；角色详情按领域和操作分组展示中文名称与原子权限代码 |
| 角色作用域全部显示为组织 | 成立。现实现仅识别 `UNIT`，其余作用域一律渲染为组织 | 完整支持 `PERSONAL`、`PLATFORM`、`ORGANIZATION`、`UNIT` 四类作用域，并使用不同标签和说明 |
| 授权依赖手工输入 ID | 成立。原始 UUID 不应成为主要操作方式 | 用户、组织使用可搜索选择器；节点使用组织内树形选择器；原始 ID 仅在详情中供复制 |
| 操作日志挤在主页面 | 成立，但需区分「授权记录」与「审计日志」 | 授权记录留在授权管理；操作审计使用现有审计事实源，通过独立筛选页查看，避免第二套日志 |
| 管理员创建平台角色 | 有价值，但不是当前已具备能力 | 作为第二期受控能力设计；第一期不显示不可用的生产按钮 |
| 三处重复展示角色定义 | 成立，且代码中使用了同一组件重复渲染 | 角色定义只保留在角色目录；用户/组织详情改为对象上下文摘要 |

### 2.2 现有页面的其他问题

- 18 个大卡片扫描效率低，英文角色代码与英文说明喧宾夺主，也没有搜索、作用域筛选或可授权状态筛选。
- 角色定义和旧授权模块使用两套视觉系统，间距、表格、按钮及内容宽度不一致。
- 授权表单没有先确定作用域，导致组织、节点字段常驻，操作者无法理解哪些字段是必填、互斥或无效。
- 可选角色在前端硬编码，不能保证与服务端角色定义、`assignable` 状态及后续迁移一致。
- 特殊约束没有在操作前解释，例如个人生命周期角色不可手工授予、所有者和超级管理员使用专属流程、临时 PII 导出需要短有效期与原因。
- 授权记录缺少组合筛选、游标分页、详情查看和撤销影响预览，数据量增长后不可维护。
- UUID 被当作主信息展示，用户名、显示名称、组织名称等业务可识别信息不足。

## 3. 新信息架构

页面名称由「角色与授权」调整为「角色与权限」，突出管理员首先要理解“角色包含什么权限”，授权是后续动作。

### 3.1 页面头部

- 标题：「角色与权限」。
- 说明：「查看平台、个人与组织作用域的角色权限，并管理用户授权。」
- 主动作：具备 `platform.roles.assign` 时显示「新增授权」。
- 次动作：「查看变更记录」，跳转至审计页并预置角色相关资源筛选。
- 只读管理员不显示写入动作，不用禁用按钮暗示其可申请未拥有的能力。

### 3.2 主工作区

#### 角色目录（默认）

工具栏包括：

- 按角色中文名称、代码、权限代码搜索。
- 作用域筛选：全部、个人、平台、组织、组织节点。
- 类型筛选：全部、系统内置、自定义（第二期启用）。
- 可授权状态筛选：可直接授权、专属流程、生命周期自动维护。

列表以紧凑表格替代大卡片：

| 字段 | 展示规则 |
|---|---|
| 角色 | 中文名称为主，稳定代码为辅 |
| 作用域 | 明确显示个人/平台/组织/组织节点 |
| 权限 | 权限数量；高风险权限另加风险标识 |
| 类型 | 系统内置/自定义；系统内置不可编辑 |
| 授予方式 | 直接授权/审批或专属安全流程/系统生命周期 |
| 状态 | 生效中/草稿/已停用（后两项为第二期） |
| 操作 | 查看；满足权限与生命周期约束时可“授权” |

点击行打开右侧详情抽屉，保留列表上下文。详情包括：

1. 中文名称、代码、作用域、类型、状态、描述。
2. 权限按「身份与组织、财务、模型与 Token、治理与安全」等领域分组。
3. 每项权限同时显示可理解的中文名称和原子权限代码。
4. 授予方式、期限限制、互斥职责和专属流程说明。
5. 可授权时提供「授权此角色」入口；不可授权时明确说明真实原因。

#### 授权管理

顶部仅保留一个主动作「新增授权」，下方为可筛选、可分页的授权记录表。

筛选项：用户、作用域、角色、组织、状态、授权来源、有效时间。默认展示当前有效与待生效记录，可切换查看已撤销和已过期记录。

表格字段：

| 字段 | 展示规则 |
|---|---|
| 用户 | 显示名称/用户名为主，用户编码为辅；UUID 进入详情后复制 |
| 角色与作用域 | 中文角色名、代码、作用域标签；组织或节点名称作为次级信息 |
| 有效期 | 生效时间至到期时间；永久授权明确标识 |
| 来源 | 管理员、组织创建、账户生命周期、安全引导等可理解文本 |
| 状态 | 待生效、有效、已过期、已撤销 |
| 操作 | 查看；满足服务端规则时显示撤销 |

点击记录打开详情抽屉，展示完整 ID、授权人、创建/撤销时间、原因、请求 ID 与关联审批；审计事件通过链接进入独立审计页。

## 4. 新增授权流程

「新增授权」使用右侧四步抽屉，不在主页面常驻大表单。

1. **选择用户**：按用户名、显示名称或用户编码搜索；不提供邮箱搜索，因为当前系统没有可靠邮箱事实源。
2. **确定作用域**：先选平台/组织/组织节点。组织作用域显示组织选择器；节点作用域继续显示组织内节点树。个人生命周期角色不可进入普通授权流程。
3. **选择角色与有效期**：角色列表实时使用服务端角色目录和 `assignable` 规则过滤；支持立即或定时生效、永久或到期时间。特殊临时权限执行服务端限制。
4. **预览并确认**：汇总用户、角色、作用域、权限数量、高风险权限、有效期、原因、审批/近期认证要求和受影响会话。提交后显示明确结果和审计入口。

角色、组织和节点之间为级联关系。更改上游选择后必须清空已不再有效的下游值，避免提交残留 ID。

撤销授权同样先显示影响预览，并由服务端决定是否允许。所有者、个人生命周期角色、最后一个超级管理员等保护规则不能只在前端隐藏按钮。

## 5. 三处重复内容的去重规则

### 5.1 角色与权限页

这是角色定义的唯一目录，负责解释“系统有什么角色、每个角色包含什么权限、如何授予”。

### 5.2 用户详情

删除完整角色定义区，保留：

- 当前用户的个人、平台、组织和节点角色，按作用域分组。
- 每个角色的状态、有效期和来源。
- 合并后的有效权限摘要与高风险权限提示。
- 「查看角色定义」跳转，携带角色代码定位到角色目录。
- 有授权权限时显示「调整授权」，并预填当前用户。

用户详情回答的是“这个用户现在能做什么”，而不是“系统有哪些角色”。

### 5.3 组织详情

删除完整角色定义区，保留：

- 成员当前组织角色和节点角色。
- 组织/节点范围内的成员访问调整。
- 「查看组织角色说明」跳转，预筛选 `ORGANIZATION` 与 `UNIT`。

组织详情回答的是“谁在这个组织拥有什么访问权”。平台角色和个人角色不在这里重复展示。

## 6. 自定义平台角色（二期候选能力）

当前接口、权限模型和已批准需求只支持查看内置角色以及管理角色绑定；没有角色创建、编辑、停用、版本管理或权限目录接口。因此「新建平台角色」不能作为第一期界面优化直接上线。

若产品批准第二期，建议只开放**受控的自定义平台角色**，暂不开放个人、组织或节点自定义角色：

- 新增独立权限 `platform.roles.manage`，不能复用 `platform.roles.assign`。
- 系统内置角色永久只读；自定义角色采用 `草稿 → 生效 → 停用`，已有授权的角色不得硬删除。
- 已生效角色修改权限时创建新版本，先展示受影响用户与新增/移除权限，再审批生效。
- 权限选择来自服务端权限目录，包含领域、风险等级、冲突集合和是否允许进入自定义角色。
- 所有者、个人生命周期、超级管理员引导、临时 PII 导出等保留专属流程，不允许拼装进普通自定义角色。
- 服务端强制职责分离，例如同一角色不得同时具有同类申请与审批权限。
- 创建、变更、启用、停用均记录审计；高风险变更要求近期认证与审批。
- 角色版本生效后刷新授权版本/缓存，确保现有会话不会继续使用旧权限。

所需新增能力至少包括：权限目录 API、角色草稿与版本 API、启用/停用 API、变更影响预检、冲突校验、审批接入、缓存失效和完整审计。未经需求与架构审批，生产界面不渲染「新建平台角色」入口。

## 7. 接口与实现改造清单

### 第一期：基于现有业务能力

- React 页面直接接管角色目录和授权管理，移除独立挂载的旧 `role-bindings` 视觉模块。
- 角色目录使用服务端返回的 `scope`、`assignable`、`permissions`，不得前端硬编码角色清单。
- 删除用户详情和组织详情中的 `RoleDefinitions`，改为上下文摘要和深链。
- 用户选择器复用用户查询接口；组织选择器复用组织查询接口；节点按选中组织加载。
- 授权接口补充或确认提交原因、特殊期限校验及可操作性错误码的展示契约。
- 授权列表 API 增加状态、角色、时间筛选和游标分页，避免全量加载。
- 审计页支持按 `resource_type`、`resource_id`、`action` 预置过滤，并能从授权详情深链进入。

### 第二期：自定义平台角色

- 角色定义返回 `built_in`、中文展示名、状态、版本及权限元数据。
- 新增自定义角色全生命周期、影响预检、冲突校验、审批与版本缓存失效能力。
- 同步更新正式需求、角色系统设计、OpenAPI、数据库迁移、授权测试和三语文案。

## 8. 验收标准

1. 四类作用域均准确显示，不再把平台或个人角色标为组织角色。
2. 管理员可在两次交互内看到任一角色的完整权限集合和授予方式。
3. 普通授权流程不要求手工输入用户、组织或节点 UUID。
4. 角色选择完全由服务端角色定义与作用域约束驱动，不存在前端角色白名单漂移。
5. 用户详情和组织详情不再出现完整角色目录，且能深链到对应角色定义。
6. 授权记录支持组合筛选、分页、详情及允许范围内的撤销；特殊角色不会出现误导性操作。
7. 审计日志使用统一事实源并在独立视图展示，不复制成第二套日志。
8. 无 `platform.roles.assign` 的管理员可查看目录和记录，但看不到新增/撤销入口。
9. 桌面、中宽和移动宽度可用；键盘焦点、抽屉关闭与焦点回退满足 WCAG 2.1 AA。
10. 简体中文、英文、日文文案同步交付，产品代码不依赖语言回退。
