# 组织工作区的单位作用域

组织工作区从 `/v1/me/authorization-context` 读取单位授权绑定。`Me.active_context.permissions` 仍只表示全组织权限；单位权限不合并进该数组。组织审计员同时具有单位管理员绑定时，保留原有全组织只读视图，并在独立的单位区域选择一个明确的授权根节点执行既有管理操作。多个不相交绑定分别选择，不合成为全组织写权限。

单位目录使用已有的 `GET /v1/organizations/{org}/units?root_unit_id={unit}`，成员列表使用已有的 `unit_id` 分页过滤。Tauri 仅在这个确切的单位目录 GET 路由接受单一、规范且非零的 UUID 查询；服务端仍决定调用者是否具有对应子树权限。其他路由、动词和查询参数不因此开放。

每次操作必须同时具有所选根节点的明确权限和当前授权上下文。创建单位必须指定子树内父节点；移动只选择所选根节点的后代及树内新父节点，并传递结构版本。成员操作要求成员全部既有单位归属以及新的归属都在所选子树内，使用成员版本执行归属替换，不截断跨子树成员事实。移除操作不提供 OWNER 目标。服务端继续执行最终授权与并发检查。

单位邀请沿用服务端已支持的 MEMBER 角色，必须指定非空的树内归属。不提供单位范围的邀请撤销、角色分配、配额或所有权管理；邀请撤销继续需要现有的全组织权限。界面以简体中文、英文和日文说明这些范围。

会话、上下文或授权版本变化会立即退役旧权限，取消目录及分页请求和待确认操作。每次新的 Me 快照（包括版本相同的快照）都会重新读取权威上下文，以处理定时到期的绑定。版本不匹配、未知响应或权限拒绝时，不用旧绑定发起新的范围请求；旧响应不能恢复已经退役的权限。结果未知的请求仍沿用既有相同事实与幂等键重试机制。

验证入口：`node --test account-platform/test/contract/organization-unit-scope.test.mjs`；应用的既有 `test:account-platform-organization-ui` 命令包含单位场景；原生 `organization_routes` 单元测试包含确切查询准入及拒绝边界。浏览器 fixture 的组织、成员及授权响应取自真实公开 Account 迁移创建的隔离测试数据库。fixture 使用合成主体，并不代表在线账号。

发布 Portal 时，须在最终合成的应用源码上运行现有 `npm run build:account-portal`（在 `pinvou3-app` 中），连同实际生成的 Portal 静态资源一起审核。隔离组件验证不能替代最终静态交付验证。
