# Registration creation dispatch and compensation

Account commits `identity_create_attempted_at` and captures the incremented business version under the registration row lock before any remote creation. Only that durable first winner calls `CreateMobileUserFirstAttempt`. A later request or recovery worker performs correlation lookup and schedules the existing recovery path while the result is unknown; it does not issue another Create, even when Find currently reports no user. Recovery claims still validate their generation and deadline under the row lock, including detached cleanup.

The existing internal `/internal/v1/users/mobile` request requires an explicit `first_attempt` boolean. Account's first-only client sends true. Missing attestation is rejected; false permits recovery of an already correlated result but cannot initiate creation. The permission remains `internal.identity.user.create`; registration correlation reads retain `internal.identity.registration.read`. No password-reset, profile-session or funding interface changes.

The adapter records `dispatched` before entering the directory Create call. A local transport timeout does not cancel or prove absence of the external mutation. Replaying a first request cannot dispatch again. The adapter returns `IDENTITY_CREATE_NOT_DISPATCHED` only when the same retained operation/username/mobile/handle binding is explicitly cancelled before any dispatch. Generic expiration, absent lookup, restart, missing binding, non-first request or previously dispatched operation cannot provide that proof. Unknown results continue lookup; unresolved absence requires operator investigation under the existing recovery boundary. This change introduces no new recovery SLA.

Account compensates only its first winner with that explicit typed proof and the exact captured business version. The SQL also requires the expected status and absent local identity/user; a concurrent later attempt defeats the CAS. Existing `compensation_evidence` stores the sanitized adapter authority, never-dispatched fact and attempt version. This is not a request to delete a possibly created external identity.

The existing operation binding map retains one entry per accepted operation for its original 48 hours. The two proof booleans add no entry or retention window. Revalidation and retries do not refresh that expiry. Plaintext password records retain their original 15-minute TTL and bounded capacity; expiring plaintext does not erase a still-valid dispatch proof. Operation cleanup uses a separate mutex and never waits for a plaintext record while holding the operation mutex. After 48 hours, missing proof remains unknown and cannot support compensation. The pre-existing operation map admission/capacity policy is unchanged; this patch adds no registration throughput quota.

Deploy by stopping and draining all old registration request/recovery writers before applying appended Account migration `900008_registration_create_dispatch`. An old binary can otherwise bypass the new first-only rule. Migration 900007 and all earlier published SQL remain unchanged. Existing ambiguous IDENTITY_CREATING and later possibly dispatched states are backfilled as already attempted, preserving their operation and ledger facts. They must not receive a fresh grant from a Find404. Previously terminal operations are not silently reopened. The migration down refuses to discard dispatch evidence; rollback requires a forward repair migration.

Formal tests cover a single durable first grant, explicit proof plus version CAS, stale recovery claims, public upgrade/backfill and down refusal, actual Register/SMS consume -> HTTP adapter -> RecoveryWorker -> late correlation -> one local identity, and adapter replay/expiry/restart/proof cleanup. The directory is controlled in these tests. Separate private causal review evidence preserves real 10-second transport timeouts, the 15-minute reference age and the real 30-second worker lease around a late remote HTTP completion. It does not claim live Keycloak deployment verification.

## Deterministic creation rejection

A first Create that returns the adapter's canonical HTTP 409 `USERNAME_ALREADY_REGISTERED` or `MOBILE_ALREADY_REGISTERED` is durably recorded as `REPAIR_REQUIRED`. This is a rejected dispatched request, not proof that creation was never dispatched: the original operation, reservations and first-attempt grant remain. No second Create, identity disable or automatic compensation follows. Generic 409, a conflict code at another status, transport failure and missing correlation remain unknown and keep the existing lookup-only recovery path.

The rejection checkpoint validates the recovery claim under the row lock and compares the locked current business version. A concurrent lookup-only backoff can advance that version while the sole Create is in flight; the checkpoint may still record rejection when no newer identity or account fact exists. It clears the recovery lease, preserves the first-attempt evidence and records one sanitized failed audit. A delayed ordinary request may finish its lookup after this rejection; generic retry scheduling must preserve this exact terminal-for-automatic-recovery predicate and cannot replace its reason. Other repair states retain their existing retry behavior. It cannot overwrite a correlated identity or committed account. The stricter captured-version CAS for never-dispatched compensation is unchanged.

The registration receipt is HTTP 202 with `status=REPAIR_REQUIRED`, the canonical `reason` and `manual_review_required=true`. An authorized query or original-key retry returns the same state after restart or password-reference expiration. Existing administrators see the operation in the repair queue; retry retains the same operation and explicit manual-review receipt. It does not promise automatic completion or release reservations. Compensation remains unavailable without the existing evidence. Operator investigation is required; this change adds no cancel/release policy or new migration.

Password-reset verification now uses the same configured 750 ms total-response floor as login verification and SMS admission. Invalid challenges, provider rejection, provider failure and success all wait for the remaining floor; a slower provider does not incur an extra full delay. Cancellation is respected and cannot turn an unfinished successful verification into success. This is the existing minimum-response defense, not a guarantee of identical provider timing or a new recovery SLA.
