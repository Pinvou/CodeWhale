# Registration challenge and password preparation

REGISTER and PASSWORD_RESET prepare passwords only after a successful slider challenge. The client first creates a challenge, then submits its mobile, purpose, offset and a stable operation UUID to Account's `/v1/auth/password-preparation-authorizations`. Account atomically consumes the existing captcha and records an authorization with its original captcha deadline. The endpoint rejects password fields and does not query account availability. Exact operation/facts retries return the original authorization; different facts conflict without renewing it.

Only then does the client send the password to Identity's `/v1/registration/password-prechecks`, with `X-Pinvou-Password-Preparation`. Identity verifies and claims the authorization through the authenticated Account internal endpoint. The only new receiver permission is `internal.auth.password-preparation.claim`, granted to the existing Identity workload. Account receives neither password nor password fingerprint. Public preparation without a grant is rejected; callers using the previous password-only allocation request must upgrade together. Already accepted references remain usable through their original 15-minute lifetime and the existing registration operation/recovery rules; they are not globally revoked. Their legacy provenance comes from an actual retained Identity record, never a client claim or an empty upstream response.

One authorization permits at most one password allocation and one SMS admission. Its durable claim is pinned to one Identity process incarnation. Concurrent or ACK-lost retries in that incarnation return the same handle and original handle expiry only for the same password and source/device facts. Another replica or a restarted process cannot take over the grant or recreate an unknown allocation. An explicit new captcha is required when that local state is unavailable. Passwords are never placed in browser persistent storage, Keycloak authentication notes, grants, Account JSON, or logs; existing password input memory remains local to the user interaction. A cancelled or retired client/page cannot use late completion to send SMS or restore its old reference.

The initial allocation window remains the original captcha deadline, checked again under the vault allocation lock after body receipt. It does not shorten the existing handle's 15-minute TTL. An already allocated receipt may be replayed after the captcha deadline without allocating or extending anything. Authority transport/ACK uncertainty returns `PASSWORD_PREPARATION_UNAVAILABLE` (503), retaining the same preparation operation for explicit retry. A definite invalid/expired/source-mismatched grant returns `PASSWORD_PREPARATION_INVALID` (403) and requires a new challenge. No automatic allocation or SMS retry is introduced. Existing global 429 responses preserve their bounded Retry-After hint; no new risk budget or captcha exemption is added.

Send consumes the authorization's SMS capability instead of consuming the same captcha twice. It then applies the existing PRECHECK source/target/global quota exactly once, validates the actual Identity reference and registration availability, reserves the operation under the unchanged uniqueness rules, and delivers SMS. A failed precheck/reservation sends no SMS. A consumed or uncertain Send is not replayed as another delivery: clients clear that proof and require a new challenge. A still valid handle may be reused with a new captcha/grant without another password allocation. LOGIN and PROFILE_MOBILE retain their original captcha paths, and final registration/reset permissions, SMS verification, fence and recovery semantics remain authoritative.

The old public availability precheck remains removed. Creating a challenge applies the existing CAPTCHA quota without checking availability. The original captcha table still binds only mobile, purpose, expiry and one-shot status; the new authorization separately binds the observed source/device at challenge completion. Account and Identity must see the same canonical source/device for this flow. Only configured exact immediate peers may supply an overwritten `X-Pinvou-Client-Source`; arbitrary XFF chains/private CIDRs never establish trust. Personal Compose uses its existing fixed edge/Keycloak addresses. The supported legacy loopback edge also overwrites the canonical source on both its Account and exact Identity preparation routes; its verified nginx immediate peer must be configured in both receivers. It does not forward the caller's source header. Helm exposes `security.passwordPreparationTrustedProxyIPs`; sites using an ingress must configure exact trusted peers and verify that it overwrites that header from its trusted connection address. No ingress installation or source forwarding is inferred from rendering a chart.

Identity uses the existing authenticated private Account service URL and rotating workload credential. Optional `ACCOUNT_CA_FILE` supplies isolated roots for an explicitly configured HTTPS Account endpoint; no ambient proxy or credential-forwarding redirect is allowed. This does not add an Account TLS listener or weaken any production service-auth gate. Default development mobile authentication remains disabled. The new append-only migration retains grant facts; existing SQL and the original captcha/handle/SMS/query-token durations are unchanged. Private build/tests do not constitute a live IdP, full Tauri, or deployed ingress acceptance.
