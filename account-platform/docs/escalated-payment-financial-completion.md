# 已升级付款异常的财务完成

适用 `DUPLICATE_PAYMENT`、`LATE_PAYMENT_CONFLICT`、`PAYMENT_FACT_CONFLICT`、`ILLEGAL_TRANSITION`，且原异常已经是 `RESOLVED / ESCALATE_FINANCIAL_REPAIR / PENDING`。

本功能只确认已经完成的财务事实，不创建付款、退款、账本分录、余额或权益。一名当前有 `platform.billing.repairs.request` 权限的管理员提出，另一名独立授权管理员重新核验后确认。原认领人与升级操作本身不能替代对完成证据的独立复核。

## 证据边界

- `PAYMENT_REPAIR`：原订单、原异常付款证据及同一提供方交易的已提交付款修复记录，连同其实际入账分录及权益来源。不能使用同订单另一笔付款的完成结果。
- `REFUND`：同一原订单及异常所指向交易的全额 `SUCCEEDED` 退款、提供方退款编号、实际退款账本分录与已撤销权益。不能拿首笔正常付款的退款关闭第二笔重复付款。
- `NO_FINANCIAL_EFFECT`：通过订单固定的提供方版本重新查询，严格匹配原订单、客户、商品、金额和币种的 FAILED 结果；本地不能存在付款交易、权益、成功付款证据、用户付款声明或更新的冲突观察。提出与复核分别执行新的权威查询。

仅有人工说明、截图摘要、客户端提交的金额、退款请求、超时或未知结果均不构成完成事实。现有 H3C 适配器不支持退款查询，不从查询订单或本地点数推断外部退款。没有可验证的完成证据时继续保留原资金阻断，运营应先在既有受控财务流程中取得实际完成回执。

`NO_FINANCIAL_EFFECT` 只完成财务异常结案及订单终态更新，不生成供应商失败确认记录（`payment_provider_failure_confirmations`）或 `billing.payment-provider.failure-confirmed.v1` 事件。因此，以此方式结案的订单不能作为供应商恢复探针的证明订单，财务完成回执也不能替代恢复审批所需的供应商确认。供应商恢复仍须通过独立的既有确认和探针流程取得符合条件的证明；本次结案不会赋予该订单恢复证明资格。

## 不变量

现有异常详情 GET 直接列出服务端验证通过的原交易修复/全额退款回执供选择，不要求管理员查库或填写金额。提出使用 `POST /admin/v1/payment-anomalies/{case_id}/financial-completion-proposals`，请求为 `proof_kind`、已有回执 `reference_id` 和 `reason`；无资金效果不提供 `reference_id`。复核使用 `POST /admin/v1/payment-anomalies/{case_id}/financial-completion-proposals/{proposal_id}/confirm`，只提交独立复核 `reason`。两个入口均要求原 `Idempotency-Key`、当前修复权限，并由 Portal 的已有会话/CSRF 代理转发。

旧证据未保存客户/商品绑定，或原证据与原订单金额、币种、交易、主体仍矛盾时，不能借当前查询结果默认为原异常已经完成；保留阻断并继续既有人工财务调查。列表只提供可证明的已完成回执，不将未知外部退款补成成功。

1. 提案不可变，记录原异常版本、服务端推导的事实及其摘要、提案人、理由和原幂等键。
2. 复核重算证据，必须与原提案一致，且复核人与提案人不同。失效提案可以用新键重新提出，不覆盖历史。
3. 同键同人同事实读取原回执；同键换人或换事实拒绝。完成命令与原异常、人工案件和订单投影在一个串行化事务提交。
4. 清除的只有已证明完成的原异常；其他付款审查、退款、拒付、应收款及注销阻断继续保留。
5. `NO_FINANCIAL_EFFECT` 的订单终态必须同时成立，不能只把异常标记完成而把原订单留在 MANUAL_REVIEW。
6. 注销或身份清理中的用户不获得新余额或权益。本功能不调用任何资金效果 writer；身份清理与新增收款的竞争围栏由独立的既有修复处理。

## 验收

使用真实迁移及运行角色，经过管理员路由与实际账本/退款/修复写方构造证据。分别验证成功、缺证据、错误订单/交易/金额/币种、同人复核、权限撤销、提案后事实变化、并发复核、提交结果未知后的同键恢复，以及资金完成后原注销评估可以继续且无新资金效果。保留独立退款/拒付出口，不批量回写历史 PENDING。

本文记录实现的验收合同，不代表代码、v3 审核、远端 CI 或现场发布已经通过。
